## 개념

절차대로 함수를 나열하면 데이터는 여기저기서 아무나 고친다. 객체 지향은 **데이터와 그 데이터를 다루는 함수를 한 객체에 묶고**(캡슐화), 바깥에는 "무엇을 할 수 있나"(메서드)만 보여 준다. 그러면 안을 바꿔도 바깥은 안 바뀐다.

여기에 **인터페이스**를 더한다. "결제한다"는 약속만 정해 두고 카드 결제·계좌 결제가 각자 구현하면, 쓰는 쪽은 어느 구현인지 몰라도 된다 — 다형성. 그래서 구현을 바꿔 끼우고 테스트에서 가짜로 대체할 수 있다. **상속**은 부모 클래스를 물려받는 것인데, 강하게 묶이므로 요즘은 "인터페이스 + 조합"을 더 권한다.

결제 기능을 객체 지향으로 짜 보자.

- 약속: `interface Payment { Receipt pay(Money amount); }`.
- 구현: `CardPayment implements Payment`, `BankPayment implements Payment`. 각자 자기 방식으로 `pay`를 짠다.
- 사용: `OrderService`는 `Payment payment` 필드만 갖고 `payment.pay(총액)`을 부른다. 카드인지 계좌인지 모른다.
- 결과: 간편결제를 추가하려면 `Payment` 구현 하나를 더 만들면 되고 `OrderService`는 그대로다. 테스트에서는 `FakePayment`를 꽂아 실제 결제 없이 돌린다.

## 왜 나왔나

프로그램이 커지자 "이 데이터를 누가 어디서 고치는지"를 알 수 없게 됐고, 한 곳을 고치면 다른 곳이 깨졌다. 데이터를 다루는 코드를 데이터 곁에 묶어 바깥에서 함부로 못 만지게 하고(캡슐화), 바깥에는 약속(인터페이스)만 드러내어 안을 바꿔도 바깥이 안 깨지게 한 것이 객체 지향이다. 스프링의 의존성 주입은 이 "약속에만 의존하기"를 프레임워크가 강제하는 장치다.

## 확인 질문

- 설명해 보기: 캡슐화가 지키는 것은?
  답: 객체의 데이터를 바깥에서 직접 못 고치게 하고, 정해진 메서드로만 다루게 해 데이터가 깨진 상태로 바뀌지 않게 한다.
- 다음 상태 예측: `OrderService`가 `CardPayment` 클래스를 직접 `new` 해서 쓴다. 계좌 결제를 추가하려면?
  답: `OrderService` 코드를 고쳐야 한다. `Payment` 인터페이스에 의존했다면 구현만 추가하면 된다.
- 다음 상태 예측: `Animal`을 상속한 `Dog`에서 `Animal`의 필드 이름을 바꿨다. 영향은?
  답: `Dog`를 포함한 모든 자식이 깨진다. 상속은 부모의 내부에 의존하는 강한 결합이다.

## 심화

### 네 기둥과 실제 무게

캡슐화(필드는 private, 메서드로 조작), 추상화(인터페이스로 "무엇"만 드러냄), 다형성(같은 호출이 구현에 따라 다르게 동작), 상속(코드 재사용). 실무에서 힘을 쓰는 것은 캡슐화와 다형성이다. 상속은 부모의 구현에 자식이 묶여 부모 변경이 자식을 깨뜨리고(취약한 기반 클래스), 계층이 깊어지면 어디서 동작이 정해지는지 따라가기 어렵다.

### 오버로딩과 오버라이딩 — 다형성의 두 얼굴

**오버로딩**은 같은 이름의 메서드를 매개변수 타입·개수만 다르게 여러 개 두는 것이다(`print(int)`, `print(String)`). 어느 것을 부를지는 **컴파일 시점**에 인자의 정적 타입으로 정해진다. **오버라이딩**은 자식 클래스가 부모(또는 인터페이스)의 메서드를 같은 시그니처로 다시 정의하는 것이고, 어느 것이 실행될지는 **실행 시점**에 객체의 실제 타입으로 정해진다(동적 디스패치). 다형성이라 부르는 것은 후자다.

| | 오버로딩 | 오버라이딩 |
|---|---|---|
| 조건 | 이름 같고 매개변수 다름(반환 타입만 다르면 안 됨) | 시그니처 같음, 반환은 같거나 하위 타입, 접근 제한을 좁힐 수 없음 |
| 결정 시점 | 컴파일 시 — 인자 변수의 선언 타입 | 실행 시 — 객체의 실제 타입 |
| `static`·`private`·`final` | 오버로딩 가능 | 오버라이딩 불가(static은 숨김, private은 안 보임, final은 금지) |

`Animal a = new Dog(); a.sound()`는 `Dog.sound()`가 실행되지만(오버라이딩), `feed(a)`에 `feed(Animal)`과 `feed(Dog)`가 있으면 `feed(Animal)`이 불린다(오버로딩은 `a`의 선언 타입 기준). `@Override`를 붙이면 시그니처가 어긋났을 때 컴파일러가 잡는다 — 오타로 오버로딩이 되어 버리는 실수를 막는다.

### 상속보다 조합

`ArrayList`를 상속해 "추가 횟수 세는 리스트"를 만들면 `addAll`이 내부에서 `add`를 부르는지에 따라 두 배로 세어진다 — 부모 구현에 의존한 결과. 대신 `List`를 필드로 갖고 위임하면 부모 구현이 바뀌어도 안전하다(Effective Java Item 18). 상속은 "진짜 is-a이고 부모가 상속을 위해 설계된 경우"로 좁힌다.

### 인터페이스 자르기

인터페이스가 너무 크면 구현체가 안 쓰는 메서드까지 구현해야 하고, 너무 잘게 자르면 파편이 된다. "쓰는 쪽이 필요로 하는 것"을 기준으로 자른다(인터페이스 분리). 구현이 하나뿐인 인터페이스를 미리 만드는 것은 대개 과하다 — 두 번째 구현이나 테스트 대체가 필요해질 때 뽑는다.

### 불변 객체와 값 객체

필드를 final로 두고 바꾸는 대신 새 객체를 만들면 여러 스레드가 공유해도 안전하고 캐시 키로 쓸 수 있다. `Money`, `Email`처럼 값으로 구별되는 것은 값 객체로 두고 `equals`를 값 기준으로 정의한다(다음 장). Java의 `record`가 이 용도다.

### 실무에서는

- 스프링 빈은 인터페이스에 의존하게 짜고 구현을 주입받는다. 테스트에서 `@MockBean`이나 가짜 구현으로 바꿔 끼우는 것이 다형성의 실용적 이득이다.
- 서비스 클래스에 getter/setter만 있는 데이터 클래스를 넘기고 로직을 서비스가 다 하면 캡슐화가 없는 절차적 코드다. "재고 차감"은 `Stock.decrease(qty)`처럼 데이터 곁에 둔다.
- JPA 엔티티의 세터를 열어 두면 아무 데서나 상태를 바꾼다. 의도를 담은 메서드(`order.cancel()`)로 바꾼다.
- 상속 계층으로 만든 `BaseService`·`AbstractController`는 시간이 지나면 모두가 의존하는 신이 된다. 공통 기능은 조합·AOP로.

### 면접 질문

#### 객체 지향의 특징을 설명하고, 실무에서 가장 중요한 것을 꼽는다면?

캡슐화(데이터와 조작을 묶고 바깥에서 직접 못 만지게), 추상화(인터페이스로 무엇만 드러냄), 다형성(같은 호출이 구현마다 다르게 동작), 상속(재사용)입니다. 실무에서는 캡슐화와 다형성이 핵심입니다.
캡슐화가 있어야 데이터가 깨진 상태로 바뀌는 곳을 한 클래스 안으로 좁힐 수 있고, 다형성이 있어야 구현을 바꿔 끼우고 테스트에서 대체할 수 있습니다. 상속은 부모 구현에 강하게 묶여 취약한 기반 클래스 문제를 낳아 조합으로 대체하는 편입니다.
예를 들어 `Payment` 인터페이스에 의존하는 `OrderService`는 카드·계좌·간편결제를 코드 수정 없이 바꿔 끼우고, 테스트에선 가짜 결제를 꽂습니다. 한계는 인터페이스를 잘못 자르면 오히려 바꾸기 어려워지고, 구현이 하나뿐인데 미리 만든 인터페이스는 간접 계층만 늘린다는 점입니다.

#### 오버로딩과 오버라이딩의 차이는 무엇인가요?

오버로딩은 같은 이름에 매개변수가 다른 메서드를 여러 개 두는 것으로 컴파일 시점에 인자의 선언 타입으로 골라지고, 오버라이딩은 자식이 부모의 메서드를 같은 시그니처로 다시 정의하는 것으로 실행 시점에 객체의 실제 타입으로 골라집니다.
다형성(같은 호출이 객체에 따라 다르게 동작)은 오버라이딩에서 나오고, 오버로딩은 편의상 이름을 공유하는 것뿐입니다.
예를 들어 `Animal a = new Dog()`에서 `a.sound()`는 Dog의 것이 실행되지만, `feed(Animal)`·`feed(Dog)` 중에서는 `feed(Animal)`이 불립니다. 한계는 오버로딩이 많으면 `null`이나 자동 형변환 때문에 어느 것이 불리는지 헷갈리고, 오버라이딩은 `static`·`private`·`final`에는 적용되지 않는다는 점입니다.

- 오답: "반환 타입만 다르게 해도 오버로딩이다" — 매개변수가 같고 반환 타입만 다르면 컴파일 오류다.
- 오답: "static 메서드도 오버라이딩된다" — static은 숨김(hiding)이며 선언 타입으로 정해진다.

#### 서비스 코드가 엔티티의 getter/setter로 필드를 직접 바꾸며 로직을 처리합니다. 문제가 있나요?

캡슐화가 깨진 상태라, 같은 규칙("재고는 0 밑으로 못 간다")이 여러 서비스에 흩어지고 한 곳이 빠뜨리면 데이터가 깨집니다.
데이터를 다루는 규칙이 데이터 곁이 아니라 호출하는 쪽마다 있으면 규칙을 바꿀 때 모든 호출처를 찾아 고쳐야 하고, 세터가 열려 있으니 어디서든 잘못된 상태로 바꿀 수 있습니다.
`stock.setQty(stock.getQty() - n)` 대신 `stock.decrease(n)`을 두고 그 안에서 검증하면 규칙이 한 곳에 모입니다. 한계는 모든 것을 엔티티에 넣으면 엔티티가 비대해지므로, 여러 엔티티에 걸친 규칙은 도메인 서비스로 빼는 균형이 필요하다는 점입니다.
