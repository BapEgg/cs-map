## 개념

운영체제가 프로세스에 준 메모리 영역(코드·데이터·힙·스택)을 JVM은 자기 방식으로 다시 나눈다. `new`로 만든 **객체는 전부 힙**에 산다 — 모든 스레드가 공유한다. 메서드를 부를 때마다 지역 변수·매개변수·돌아갈 위치를 담은 프레임이 **스택**에 쌓인다 — 스레드마다 따로. 클래스 구조·메서드 바이트코드·상수는 **메타스페이스**(메서드 영역)에 있다.

GC가 치우는 것은 힙뿐이다. 스택은 메서드가 끝나면 프레임이 저절로 빠지고, 메타스페이스는 클래스가 언로드될 때만 준다.

`Order o = new Order(42)`를 실행하는 스레드를 따라가 보자.

- 스택: 현재 메서드의 프레임에 지역 변수 `o` 자리가 생긴다. `o`에는 객체가 아니라 **주소**가 들어간다.
- 힙: `Order` 객체(필드 `id=42`, 객체 헤더)가 힙에 만들어지고, 그 주소가 `o`에 담긴다.
- 메타스페이스: `Order` 클래스의 필드 목록·메서드 코드는 처음 로딩될 때 여기 한 번만 올라갔다.
- 메서드 종료: 프레임이 빠지며 `o`가 사라진다. 객체는 아직 힙에 있고, 아무도 가리키지 않으니 GC 대상이 된다.
- 결과: 객체는 힙에, 그 객체를 가리키는 변수는 스택에. 다른 스레드가 같은 객체 주소를 갖고 있으면 그 객체는 공유된다.

## 왜 나왔나

C는 프로그래머가 `malloc`/`free`로 힙을 직접 관리하다 해제를 잊거나(누수) 두 번 해제하거나 해제 뒤 접근하는(댕글링) 버그를 냈다. JVM은 힙을 자기가 관리하고 GC가 치우게 해 그 버그를 없앴다. 대신 "무엇이 힙이고 무엇이 스택인가, GC는 언제 무엇을 치우나"를 알아야 메모리 문제를 다룰 수 있게 됐다.

## 확인 질문

- 설명해 보기: 힙과 스택의 차이를 "누가 공유하나"로.
  답: 힙은 모든 스레드가 공유하고 객체가 산다. 스택은 스레드마다 따로 있고 메서드 프레임(지역 변수)이 산다.
- 다음 상태 예측: 두 스레드가 같은 `Order` 객체의 참조를 가졌다. 한쪽이 필드를 바꾸면?
  답: 다른 쪽도 본다(가시성 시점은 별개). 객체는 힙에 하나뿐이고 둘 다 그 주소를 갖고 있다.
- 다음 상태 예측: 정적 `List`에 요청마다 객체를 `add`하고 지우지 않으면?
  답: 정적 필드가 살아 있는 한 그 리스트의 객체들은 GC 대상이 아니다. 힙이 차서 `OutOfMemoryError: Java heap space`.

## 심화

### 영역별 정리

| 영역 | 무엇 | 공유 | 크기 옵션 | 넘치면 |
|---|---|---|---|---|
| 힙 | 객체, 배열 | 모든 스레드 | `-Xms`(초기) `-Xmx`(최대) | `OutOfMemoryError: Java heap space` |
| 스택 | 메서드 프레임(지역 변수, 피연산자, 반환 주소) | 스레드별 | `-Xss`(기본 1MB, 64비트 리눅스) | `StackOverflowError` |
| 메타스페이스 | 클래스 메타데이터, 메서드 바이트코드 | 모든 스레드 | `-XX:MaxMetaspaceSize`(기본 무제한) | `OutOfMemoryError: Metaspace` |
| 네이티브 메모리 | 스레드 스택, JIT 코드 캐시, NIO 다이렉트 버퍼 | — | 컨테이너 한도 | 프로세스 자체가 죽음(OOM killer) |

JDK 8에서 PermGen이 메타스페이스로 바뀌어 네이티브 메모리를 쓰고 기본 상한이 없어졌다.

### 운영체제 관점과 이어 보기

JVM 힙은 운영체제가 준 프로세스 힙의 일부를 JVM이 미리 크게 잡아 자기가 나눠 쓰는 것이다. JVM 스택 하나 = 운영체제 스레드의 스택. 그래서 컨테이너 메모리 한도는 `-Xmx`보다 커야 한다 — 힙 외에 메타스페이스·스레드 스택·코드 캐시·다이렉트 버퍼가 있다. JDK 10+는 컨테이너 한도를 인식해 기본 최대 힙을 그 1/4로 잡는다(`-XX:MaxRAMPercentage`로 조정).

### 참조와 객체는 다르다

변수에 든 것은 주소다. `Order a = new Order(); Order b = a;`면 객체는 하나고 참조가 둘이다. 메서드에 객체를 넘기면 주소가 복사되므로 안에서 필드를 바꾸면 밖에서도 보인다 — "자바는 값 전달"이지만 그 값이 참조다. 지역 변수·기본형은 스택에, 객체는 힙에.

### 실무에서는

- `OutOfMemoryError: Java heap space`는 힙 부족. 힙 덤프(`-XX:+HeapDumpOnOutOfMemoryError`)를 떠서 무엇이 차지하는지 본다. 대개 캐시·정적 컬렉션·리스너 누수.
- `Metaspace` OOM은 클래스가 계속 만들어지는 것 — 동적 프록시·스크립트 엔진·클래스 로더 누수(핫 리로드 반복).
- 컨테이너에서 JVM이 `-Xmx`는 남았는데 죽는다면 네이티브 메모리(스레드·다이렉트 버퍼)가 한도를 넘은 것. `-Xmx`를 컨테이너 한도의 50~75%로.
- 스레드를 많이 만들면 스택 예약이 그만큼 든다. 1MB × 1,000 스레드 = 1GB 가상 메모리.

### 면접 질문

#### JVM 메모리 구조를 설명하고, 힙과 스택의 차이를 말해 보세요.

JVM 메모리는 객체가 사는 힙, 스레드마다 메서드 프레임이 쌓이는 스택, 클래스 정보가 있는 메타스페이스, 그리고 JIT 코드·다이렉트 버퍼 같은 네이티브 영역으로 나뉩니다. 힙은 모든 스레드가 공유하고 GC가 관리하며, 스택은 스레드별로 따로이고 메서드가 끝나면 프레임이 자동으로 빠집니다.
`Order o = new Order()`에서 객체는 힙에, 그 주소를 담은 `o`는 스택에 있으므로, 두 스레드가 같은 주소를 가지면 객체는 공유되고 지역 변수는 공유되지 않습니다.
그래서 힙이 넘치면 `OutOfMemoryError: Java heap space`, 재귀가 깊으면 `StackOverflowError`가 납니다. 한계는 `-Xmx`가 프로세스 메모리 전부가 아니라 컨테이너 한도를 잡을 때 메타스페이스·스레드 스택·다이렉트 버퍼를 따로 계산해야 한다는 점입니다.

#### 서버가 며칠 돌면 메모리가 계속 늘다가 OOM으로 죽습니다. 어떻게 찾나요?

`-XX:+HeapDumpOnOutOfMemoryError`로 힙 덤프를 떠서 분석 도구(Eclipse MAT, VisualVM)로 어떤 객체가 어디에서 참조되어 살아남는지 봅니다. GC 로그에서 Full GC 뒤에도 힙이 안 줄어드는 추세면 누수입니다.
GC는 도달 가능한 객체를 치우지 않으므로, 정적 컬렉션·캐시·리스너·`ThreadLocal`(스레드 풀에서 안 지움)이 참조를 붙들고 있으면 안 쓰는 객체가 영원히 남습니다.
덤프에서 지배 트리(dominator tree)로 가장 큰 참조 사슬을 찾아 그 끝의 정적 필드나 캐시를 고칩니다 — 크기 상한·만료를 두거나 요청 끝에 `ThreadLocal.remove()`. 한계는 덤프가 힙 크기만큼 커서 운영에서 뜨기 부담스러우니, 평소 GC 로그·힙 사용량 추세를 모니터링해 미리 잡는 것이 낫습니다.

- 꼬리: Full GC 뒤 힙 사용량이 계단처럼 오르면 무엇을 뜻하나요?
