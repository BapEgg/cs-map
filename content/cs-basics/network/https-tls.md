## 개념

HTTP는 글이 그대로 흘러가서 중간 누구나(공유기, 통신사, 카페 와이파이) 읽고 바꿀 수 있다. HTTPS는 HTTP 아래에 **TLS**를 깔아 세 가지를 해결한다. 상대 서버가 진짜인지 **확인**하고(인증서), 내용을 남이 못 읽게 **암호화**하고, 도중에 바뀌지 않았는지 **검증**한다.

핵심은 두 종류의 암호를 섞는 것이다. 비대칭 암호(공개 키·개인 키)는 열쇠를 안전하게 나눠 갖는 데 쓰고, 실제 데이터는 빠른 대칭 암호로 잠근다. "이 서버가 정말 example.com인가"는 인증 기관(CA)이 서명한 인증서로 확인한다.

브라우저가 `https://shop.example`에 처음 연결하는 과정(TLS 1.3)을 따라가 보자.

- 클라이언트: "이런 암호 방식들을 쓸 수 있고, 키 교환용 내 공개 값은 이것"을 보낸다.
- 서버: 자기 인증서(`shop.example`, CA 서명, 공개 키)와 키 교환용 공개 값을 보낸다. 양쪽이 각자 공개 값으로 같은 **세션 키**를 계산한다 — 열쇠 자체는 선로에 흐르지 않는다.
- 클라이언트: 인증서의 서명이 믿는 CA(운영체제·브라우저에 내장)에서 나왔는지, 도메인이 맞는지, 기간이 유효한지 확인한다.
- 결과: 왕복 한 번 뒤 세션 키로 암호화된 HTTP가 오간다. 중간자는 암호문만 보고, 인증서를 위조하려면 CA 서명이 필요해 실패한다.

## 왜 나왔나

로그인 비밀번호와 카드 번호가 평문으로 흐르는 것을 막아야 했다. 암호화만으로는 부족했다 — 중간자가 "내가 서버다"라며 끼어들면 암호화된 채로 그에게 보낸다. 그래서 "이 공개 키가 정말 그 도메인의 것"을 제3자(CA)가 보증하는 체계가 붙었고, 그것이 인증서다. 오늘날 브라우저는 HTTP를 "안전하지 않음"으로 표시하고, HTTP/2·HTTP/3은 사실상 TLS를 전제한다.

## 심화

### 인증서와 신뢰 사슬

인증서는 "이 공개 키는 이 도메인 것"이라는 문서에 CA가 서명한 것이다. 브라우저·운영체제에는 믿는 루트 CA 목록이 있고, 서버 인증서 → 중간 CA → 루트 CA로 서명이 이어져야 한다. 서버가 중간 인증서를 빠뜨리면 브라우저는 되지만(자동 보완) Java 클라이언트는 실패하는 일이 흔하다. Let's Encrypt 인증서는 90일이라 자동 갱신이 필수다.

### 왜 두 종류의 암호를 섞나

비대칭 암호는 공개 키로 잠그면 개인 키로만 열려 열쇠 배송 문제를 풀지만 느리다. 대칭 암호는 빠르지만 양쪽이 같은 열쇠를 미리 가져야 한다. 그래서 비대칭(정확히는 키 교환 알고리즘)으로 세션 키를 만들고, 그 키로 대칭 암호화한다. TLS 1.3은 매 연결마다 새 키를 만들어(전방 비밀성) 나중에 개인 키가 새도 과거 통신은 못 푼다.

### handshake 비용과 재개

TLS 1.3은 왕복 1회(1-RTT), 1.2는 2회다. 연결마다 치르므로 keep-alive·커넥션 풀로 연결을 재사용하고, 세션 재개(PSK)로 다음 연결은 더 짧게 한다. HTTP/3(QUIC)는 TCP handshake와 TLS handshake를 합쳤다.

### 어디서 끝나나 — TLS 종료

보통 로드밸런서나 리버스 프록시(Nginx, ALB)가 TLS를 풀고, 뒤 서버(Tomcat)로는 평문 HTTP로 보낸다(TLS 종료). 서버 코드가 `https`인지 보려면 프록시가 붙인 `X-Forwarded-Proto`를 읽어야 한다. 내부망도 암호화해야 하는 환경(제로 트러스트)에서는 서비스 사이도 mTLS를 쓴다.

### 실무에서는

- 인증서 만료가 가장 흔한 장애다. 만료일 모니터링과 자동 갱신(certbot·ACM)을 둔다.
- Java 클라이언트의 `PKIX path building failed`는 인증서 사슬을 못 이었다는 뜻 — 서버가 중간 인증서를 안 보내거나 사내 CA가 JVM 신뢰 저장소에 없다.
- 개발 편의로 인증서 검증을 끄는 코드(`TrustAll`)가 운영에 남으면 중간자 공격에 그대로 뚫린다.
- 쿠키에 `Secure`를 붙여 HTTPS로만 보내게 하고, `Strict-Transport-Security`로 브라우저가 HTTP로 접속하지 않게 한다.

### 면접 질문

#### HTTPS는 어떻게 안전을 보장하나요? 대칭 키와 비대칭 키는 각각 어디에 쓰이나요?

TLS handshake에서 인증서로 서버를 확인하고 키 교환으로 둘만 아는 세션 키를 만든 뒤, 그 대칭 키로 데이터를 암호화합니다. 비대칭(공개 키) 방식은 열쇠를 안전하게 합의하고 서명을 검증하는 데, 대칭 방식은 실제 데이터 암호화에 씁니다.
비대칭은 열쇠를 미리 나누지 않아도 되지만 느리고, 대칭은 빠르지만 열쇠를 나눠야 하므로 둘을 이어 붙인 것입니다. 인증서는 "이 공개 키가 그 도메인 것"을 CA가 서명으로 보증해 중간자를 막습니다.
예를 들어 카페 와이파이의 공격자는 암호문과 접속 도메인만 볼 수 있고, 가짜 서버를 세우려 해도 CA 서명 인증서가 없어 브라우저가 거부합니다. 한계는 TLS가 "중간"만 지키므로 서버 안의 처리·저장과 클라이언트 기기는 별도로 지켜야 한다는 점입니다.

#### 로드밸런서에서 TLS를 종료하면 뒤 서버는 안전한가요?

로드밸런서와 서버 사이 구간은 평문이므로, 그 구간이 신뢰할 수 있는 사설망이라는 전제에서만 안전합니다.
TLS 종료는 인증서 관리와 암호화 부담을 한곳에 모으고 뒤 서버를 단순하게 하는 장점이 있지만, 내부 구간 도청·변조는 막지 못하고 서버 코드는 원래 요청이 HTTPS였는지를 `X-Forwarded-Proto`로만 압니다.
사설망을 신뢰할 수 없거나 규제가 요구하면 로드밸런서에서 다시 TLS로 감싸거나(재암호화) 서비스 간 mTLS를 씁니다. 한계는 그만큼 인증서를 서비스마다 관리해야 한다는 비용입니다.
