## 개념

프록시는 **중간에서 요청을 대신 받아 넘기는 서버**다. 누구 편에 서 있느냐로 둘로 나뉜다. 클라이언트 쪽에 서서 바깥으로 나가는 요청을 대신 보내는 것이 **포워드 프록시**(회사 방화벽, 우회 프록시), 서버 앞에 서서 들어오는 요청을 받아 뒤의 서버들에 넘기는 것이 **리버스 프록시**다. 리버스 프록시가 여러 서버에 요청을 나눠 주면 그것이 **로드밸런서**다.

서버 앞의 프록시는 넘기기만 하지 않는다. TLS를 풀고(종료), 정적 파일이나 캐시된 응답을 대신 주고, 죽은 서버를 빼고, 요청 수를 제한한다. 클라이언트는 프록시의 주소 하나만 안다.

서버 3대 앞의 로드밸런서로 요청이 오는 상황을 따라가 보자.

- 시작: DNS가 `shop.example`을 로드밸런서 IP로 푼다. 클라이언트는 그 IP의 443으로 TLS 연결을 맺는다.
- 진행: 로드밸런서가 TLS를 풀고 요청을 읽는다. 헬스체크로 살아 있는 서버 3대 중 하나를 규칙(라운드 로빈·최소 연결)으로 고르고, `X-Forwarded-For: 클라이언트IP`를 붙여 사설망으로 평문 HTTP를 보낸다.
- 결과: 서버 2가 처리해 응답하면 로드밸런서가 클라이언트에게 돌려준다. 서버 2가 죽으면 다음 요청은 1이나 3으로 간다. 클라이언트는 서버가 몇 대인지 모른다.

## 왜 나왔나

서버 한 대로 감당이 안 되면 여러 대를 두어야 하는데, 클라이언트에게 주소를 여러 개 알려 줄 수는 없었다. 주소 하나를 받아 뒤로 나누는 중간 서버가 필요했고, 기왕 중간에 있으니 TLS·캐시·압축·인증 같은 공통 일도 거기 모았다. 반대편의 포워드 프록시는 내부망에서 바깥으로 나갈 때 통제·캐시하려고 생겼다.

## 확인 질문

- 설명해 보기: 포워드 프록시와 리버스 프록시의 차이를 "누구를 숨기나"로 말해 보세요.
  답: 포워드는 클라이언트를 숨긴다(서버는 프록시만 본다). 리버스는 서버를 숨긴다(클라이언트는 프록시만 본다).
- 다음 상태 예측: 로드밸런서 뒤 서버 3대 중 하나가 죽으면 사용자는?
  답: 헬스체크가 감지한 뒤로는 나머지 2대로만 간다. 감지 전 몇 초 동안은 일부 요청이 실패할 수 있다.
- 다음 상태 예측: 서버가 세션을 메모리에 두는데 로드밸런서가 라운드 로빈이면?
  답: 요청마다 다른 서버로 가서 로그인이 풀린 것처럼 보인다. 세션을 공유 저장소로 옮기거나 sticky session을 쓴다.

## 심화

### L4와 L7

L4 로드밸런서는 IP·포트만 보고 TCP 연결 단위로 넘긴다 — 빠르고 단순하지만 요청 내용을 모른다. L7은 HTTP를 읽어 경로·헤더·쿠키로 나누고, TLS 종료·캐시·헤더 조작·재시도를 한다. Nginx·HAProxy·AWS ALB가 L7, AWS NLB가 L4다.

### 분산 규칙과 상태

라운드 로빈(차례로), 가중치, 최소 연결(가장 한가한 곳), IP 해시(같은 클라이언트는 같은 서버 — sticky). sticky는 세션을 서버 메모리에 둘 때의 임시방편이고, 서버가 죽으면 그 사용자들은 어차피 잃는다. 세션은 Redis로 빼는 것이 정석이다.

### 헬스체크와 타임아웃

프록시는 뒤 서버에 주기적으로 `/health`를 쳐서 살아 있는지 본다. 응답이 늦으면 502(뒤 서버 응답 불량)·504(뒤 서버 시간 초과)를 낸다 — 애플리케이션 로그에는 없는 오류라 프록시의 타임아웃 설정을 서버 처리 시간과 맞춰야 한다. 느린 요청 하나가 프록시 타임아웃을 넘으면 서버는 여전히 처리 중인데 클라이언트는 이미 실패를 봤고, 재시도하면 두 번 처리된다.

### API 게이트웨이

마이크로서비스 앞의 리버스 프록시에 인증·요율 제한·경로 라우팅·로깅을 모은 것이다. 편리하지만 모든 요청이 지나는 단일 지점이라 여기가 느리면 전부 느리고, 여기서 하는 일이 늘수록 "얇은 프록시"가 아니게 된다.

### 실무에서는

- 서버 코드가 보는 클라이언트 IP는 프록시 IP다. `X-Forwarded-For`를 읽되 신뢰하는 프록시 수만큼만 믿는다.
- 무중단 배포는 로드밸런서가 서버를 하나씩 빼고(드레이닝, 진행 중 요청 끝날 때까지 기다림) 새 버전을 넣고 다시 붙이는 일이다.
- 프록시의 요청 본문 크기 제한(`client_max_body_size`)이 서버 설정보다 작으면 큰 업로드가 413으로 프록시에서 막힌다.
- WebSocket·SSE는 오래 열린 연결이라 프록시의 유휴 타임아웃과 업그레이드 헤더 전달 설정이 필요하다.

### 면접 질문

#### 리버스 프록시와 로드밸런서는 무엇이고 왜 두나요?

리버스 프록시는 서버 앞에서 요청을 대신 받아 뒤로 넘기는 중간 서버이고, 그중 여러 서버에 요청을 나눠 주는 것이 로드밸런서입니다. 서버를 늘려도 클라이언트에겐 주소 하나만 보이게 하고, TLS 종료·캐시·헬스체크·요율 제한 같은 공통 일을 한곳에 모으려고 둡니다.
클라이언트는 프록시만 알기 때문에 뒤에서 서버를 빼고 넣고 배포해도 주소가 안 바뀌고, 죽은 서버는 헬스체크로 자동으로 빠집니다.
예를 들어 Nginx나 AWS ALB가 443에서 TLS를 풀고 사설망의 Tomcat 여러 대로 나눕니다. 한계는 프록시 자체가 단일 지점이라 이중화가 필요하고, 프록시 타임아웃이 서버보다 짧으면 502/504가 애플리케이션 로그 없이 발생한다는 점입니다.

#### 사용자는 504를 보는데 서버 로그에는 요청이 정상 처리로 남아 있습니다. 무슨 일인가요?

프록시(로드밸런서)의 응답 대기 타임아웃이 서버의 처리 시간보다 짧아서, 프록시가 먼저 포기하고 504를 낸 뒤 서버는 계속 처리를 끝낸 것입니다.
프록시는 뒤 서버의 응답을 정해진 시간만 기다리므로, 느린 쿼리나 외부 호출로 처리가 길어지면 프록시 쪽에서 끊깁니다. 서버는 끊긴 줄 모르고 끝까지 돌아 로그에는 200으로 남습니다.
대응은 느린 처리 자체를 줄이고(쿼리·외부 호출 타임아웃), 프록시 타임아웃을 서버의 최대 처리 시간에 맞추며, 클라이언트가 재시도했을 때 두 번 처리되지 않게 멱등 키를 두는 것입니다. 오래 걸리는 작업은 즉시 202로 받고 비동기로 처리한 뒤 결과를 따로 알리는 구조로 바꿉니다.

- 꼬리: 배포 중 요청이 끊기지 않게 하는 드레이닝이란?
