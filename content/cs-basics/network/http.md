## 개념

HTTP는 클라이언트가 **요청**을 보내고 서버가 **응답**을 돌려주는 글 형식이다. 요청은 "무엇에(경로) 무엇을(메서드) 해 달라"와 부가 정보(헤더), 필요하면 본문으로 이루어진다. 응답은 결과를 세 자리 숫자(상태 코드)로 먼저 알리고 헤더·본문이 따른다. 메서드는 GET(조회), POST(생성·처리), PUT(통째로 바꾸기), PATCH(일부 수정), DELETE(삭제)가 주로 쓰인다.

서버는 요청 사이에 아무것도 기억하지 않는다(무상태). 그래서 "누구인지"는 매 요청에 쿠키나 토큰으로 실어 보낸다.

주문 조회 요청 하나를 따라가 보자.

- 요청: `GET /orders/42 HTTP/1.1`, 헤더 `Host: shop.example`, `Authorization: Bearer …`. 본문 없음.
- 서버: 42번 주문을 찾는다. 있으면 `200 OK`에 JSON 본문, 없으면 `404 Not Found`, 토큰이 틀리면 `401 Unauthorized`, 남의 주문이면 `403 Forbidden`.
- 응답: `HTTP/1.1 200 OK`, `Content-Type: application/json`, `Content-Length: 87`, 빈 줄, 본문.
- 결과: 클라이언트는 상태 코드로 성공·실패 종류를 먼저 알고, 본문을 파싱한다. 같은 GET을 열 번 보내도 서버 상태는 안 바뀐다(안전·멱등).

## 왜 나왔나

문서를 링크로 연결해 주고받으려고 만든 단순한 요청-응답 약속이 웹 전체의 공용어가 됐다. 처음엔 요청마다 TCP 연결을 새로 맺고(HTTP/1.0), 느려서 연결을 재사용하게 했고(1.1 keep-alive), 그래도 한 연결에 한 요청씩 순서대로라 막히니 한 연결에 여러 요청을 섞어 보내게 했고(2, 다중화), TCP 자체의 순서 대기까지 피하려고 UDP 위로 옮겼다(3, QUIC).

## 확인 질문

- 설명해 보기: 요청의 세 부분과 응답의 세 부분을 말해 보세요.
  답: 요청은 시작줄(메서드·경로·버전)·헤더·본문, 응답은 상태줄(버전·상태 코드)·헤더·본문.
- 다음 상태 예측: 같은 `DELETE /orders/42`를 두 번 보내면 두 번째 응답은?
  답: 이미 없으므로 보통 404(또는 204). 서버 상태는 첫 번째와 같다 — DELETE는 멱등이다.
- 다음 상태 예측: 로그인은 됐는데 남의 주문을 조회하면 상태 코드는?
  답: 403. 401은 "누군지 모름", 403은 "누군지 알지만 권한 없음".

## 심화

### 메서드의 성질 — 안전과 멱등

안전(safe)은 서버 상태를 안 바꾸는 것(GET, HEAD), 멱등(idempotent)은 여러 번 해도 한 번과 같은 것(GET, PUT, DELETE; POST는 아님, PATCH는 정의상 아님). 브라우저·프록시·재시도 로직이 이 성질을 믿는다 — GET은 캐시하고 미리 가져오며, 멱등 요청은 실패하면 다시 보내도 된다. POST를 두 번 보내면 주문이 두 건 생기므로 재시도에는 멱등 키가 필요하다(서비스 설계 장).

### 상태 코드

2xx 성공(200, 201 생성됨, 204 본문 없음), 3xx 다른 곳으로(301 영구, 302 임시, 304 캐시 그대로 써라), 4xx 클라이언트 잘못(400 형식 오류, 401 인증 필요, 403 권한 없음, 404 없음, 409 충돌, 429 너무 많음), 5xx 서버 잘못(500, 502 뒤 서버 응답 불량, 503 과부하, 504 뒤 서버 시간 초과). 502·504는 대개 프록시가 내는 것이라 원인은 그 뒤에 있다.

### 헤더로 하는 일

`Content-Type`(본문 형식), `Content-Length`(본문 길이 — TCP는 경계가 없어 필요), `Host`(한 IP에 여러 도메인), `Authorization`, `Cookie`/`Set-Cookie`, `Cache-Control`/`ETag`, `Accept`(원하는 형식). 전송 방식은 `Transfer-Encoding: chunked`(길이를 모를 때 조각으로).

### 1.1 → 2 → 3

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 | TCP, 글자 | TCP, 이진 프레임 | UDP 위 QUIC |
| 한 연결에 | 요청 하나씩 순서대로(파이프라이닝은 사실상 미사용) | 여러 요청 동시(다중화, 스트림) | 여러 스트림, 스트림별 독립 |
| 막힘 | 앞 요청이 끝나야 다음 | TCP 손실 하나가 전 스트림을 막음 | 스트림별로만 막힘 |
| 그 밖에 | 브라우저가 도메인당 연결 6개로 우회 | 헤더 압축(HPACK), 서버 푸시(사실상 폐기) | 연결·TLS handshake 통합으로 왕복 감소 |

의미(메서드·상태 코드·헤더)는 셋이 같다. 바뀐 것은 전송 방식이다.

### 실무에서는

- REST API의 상태 코드를 성공에 전부 200으로 주면 클라이언트가 본문을 파싱해야만 실패를 안다. 의미에 맞게 201/204/400/404/409를 쓴다.
- 조회를 POST로 만들면 캐시·재시도·북마크가 안 된다. 조회는 GET, 단 URL 길이·민감 정보 문제가 있으면 POST로 하되 그 대가를 안다.
- 프록시·로드밸런서가 502/504를 낼 때 애플리케이션 로그에는 아무것도 없다 — 타임아웃 설정을 프록시와 서버 양쪽에서 본다.
- HTTP/2는 대부분 TLS와 함께 쓰이고 로드밸런서에서 종료돼 뒤 서버는 1.1을 받는 경우가 흔하다.

### 면접 질문

#### HTTP가 무상태라는 것은 무슨 뜻이고, 그럼 로그인 상태는 어떻게 유지하나요?

서버가 요청 사이에 클라이언트 정보를 기억하지 않아 각 요청이 독립적으로 처리된다는 뜻이며, 로그인 상태는 클라이언트가 매 요청에 식별자(세션 ID 쿠키나 JWT 토큰)를 실어 보내고 서버가 그것으로 알아보는 방식으로 유지합니다.
무상태 덕에 어느 서버가 받아도 같은 결과라 서버를 늘리기 쉽지만, "누구인가"는 요청마다 다시 증명해야 합니다.
예를 들어 세션 방식은 서버(또는 Redis)가 세션 ID → 사용자 정보를 저장하고, JWT는 정보를 서명해 토큰 자체에 넣어 서버 저장 없이 검증합니다. 각각의 장단은 쿠키·세션·JWT 장에서 다룹니다.

- 꼬리: 세션을 서버 메모리에 두면 서버를 여러 대로 늘릴 때 무슨 문제가 생기나요?
- 꼬리: GET과 POST의 차이를 "안전·멱등"으로 설명해 보세요.

#### HTTP/1.1과 HTTP/2의 차이는 무엇이고, 무엇이 빨라지나요?

HTTP/2는 한 TCP 연결 안에서 여러 요청·응답을 이진 프레임으로 섞어 보내는 다중화를 하고 헤더를 압축해, 1.1의 "한 연결에 한 요청씩 순서대로"라는 막힘을 없앱니다.
1.1에서는 앞 요청 응답이 끝나야 다음을 받을 수 있어 브라우저가 도메인당 연결을 6개씩 열어 우회했지만, 2에서는 연결 하나로 수십 개 리소스를 동시에 받습니다. 메서드·상태 코드·헤더 의미는 그대로입니다.
한계는 TCP 위라 패킷 하나가 손실되면 그 연결의 모든 스트림이 재전송을 기다린다는 점이고, HTTP/3가 UDP 기반 QUIC로 스트림을 독립시켜 이를 풀었습니다. API 서버 하나에 요청 하나만 보내는 경우엔 차이가 작습니다.
