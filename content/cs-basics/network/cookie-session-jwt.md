## 개념

HTTP는 요청마다 남남이다. 로그인한 사람을 다음 요청에서 알아보려면 **클라이언트가 매번 무언가를 들고 와야** 한다. 그 "무언가"를 들고 오는 수단이 **쿠키**다 — 서버가 `Set-Cookie`로 주면 브라우저가 같은 사이트에 요청할 때마다 `Cookie` 헤더로 되돌려 보낸다.

쿠키에 무엇을 담느냐가 두 갈래다. **세션** 방식은 무작위 ID만 담고, ID → 사용자 정보는 서버(메모리·Redis)가 기억한다. **JWT** 방식은 사용자 정보와 만료 시각을 토큰에 넣고 서버 비밀 키로 서명해, 서버가 저장하지 않고 서명만 검증한다.

로그인 뒤 "내 주문" 조회를 두 방식으로 따라가 보자.

- 세션: 로그인 성공 → 서버가 `sess:9f3a…` → `{userId: 7}`를 저장하고 `Set-Cookie: SID=9f3a…` → 다음 요청에 `Cookie: SID=9f3a…` → 서버가 저장소에서 찾아 userId 7 → 주문 조회. 로그아웃은 저장소에서 지우면 즉시 끝.
- JWT: 로그인 성공 → 서버가 `{userId: 7, exp: …}`를 서명해 토큰으로 줌 → 다음 요청에 `Authorization: Bearer <토큰>` → 서버가 서명과 만료만 확인 → userId 7. 저장소 조회 없음. 로그아웃해도 만료 전 토큰은 여전히 유효.
- 결과: 둘 다 사용자를 알아본다. 세션은 서버 저장소가 필요하지만 즉시 무효화가 되고, JWT는 저장소 없이 검증되지만 회수가 어렵다.

## 왜 나왔나

HTTP가 무상태라 "로그인 유지"가 안 됐다. 브라우저가 서버가 준 값을 자동으로 되돌려 보내는 쿠키가 먼저 생겼고, 거기에 사용자 정보를 그대로 넣으면 위조되니 서버가 기억하는 세션이 표준이 됐다. 서버가 여러 대가 되자 세션을 공유 저장소(Redis)로 옮겼고, 모바일 앱·여러 서비스가 한 사용자를 알아봐야 하자 서버 저장 없이 검증되는 서명 토큰(JWT)이 퍼졌다.

## 확인 질문

- 설명해 보기: 쿠키와 세션은 어떤 관계인가?
  답: 쿠키는 전달 수단, 세션은 저장 방식. 세션 ID를 쿠키에 담아 나른다. JWT도 쿠키에 담을 수 있다.
- 다음 상태 예측: 세션을 서버 메모리에 두고 서버를 2대로 늘리면?
  답: 1번 서버에서 로그인한 사용자가 2번으로 가면 세션이 없어 로그아웃된 것처럼 보인다. Redis 같은 공유 저장소로 옮겨야 한다.
- 다음 상태 예측: JWT를 발급한 뒤 사용자를 강제 로그아웃시키고 싶다. 서버가 할 수 있는 일은?
  답: 토큰 자체는 회수할 수 없다. 만료를 짧게 두거나, 차단 목록을 저장소에 두어 검증 때 확인해야 한다 — 그 순간 "저장소 없음"이라는 장점이 줄어든다.

## 심화

### 쿠키 속성

`HttpOnly`(자바스크립트가 못 읽음 — XSS로 훔치기 방지), `Secure`(HTTPS로만), `SameSite`(다른 사이트에서 시작된 요청에 안 보냄 — CSRF 완화, 기본 `Lax`), `Domain`/`Path`(어디로 보낼지), `Max-Age`/`Expires`(수명, 없으면 브라우저 닫을 때까지). 쿠키는 브라우저가 자동으로 보내므로 CSRF의 표적이 되고, 그래서 `SameSite`나 CSRF 토큰이 필요하다.

### JWT의 구조와 함정

`헤더.페이로드.서명`을 Base64로 이어 붙인 것이다. 페이로드는 **암호화가 아니라 인코딩**이라 누구나 읽는다 — 비밀번호나 민감 정보를 넣으면 안 된다. 서명은 위조를 막을 뿐이다. 서명 알고리즘은 대칭(HS256, 발급자와 검증자가 같은 비밀)과 비대칭(RS256, 발급자만 개인 키 — 여러 서비스가 공개 키로 검증)이 있다. `alg: none`을 받아 주는 구현 취약점이 유명하다.

### 만료와 갱신

JWT는 회수가 안 되므로 액세스 토큰은 짧게(분 단위), 리프레시 토큰으로 재발급한다. 리프레시 토큰은 결국 서버가 저장·검증하므로 "완전한 무상태"는 아니다. 세션도 만료를 두고, 활동 때마다 연장한다.

### 어디에 담나

브라우저 웹은 세션 ID나 JWT를 `HttpOnly` 쿠키에 담는 것이 XSS에 안전하다. `localStorage`에 JWT를 두면 스크립트가 읽을 수 있어 XSS 한 번에 털린다. 모바일 앱·서버 간 호출은 `Authorization: Bearer` 헤더가 자연스럽다.

### 실무에서는

- Spring Boot 서버 여러 대의 세션은 Spring Session + Redis로 공유한다. 로드밸런서의 sticky session은 임시방편이다.
- JWT 검증은 저장소 조회가 없어 빠르지만, 권한이 바뀌어도 토큰 만료 전엔 옛 권한이 남는다. 권한 변경이 잦은 관리 기능은 세션이나 짧은 만료가 맞다.
- 토큰을 로그에 남기지 않는다. 페이로드가 읽히고, 만료 전이면 그대로 쓸 수 있다.
- 쿠키 크기 4KB 한도가 있고 요청마다 붙으므로 JWT에 권한 목록을 잔뜩 넣으면 모든 요청이 무거워진다.

### 면접 질문

#### 세션과 JWT의 차이와 각각 언제 쓰나요?

세션은 서버(또는 공유 저장소)가 사용자 상태를 저장하고 클라이언트는 ID만 들고 다니며, JWT는 상태를 서명해 토큰에 담아 서버가 저장 없이 검증합니다.
세션은 서버가 즉시 무효화할 수 있고 토큰이 가볍지만 저장소 조회와 서버 간 공유가 필요하고, JWT는 저장소 없이 여러 서비스가 검증할 수 있지만 만료 전 회수가 안 되고 페이로드가 읽힙니다.
예를 들어 서버 몇 대의 일반 웹 서비스는 Redis 세션이 단순하고 안전하며, 여러 서비스·모바일 앱이 한 인증 서버의 토큰을 공유하는 구조에는 JWT(RS256 + 짧은 만료 + 리프레시)가 맞습니다. 한계는 JWT도 리프레시·차단 목록을 두는 순간 서버 저장이 다시 생긴다는 점입니다.

#### 쿠키에 `HttpOnly`와 `SameSite`를 두는 이유는?

`HttpOnly`는 자바스크립트가 쿠키를 못 읽게 해 XSS로 세션·토큰이 유출되는 것을 막고, `SameSite`는 다른 사이트에서 시작된 요청에 쿠키를 안 보내 CSRF를 완화합니다.
쿠키는 브라우저가 자동으로 붙이므로 스크립트가 읽을 수 있으면 훔쳐 갈 수 있고, 공격자 사이트가 우리 사이트로 요청을 보내면 로그인 쿠키가 따라붙어 사용자 모르게 동작이 실행됩니다.
`Set-Cookie: SID=…; HttpOnly; Secure; SameSite=Lax`가 기본형입니다. 한계는 `SameSite=Lax`가 최상위 GET 이동에는 쿠키를 보내므로 상태를 바꾸는 요청을 GET으로 만들면 여전히 뚫리고, 서드파티 임베드처럼 다른 사이트에서 쿠키가 필요하면 `None; Secure`로 열어야 한다는 점입니다.
