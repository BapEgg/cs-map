## 개념

브라우저가 서버에 "이 페이지 주세요"를 보내는 일은 한 프로그램이 다 하지 않는다. 일을 **층**으로 나눠 각 층이 한 가지만 맡고, 위층은 아래층을 부르되 아래층이 어떻게 하는지 모른다. 실무에서 쓰는 모델은 네 층이다. **링크 계층**(이더넷·Wi-Fi): 같은 케이블·같은 공유기에 붙은 **옆 장비**까지 프레임을 보낸다, 주소는 MAC. **인터넷 계층**(IP): 여러 망을 거쳐 **목적지 호스트**까지 패킷을 보낸다, 주소는 IP, 배달 보장은 없다. **전송 계층**(TCP·UDP): 그 호스트의 **어느 프로그램**에게인지(포트)와, 잃어버린 것을 다시 보낼지(신뢰성)를 맡는다. **응용 계층**(HTTP·DNS·SMTP): 내용의 형식과 뜻.

OSI 7계층은 같은 것을 더 잘게 나눈 교과서 모델이다(물리·데이터링크·네트워크·전송·세션·표현·응용). 면접에서 "7계층"을 물으면 이 이름을 대고, 실제 프로토콜은 4계층 모델에 대응시키면 된다 — 세션·표현은 대개 응용 안에 녹아 있다(TLS를 표현 계층에 두기도 한다).

**라우팅**은 인터넷 계층의 일이다. 라우터는 패킷의 목적지 IP를 보고 **라우팅 표**에서 "이 대역은 저 인터페이스로"를 찾아 다음 라우터(홉)에 넘긴다. 끝까지의 길을 아는 게 아니라 **다음 한 홉**만 안다. **NAT**는 집·회사의 사설 IP(192.168.x.x)를 공유기의 공인 IP 하나로 바꿔 내보내고, 돌아오는 응답을 포트 번호로 구분해 안의 장비에 되돌려 준다 — IPv4 주소가 모자라서 나온 장치다.

#### 작동 과정 — 집에서 `GET /` 하나가 나가는 길

- 응용: 브라우저가 HTTP 요청 텍스트를 만든다.
- 전송: TCP가 앞에 헤더(출발 포트 50123, 목적 포트 443, 순서 번호)를 붙인다 → 세그먼트.
- 인터넷: IP가 헤더(출발 192.168.0.10, 목적 93.184.216.34)를 붙인다 → 패킷. 목적지가 내 망 밖이므로 **기본 게이트웨이**(공유기)로 보내기로 한다.
- 링크: 이더넷이 헤더(출발 내 MAC, 목적 **공유기 MAC** — ARP로 알아냄)를 붙인다 → 프레임. 케이블로 나간다.
- 공유기(NAT): 프레임을 벗기고 IP를 본다. 출발 주소를 자기 공인 IP(203.0.113.5)로, 출발 포트를 임의 포트(40001)로 바꾸고, `(192.168.0.10:50123 ↔ 203.0.113.5:40001)`을 표에 적는다. 라우팅 표에서 다음 홉(ISP 라우터)을 찾아 새 프레임에 싸서 보낸다.
- 인터넷의 라우터들: 각자 목적지 IP 대역만 보고 다음 홉으로. 홉마다 프레임은 새로 싸이고 IP 헤더의 TTL은 1씩 준다.
- 서버: 프레임·IP·TCP 헤더를 차례로 벗겨 포트 443의 프로그램(웹 서버)에 데이터를 준다. 응답은 `203.0.113.5:40001`로.
- 결과: 응답이 공유기에 오면 표를 보고 `192.168.0.10:50123`으로 되돌린다. 서버는 내 사설 IP를 모른다. 밖에서 먼저 `192.168.0.10`에 접속할 방법도 없다 — 표에 없으니까.

#### 비교 — 층마다 무엇이 다른가

| 층 | 단위 | 주소 | 어디까지 | 대표 장비·프로토콜 |
|---|---|---|---|---|
| 응용 | 메시지 | URL·도메인 | 프로그램의 의미 | HTTP, DNS, SMTP |
| 전송 | 세그먼트 | 포트 | 호스트 안의 프로그램 | TCP, UDP |
| 인터넷 | 패킷 | IP | 망을 건너 호스트까지 | 라우터, IP, ICMP |
| 링크 | 프레임 | MAC | 옆 장비까지 | 스위치, 이더넷, Wi-Fi, ARP |

## 왜 나왔나

한 프로그램이 전선 신호부터 HTML까지 다 알면 케이블이 광섬유로 바뀔 때 브라우저를 고쳐야 한다. 층으로 나누면 각 층은 아래 층에 "이 데이터를 저 주소로"만 부탁하고, 층의 구현은 따로 바뀔 수 있다 — Wi-Fi가 생겨도 TCP·HTTP는 그대로였다. 라우팅이 "다음 홉만 안다"인 이유는 인터넷 전체 지도를 모든 라우터가 갖고 최신으로 유지하는 게 불가능해서다. NAT는 IPv4 주소 43억 개가 모자라자 "한 주소 뒤에 여러 장비"를 두려고 나왔고, 덕분에 IPv6 전환이 늦어졌다는 평도 받는다.

## 확인 질문

- 설명해 보기: IP와 포트는 각각 어느 층의 주소이고 무엇을 가리키나?
  답: IP는 인터넷 계층, 호스트(컴퓨터)를 가리킨다. 포트는 전송 계층, 그 호스트 안의 프로그램(소켓)을 가리킨다.
- 다음 상태 예측: 집 PC(192.168.0.10)에서 서버를 띄우고 친구에게 그 주소를 알려 주면?
  답: 접속 못 한다. 사설 IP는 내 망 안에서만 뜻이 있고, 공유기 NAT 표에 없는 바깥발 연결은 버려진다. 공유기에 포트 포워딩(공인 IP:8080 → 192.168.0.10:8080)을 걸어야 한다.
- 다음 상태 예측: 패킷이 라우터를 거칠 때 IP 주소와 MAC 주소는 각각 어떻게 되나?
  답: 출발·목적 IP는 (NAT를 빼면) 끝까지 그대로. MAC은 홉마다 바뀐다 — 링크 계층은 옆 장비까지만 책임지므로 프레임을 매번 새로 싼다.

## 심화

### 라우팅 표와 최장 접두 일치

라우팅 표의 항목은 `목적지 대역/프리픽스 → 다음 홉·인터페이스`다. `10.0.0.0/8`과 `10.1.0.0/16`이 둘 다 맞으면 **더 긴 프리픽스**(더 구체적인 쪽)를 고른다. 아무것도 안 맞으면 기본 경로(`0.0.0.0/0`, 기본 게이트웨이). 표는 정적으로 적거나 라우팅 프로토콜(망 안은 OSPF, 망 사이는 BGP)이 채운다. `traceroute`는 TTL을 1, 2, 3…으로 보내 홉마다 오는 ICMP 초과 응답으로 경로를 보여 준다.

### NAT의 종류와 부작용

가장 흔한 것은 포트까지 바꾸는 NAPT(PAT)다. 부작용: 안에서 먼저 연결해야 표가 생기므로 바깥발 연결(P2P, 게임 호스팅, 집 서버)이 안 되고 포트 포워딩이나 STUN·TURN 같은 우회가 필요하다. 표 항목은 시간이 지나면 지워지므로 오래 조용한 TCP 연결은 keep-alive를 보내야 끊기지 않는다. 클라우드의 NAT 게이트웨이도 같은 원리이고, 사설 서브넷의 서버가 외부 API를 부를 때 지나간다. IPv6는 주소가 충분해 원칙상 NAT가 필요 없다.

### 같은 망 안과 밖 — 서브넷 마스크

호스트는 목적지 IP를 자기 IP·서브넷 마스크와 비교해 같은 망이면 ARP로 상대 MAC을 알아내 직접 보내고, 다른 망이면 기본 게이트웨이의 MAC으로 보낸다. `192.168.0.10/24`에서 `192.168.0.20`은 직접, `8.8.8.8`은 게이트웨이. 클라우드 VPC의 서브넷·라우팅 표·보안 그룹은 이 개념을 그대로 소프트웨어로 만든 것이다.

### 캡슐화와 MTU

층마다 헤더가 붙어 이더넷 프레임 최대 1500바이트(MTU) 안에 IP 20 + TCP 20 + 데이터가 들어간다. 더 크면 IP가 조각내거나(단편화) TCP가 처음부터 MSS에 맞춰 자른다. VPN·터널은 헤더를 하나 더 얹어 MTU 문제를 만들기도 한다 — "작은 요청은 되는데 큰 파일 업로드만 안 된다"의 흔한 원인.

### 실무에서는

- 서버가 "요청이 안 온다"면 층 순서로 본다: 핑(ICMP, 인터넷 층) → 포트 열림(`nc`, 전송 층) → HTTP 응답(응용 층). 어느 층에서 막히는지가 곧 원인 위치다.
- 클라우드 서버의 사설 IP·공인 IP·탄력 IP는 NAT 관계다. 인스턴스 안에서 `ifconfig`에 공인 IP가 안 보이는 게 정상.
- 로드밸런서 뒤 서버가 보는 출발 IP는 LB의 사설 IP다. 실제 클라이언트 IP는 `X-Forwarded-For`(프록시 장).
- 보안 그룹·방화벽 규칙은 "어느 층의 무엇"으로 적는다 — 프로토콜(TCP) + 포트(443) + 출발 대역(IP).

### 면접 질문

#### OSI 7계층(또는 TCP/IP 4계층)을 설명하고, 각 층의 대표 프로토콜을 말해 주세요.

TCP/IP 4계층으로 말하면 링크(옆 장비까지 프레임, MAC, 이더넷·Wi-Fi·ARP), 인터넷(망을 건너 호스트까지 패킷, IP, 라우터·ICMP), 전송(호스트 안의 프로그램까지·신뢰성, 포트, TCP·UDP), 응용(내용의 형식, HTTP·DNS·SMTP)입니다. OSI 7계층은 여기에 물리를 링크에서 떼고 세션·표현을 응용에서 뗀 것으로, 실제 프로토콜은 대개 4계층에 대응됩니다.
층으로 나눈 이유는 각 층이 아래 층의 구현을 몰라도 되게 해서 케이블이 Wi-Fi로 바뀌어도 HTTP는 그대로이게 하기 위해서입니다.
예를 들어 HTTP 요청은 TCP 헤더(포트) → IP 헤더(주소) → 이더넷 헤더(MAC) 순으로 싸여 나가고, 라우터는 IP만 보고 다음 홉으로 넘기며 MAC은 홉마다 바뀝니다. 한계는 실제 프로토콜이 층 경계에 딱 맞지 않아(TLS, QUIC) 모델은 사고의 틀이지 구현 명세가 아니라는 점입니다.

- 오답: "라우터는 MAC 주소로 목적지를 찾는다" — MAC은 링크 층(옆 장비)까지, 라우터는 IP로 다음 홉을 고른다.

#### 집 PC의 IP가 192.168.0.10인데 서버에는 다른 주소로 보입니다. 왜 그렇고, 집 서버를 밖에서 접속하려면?

192.168.x.x는 RFC 1918 사설 주소라 집 안에서만 유효하고, 공유기의 NAT가 나가는 패킷의 출발 주소·포트를 공인 IP와 임의 포트로 바꿔 표에 기록한 뒤 보내므로 서버는 공유기의 공인 IP를 봅니다. 응답은 그 표로 안의 PC에 되돌려집니다.
IPv4 주소가 부족해 한 공인 주소 뒤에 여러 장비를 두려고 만든 장치이고, 안에서 먼저 나간 연결만 표에 생기는 것이 원리입니다.
밖에서 집 서버에 접속하려면 표가 없으므로 공유기에 포트 포워딩(공인 IP:포트 → 192.168.0.10:포트)을 걸거나, DDNS로 바뀌는 공인 IP에 이름을 붙이거나, 터널(ngrok, Cloudflare Tunnel)로 안에서 먼저 연결을 열어 둡니다. 한계는 ISP가 공유기 앞에 또 NAT를 두면(CGNAT) 포트 포워딩도 안 되고, 집 서버를 열면 보안 책임도 함께 열린다는 점입니다.

- 오답: "공유기가 IP를 숨겨 주니 보안 장치다" — 부수 효과일 뿐 방화벽이 아니다. 포트 포워딩을 열면 그대로 노출된다.
- 꼬리: 클라우드 인스턴스의 사설 IP와 공인 IP는 어떤 관계인가요?
