## 개념

인터넷에서 상대를 찾으려면 세 가지가 필요하다. **IP 주소**는 컴퓨터(정확히는 네트워크 인터페이스) 하나를 가리키는 번호다(`142.250.196.110`처럼 IPv4는 32비트, IPv6는 128비트). **포트**는 그 컴퓨터 안에서 어느 프로그램에게 줄지 정하는 0~65535 번호다 — 웹 서버는 보통 443(HTTPS)·80(HTTP), MySQL은 3306. **DNS**는 `google.com` 같은 이름을 IP로 바꿔 주는 분산 전화번호부다.

브라우저에 `https://example.com/login`을 치면 이 셋이 차례로 쓰인다.

- 시작: 브라우저는 `example.com`이 어디인지 모른다.
- DNS: 운영체제 캐시 → 공유기/통신사 리졸버 → (없으면) 루트 → `.com` → `example.com`의 네임서버 순으로 물어 `93.184.216.34`를 받는다. 답에는 TTL(예: 300초)이 붙어 그동안 다시 안 묻는다.
- IP·포트: 브라우저가 `93.184.216.34`의 443번 포트로 연결한다. 그 서버에서 443을 열고 듣고 있는 프로세스(Nginx 등)가 받는다.
- 결과: 이름 하나가 "어느 컴퓨터의 어느 프로그램"으로 바뀌었다. 서버를 다른 IP로 옮겨도 DNS 기록만 바꾸면 사용자는 같은 이름을 쓴다.

## 왜 나왔나

컴퓨터끼리 통하려면 서로를 가리킬 번호가 필요했고(IP), 한 컴퓨터에서 여러 프로그램이 동시에 통신하니 프로그램을 구분할 번호도 필요했다(포트). 그런데 사람은 숫자를 못 외우고 서버는 IP가 바뀌므로, 이름을 따로 두고 이름 → IP 변환을 전 세계가 나눠 맡는 체계(DNS)를 만들었다.

## 확인 질문

- 설명해 보기: IP와 포트를 "건물"로 비유하면 각각 무엇인가?
  답: IP는 건물 주소, 포트는 호실. 같은 건물(컴퓨터)의 다른 호실(프로그램)로 간다.
- 다음 상태 예측: 서버 한 대에서 웹 서버와 DB를 같이 돌리면 클라이언트는 어떻게 구분해 접속하나?
  답: 같은 IP에 다른 포트(443과 3306). 포트가 프로그램을 가른다.
- 다음 상태 예측: DNS 기록의 TTL이 3600초인데 서버 IP를 바꿨다. 사용자는 언제 새 IP로 가나?
  답: 각자의 캐시가 만료되는 최대 1시간 뒤. 이사 전에 TTL을 미리 줄여 두는 이유다.

## 심화

### IP 주소의 구조

IPv4는 32비트라 약 43억 개뿐이어서 고갈됐고, 사설 IP(`192.168.x.x`, `10.x.x.x`)와 NAT(공유기가 여러 기기를 하나의 공인 IP 뒤에 둠)로 버텨 왔다. IPv6는 128비트다. 클라우드 서버는 보통 사설 IP를 갖고 로드밸런서나 NAT 게이트웨이가 공인 IP를 가진다. 서버 코드에서 보는 클라이언트 IP가 프록시의 IP인 이유가 여기 있다(`X-Forwarded-For`).

### 포트

0~1023은 잘 알려진 포트(80, 443, 22, 53)로 리눅스에서는 root만 열 수 있다. 서버가 포트를 "듣는다"(listen)는 것은 그 번호로 오는 연결을 받겠다는 뜻이고, 한 포트는 한 프로세스만 들을 수 있다(`Address already in use`). 클라이언트 쪽 포트는 운영체제가 임시로 하나 골라 준다(임시 포트, 보통 32768~60999). 연결 하나는 (출발 IP, 출발 포트, 도착 IP, 도착 포트)로 구별된다.

### DNS 조회

로컬 캐시 → 스텁 리졸버(운영체제) → 재귀 리졸버(통신사·8.8.8.8) → 루트 → TLD(`.com`) → 권한 네임서버 순이다. 재귀 리졸버가 TTL 동안 캐시하므로 대부분은 첫 단계에서 끝난다. 레코드 종류: A(IPv4), AAAA(IPv6), CNAME(별명), MX(메일), TXT. 로드밸런서 뒤로 보내는 것은 보통 CNAME이나 A 여러 개(DNS 라운드 로빈).

### 실무에서는

- 배포 전 DNS TTL을 60초로 줄여 두면 IP 전환이 빨라진다. 전환 뒤 다시 올린다.
- JVM은 DNS 결과를 자체 캐시한다(`networkaddress.cache.ttl`, 보안 관리자 없으면 기본 30초). 무한 캐시 설정이면 서버 이전 뒤에도 옛 IP를 붙든다.
- 로드밸런서 뒤 서버는 `X-Forwarded-For`로 원래 클라이언트 IP를 받는다. 프록시가 여럿이면 맨 앞이 클라이언트다. 신뢰 안 되는 값이니 IP 기반 제한에 그대로 쓰지 않는다.
- 컨테이너·쿠버네티스에서 서비스 이름이 곧 DNS 이름이다(`db:3306`). 내부 DNS가 이름을 파드 IP로 바꾼다.
- `Connection refused`는 IP는 맞는데 그 포트를 듣는 프로세스가 없다는 뜻, 타임아웃은 IP까지 도달을 못 하거나 방화벽이 버린다는 뜻이다.

### 면접 질문

#### 브라우저에 주소를 입력하면 서버를 어떻게 찾나요?

DNS로 이름을 IP로 바꾸고, 그 IP의 정해진 포트(HTTPS면 443)로 연결합니다.
운영체제·리졸버 캐시에 있으면 바로 쓰고, 없으면 재귀 리졸버가 루트 → TLD → 권한 네임서버 순으로 물어 IP를 받아 TTL 동안 캐시합니다. IP는 컴퓨터를, 포트는 그 안의 프로그램을 가리키므로 둘이 있어야 요청이 웹 서버 프로세스에 닿습니다.
예를 들어 `example.com`이 `93.184.216.34`로 풀리면 그 주소의 443번을 듣는 Nginx가 받습니다. 한계는 DNS 캐시 때문에 IP를 바꿔도 TTL만큼 옛 주소로 가는 사용자가 남는다는 점이라, 이전 전에 TTL을 줄여 둡니다.

- 꼬리: 같은 IP·같은 포트로 연결이 수천 개 들어와도 서버가 구분하는 방법은?

#### 서버 코드에서 `request.getRemoteAddr()`가 늘 같은 IP로 나옵니다. 왜일까요?

앞에 로드밸런서나 리버스 프록시가 있어서, 서버가 보는 연결의 상대가 클라이언트가 아니라 프록시이기 때문입니다.
프록시가 클라이언트 연결을 받고 서버로 새 연결을 맺으므로 TCP 상의 출발 IP는 프록시의 사설 IP입니다. 원래 클라이언트 IP는 프록시가 `X-Forwarded-For` 헤더에 붙여 보냅니다.
Spring Boot는 `server.forward-headers-strategy`를 설정하면 그 헤더를 읽어 `getRemoteAddr()`에 반영합니다. 한계는 이 헤더를 클라이언트가 위조할 수 있으므로, 신뢰하는 프록시가 덮어쓰거나 앞에서부터 몇 단계까지만 믿도록 설정해야 한다는 점입니다.
