## 개념

찾는 방법은 데이터 상태에 따라 갈린다. 정렬이 안 돼 있으면 처음부터 하나씩 비교하는 수밖에 없다 — **선형 탐색**, O(n). 정렬돼 있으면 가운데를 보고 찾는 값이 작은지 큰지에 따라 한쪽 절반을 버린다 — **이진 탐색**, 비교 한 번에 후보가 절반이 되어 O(log n). 100만 개도 20번이면 찾는다.

이진 탐색은 "정렬돼 있다"는 전제 위에 선다. 그래서 탐색을 빠르게 하려면 미리 정렬해 두거나(정렬 비용을 한 번 치름), 정렬을 유지하는 구조(트리·B-tree 인덱스)에 넣거나, 아예 순서 없이 자리를 계산하는 해시를 쓴다.

정렬된 `[3, 8, 15, 21, 27, 34, 40]`에서 27을 찾아 보자.

- 1회: 범위 0~6, 가운데 3번(21). 27 > 21 → 오른쪽 4~6만 남긴다.
- 2회: 범위 4~6, 가운데 5번(34). 27 < 34 → 왼쪽 4~4.
- 3회: 4번(27). 찾았다. 7개에서 3번 비교, 선형이면 최대 7번.
- 결과: 없는 값(예: 30)이면 범위가 비는 순간 "없음"으로 끝난다. 정렬이 안 된 배열에 같은 절차를 쓰면 엉뚱한 답이 나온다.

## 왜 나왔나

데이터가 커지자 매번 처음부터 훑는 비용이 문제였다. 정렬된 순서를 이용하면 절반씩 버릴 수 있다는 것이 이진 탐색이고, 이 발상은 탐색 트리와 DB 인덱스로 이어졌다. "이진 탐색은 아이디어는 쉽지만 경계 처리에서 틀리기 쉽다"는 것이 오래된 교훈이다(중간 인덱스 오버플로, 범위 갱신 실수).

## 확인 질문

- 설명해 보기: 이진 탐색이 O(log n)인 이유는?
  답: 비교 한 번마다 남은 후보가 절반이 되므로, n개를 1개로 줄이는 데 log₂n번이면 된다.
- 다음 상태 예측: 정렬 안 된 배열에 이진 탐색을 하면?
  답: 가운데 값으로 방향을 정할 수 없어 있는 값도 못 찾을 수 있다. 결과를 믿을 수 없다.
- 다음 상태 예측: 정렬된 10억 개에서 이진 탐색은 최대 몇 번 비교하나?
  답: 약 30번(2³⁰ ≈ 10억).

## 심화

### 경계 처리

`mid = (low + high) / 2`는 `low + high`가 int 범위를 넘으면 오버플로한다 — `low + (high − low) / 2`로 쓴다(JDK의 `Arrays.binarySearch`에도 있던 버그). "값이 없을 때 들어갈 자리"(lower bound)를 돌려주게 짜면 삽입 위치·범위 개수 세기에 쓸 수 있다. Java `binarySearch`는 없으면 `-(삽입 위치) − 1`을 돌려준다.

### 어디서 이진 탐색이 사는가

정렬된 배열(`Arrays.binarySearch`), 탐색 트리(`TreeMap`은 트리 위에서 같은 절차), DB B-tree 인덱스(노드 안에서 이진 탐색으로 자식 선택), 버전 관리의 `git bisect`(문제가 생긴 커밋을 절반씩 좁힘), "조건을 만족하는 최소값 찾기"류 문제(답의 범위를 이진 탐색).

### 해시와의 선택

한 개를 정확히 찾기만 하면 해시(O(1))가 이긴다. 범위·순서·"가장 가까운 값"이 필요하면 이진 탐색·트리다. 데이터가 바뀌지 않고 메모리에 있으면 정렬 배열 + 이진 탐색이 트리보다 메모리·캐시 면에서 유리하다.

### 실무에서는

- `List.contains`·`indexOf`는 선형 탐색이다. 반복문 안에서 부르면 O(n²) — `HashSet`이나 정렬 + 이진 탐색으로.
- DB `WHERE id = ?`가 빠른 것은 B-tree 인덱스 안의 이진 탐색 덕분이고, 인덱스 없는 컬럼은 선형 탐색(풀 스캔)이다.
- 설정 값처럼 자주 읽고 거의 안 바뀌는 정렬 목록은 배열 + `binarySearch`가 `TreeMap`보다 가볍다.
- `git bisect`로 회귀 커밋 찾기: 커밋 1,000개도 10번이면 좁힌다.

### 면접 질문

#### 이진 탐색의 전제와 복잡도, 그리고 주의할 점은?

전제는 데이터가 정렬돼 있어야 한다는 것이고, 복잡도는 O(log n)이며, 주의점은 중간 인덱스 계산의 오버플로와 범위 갱신·종료 조건입니다.
비교마다 후보가 절반이 되므로 100만 개도 20번이면 되지만, 정렬이 안 돼 있으면 방향을 정할 근거가 없어 결과를 믿을 수 없습니다.
`mid = (low + high) / 2`는 큰 배열에서 오버플로하므로 `low + (high − low) / 2`로 쓰고, `high = mid − 1`/`low = mid + 1` 갱신과 `low <= high` 종료 조건을 맞춰야 무한 루프나 한 칸 오차가 없습니다. 한계는 정렬 비용 O(n log n)을 먼저 치러야 하므로 한 번만 찾을 거면 선형 탐색이 싸다는 점입니다.

- 꼬리: 값이 없을 때 이진 탐색이 돌려주는 "삽입 위치"는 어디에 쓰나요?
- 꼬리: 연결 리스트에서 이진 탐색이 의미 없는 이유는?

#### 데이터 100만 건에서 조회가 느립니다. 탐색 관점에서 어떤 선택지가 있나요?

조회 패턴에 따라 셋 중 하나입니다 — 키 하나로 정확히 찾으면 해시(O(1)), 범위·정렬·근접 값이면 정렬 유지 구조에서 이진 탐색(O(log n)), 둘 다 아니고 한 번뿐이면 그냥 선형 탐색(O(n))입니다.
해시는 순서를 잃고, 이진 탐색은 정렬 유지 비용이 들며, 선형은 매번 전부 훑기 때문에 "얼마나 자주, 어떤 조건으로 찾는가"가 선택을 정합니다.
예를 들어 DB라면 `=` 조회에 인덱스(B-tree)를 걸면 풀 스캔 O(n)이 O(log n)이 되고, 애플리케이션 메모리라면 `List.contains`를 `HashSet.contains`로 바꾸는 것만으로 끝나는 경우가 많습니다.

- 꼬리: 인덱스가 있어도 이진 탐색을 못 타는 쿼리는?
- 꼬리: 정렬 배열과 `TreeMap` 중 메모리·속도 면에서 어느 쪽이 유리한가요?
