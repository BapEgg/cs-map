## 개념

정렬은 데이터를 크기순으로 늘어놓는 것이다. 방법이 여럿인 이유는 **속도·메모리·안정성·최악 경우**가 서로 다르기 때문이다. 이중 반복문으로 하나씩 제자리를 찾는 방법(삽입·선택·버블)은 O(n²)라 작을 때만 쓰고, 반으로 나눠 정복하는 방법(병합·퀵·힙)은 O(n log n)이다. 비교로만 정렬하는 한 O(n log n)보다 빠를 수는 없다.

**안정 정렬**은 같은 값의 원래 순서를 지킨다. "이름순으로 정렬한 뒤 학년순으로 정렬하면 같은 학년 안에서 이름순이 유지된다"가 안정 정렬에서만 보장된다.

`[5, 2, 8, 1]`을 병합 정렬로 정렬해 보자.

- 나누기: `[5, 2]`, `[8, 1]` → `[5]`, `[2]`, `[8]`, `[1]`. 하나짜리는 정렬된 것이다.
- 합치기: `[5]`+`[2]` → 앞을 비교하며 `[2, 5]`. `[8]`+`[1]` → `[1, 8]`. `[2, 5]`+`[1, 8]` → 1, 2, 5, 8.
- 결과: `[1, 2, 5, 8]`. 나누는 단계가 log n, 각 단계에서 합치기가 n → O(n log n). 합칠 때 같은 값이면 왼쪽을 먼저 놓으므로 안정적이다.

## 왜 나왔나

정렬은 그 자체가 목적이라기보다 다른 일의 전제다 — 이진 탐색, 중복 제거, 순위, 상위 N개, 두 목록 맞추기(조인)가 모두 정렬을 깔고 있다. 데이터가 커지면서 O(n²)로는 감당이 안 되자 분할 정복 정렬이 나왔고, 실제 데이터가 "거의 정렬돼 있는" 경우가 많다는 관찰에서 그런 데이터에 O(n)에 가깝게 동작하는 TimSort가 나왔다.

## 확인 질문

- 설명해 보기: 안정 정렬이란 무엇이고 언제 중요한가?
  답: 같은 값의 원래 순서를 지키는 정렬. 이미 다른 기준으로 정렬된 것을 두 번째 기준으로 다시 정렬할 때 첫 기준이 유지된다.
- 다음 상태 예측: 10개 정렬에 이중 반복문(O(n²))이 100번 비교라면 1만 개는?
  답: 약 1억 번. n이 1,000배면 비교는 100만 배.
- 다음 상태 예측: 이미 정렬된 100만 개에 TimSort를 돌리면?
  답: 정렬돼 있음을 감지해 거의 O(n)에 끝난다. 퀵 정렬은 여전히 O(n log n)이다.

## 심화

### 대표 정렬 비교

| 정렬 | 평균 | 최악 | 추가 메모리 | 안정 | 특징 |
|---|---|---|---|---|---|
| 삽입 | O(n²) | O(n²) | O(1) | 예 | 작거나 거의 정렬된 데이터에 빠름 |
| 병합 | O(n log n) | O(n log n) | O(n) | 예 | 최악이 없고 안정. 외부 정렬·연결 리스트에 맞음 |
| 퀵 | O(n log n) | O(n²) | O(log n) | 아니오 | 캐시 친화적, 실전에서 가장 빠른 편. 피벗이 나쁘면 최악 |
| 힙 | O(n log n) | O(n log n) | O(1) | 아니오 | 최악 보장 + 메모리 최소, 대신 캐시 비친화 |
| TimSort | O(n log n) | O(n log n) | O(n) | 예 | 병합 + 삽입. 이미 정렬된 구간(run)을 활용 |

### 언어 라이브러리는 무엇을 고르나

Java `Arrays.sort(int[])`는 듀얼 피벗 퀵 정렬(기본형은 안정성이 의미 없음), `Arrays.sort(Object[])`와 `Collections.sort`는 TimSort(안정, 객체 정렬은 안정성이 중요). 파이썬 `sorted`도 TimSort. 즉 실무에서 정렬을 직접 짤 일은 거의 없고, "객체 정렬은 안정적이다"와 "거의 정렬된 입력에 빠르다"를 아는 것이 쓸모다.

### 비교하지 않는 정렬

키가 정수 범위로 제한되면 계수 정렬·기수 정렬이 O(n)에 정렬한다. 나이(0~150)·우편번호·고정 길이 문자열 같은 경우다. 비교 정렬의 O(n log n) 하한은 "비교만으로"라는 조건이 붙는다.

### 실무에서는

- DB `ORDER BY`는 인덱스 순서를 그대로 읽으면 정렬을 안 하고, 못 타면 filesort(메모리·디스크 정렬)를 한다. 인덱스 `(a, b)`가 있으면 `ORDER BY a, b`는 인덱스 순서대로 읽어 정렬 단계가 없고, `ORDER BY b`는 정렬이 든다.
- 페이지네이션의 `ORDER BY created_at LIMIT 10 OFFSET 100000`은 앞 10만 건도 정렬·건너뛰어야 느리다. 마지막 값 기준(keyset)으로 바꾼다.
- 상위 N개는 전체 정렬 대신 크기 N 힙(힙 장).
- `Comparator`가 일관되지 않으면(a<b, b<c인데 c<a) `IllegalArgumentException: Comparison method violates its general contract`가 TimSort에서 난다.

### 면접 질문

#### 퀵 정렬과 병합 정렬의 차이와 각각 언제 쓰나요?

퀵 정렬은 피벗으로 갈라 제자리에서 정렬해 평균이 빠르고 메모리를 거의 안 쓰지만 최악 O(n²)에 불안정하고, 병합 정렬은 반으로 나눠 합치므로 항상 O(n log n)에 안정적이지만 O(n) 추가 메모리가 듭니다.
메모리에 다 올라가는 기본형 배열은 퀵(캐시 친화, 실전 최속), 객체 정렬처럼 안정성이 필요하거나 최악을 보장해야 하거나 연결 리스트·외부 파일을 정렬하면 병합 계열입니다.
Java가 `int[]`에 듀얼 피벗 퀵 정렬을, `Object[]`에 TimSort(병합 계열)를 쓰는 것이 그 선택입니다. 퀵의 최악은 피벗을 무작위·중앙값으로 골라 피하고, 그래도 걱정되면 힙 정렬로 넘기는 인트로 정렬을 씁니다.

#### 100만 건을 `ORDER BY` 하는 쿼리가 느립니다. 어떻게 접근하나요?

먼저 실행 계획에서 `Using filesort`가 뜨는지 보고, 정렬 컬럼에 인덱스를 두어 인덱스 순서로 읽게 만듭니다.
DB는 인덱스 순서와 `ORDER BY`가 맞으면 정렬 없이 순서대로 읽지만, 아니면 결과 전체를 메모리·디스크에서 정렬해야 하고 그 비용이 O(n log n)에 I/O까지 듭니다.
예를 들어 `WHERE status = ? ORDER BY created_at`이면 `(status, created_at)` 복합 인덱스로 필터와 정렬을 한 번에 탑니다. `LIMIT 10 OFFSET 100000`처럼 깊은 페이지는 정렬 뒤 건너뛰기라 느리므로 마지막 본 값 기준(`WHERE created_at < ? LIMIT 10`)으로 바꿉니다. 한계는 인덱스가 늘수록 쓰기가 느려지므로 정렬 패턴을 한두 개로 좁혀야 한다는 점입니다.
