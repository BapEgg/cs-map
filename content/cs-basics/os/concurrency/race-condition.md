## 개념

경쟁 상태는 **둘 이상의 흐름이 같은 데이터를 동시에 읽고 쓸 때, 누가 먼저 끼어드느냐에 따라 결과가 달라지는** 문제다.
코드 한 줄이 실제로는 "읽고 → 고치고 → 쓰기" 여러 명령으로 실행되는데, 그 사이에 다른 흐름이 끼어들면 서로의 변경을 덮어쓴다.
실행할 때마다 결과가 다를 수 있어서 테스트에서는 잘 통과하고 운영에서 가끔 터진다.

예를 들어 `count`가 50일 때 스레드 1과 2가 각각 `count++`를 한 번씩 한다. 기대 결과는 52다.
스레드 1이 50을 읽어 51을 만든 순간 문맥 교환이 일어난다. 스레드 2가 아직 50인 `count`를 읽어 51을 만들어 저장한다. 다시 스레드 1로 돌아와 아까 만든 51을 저장한다.
두 번 올렸는데 결과는 51이다. 스레드 2의 증가가 사라졌고, 끼어드는 타이밍이 조금만 달랐다면 52가 나왔을 것이다.

비유하면 두 사람이 같은 통장 잔액을 각자 종이에 적어 계산한 뒤, 나중에 적은 쪽 값만 통장에 남는 것이다.
비유가 안 통하는 데는, 사람은 "아까 적었는데 바뀌었네"를 알아챌 수 있지만 스레드는 **끼어들기가 있었다는 사실 자체를 모른다**는 점이다. 그래서 코드로는 절대 못 알아채고, 막는 수밖에 없다.

## 왜 나왔나

스레드는 메모리를 공유해서 값을 주고받기 편했다. 그런데 CPU는 `count++` 같은 한 줄을 여러 명령으로 나눠 실행하고, 운영체제는 **어느 명령 사이에서든** 스레드를 바꿀 수 있다.
그래서 두 스레드의 "읽고-고치고-쓰기"가 서로 엇갈리는 순간이 생겼고, 그 결과가 실행 순서에 따라 달라졌다.
결국 공유 데이터를 고치는 구간을 찾아내(임계 구역) 한 번에 하나만 들어가게 하는 동기화가 필요해졌다.

## 심화

### 내부 구조

- `count++`는 x86에서 `mov`(메모리→레지스터), `add`(레지스터 +1), `mov`(레지스터→메모리) 세 명령이다. 각 스레드는 **자기 레지스터**에 값을 올려 계산하므로, 사이에 문맥 교환이 끼면 상대의 저장을 못 보고 덮어쓴다(OSTEP 26장 Figure 26.7의 흐름). 멀티코어에서는 문맥 교환 없이도 두 코어가 같은 순간에 읽으면 같은 일이 생긴다.
- 조건: (1) 공유 데이터가 있고 (2) 적어도 하나가 **쓰기**이며 (3) 순서를 강제하는 장치가 없다. 셋 중 하나만 없애도 사라진다 — 공유하지 않거나(스레드별 복사, 불변 객체), 읽기만 하거나, 동기화하거나.
- 읽기-확인-쓰기(check-then-act)도 같은 문제다. "재고가 1 이상이면 1 빼기"를 두 스레드가 동시에 하면 둘 다 "1 이상"을 확인하고 둘 다 빼서 −1이 된다. 확인과 행동 사이에 끼어들 수 있다.
- 막는 방법 세 갈래: 락(뮤텍스)으로 구간을 잠그기, 하드웨어 원자적 연산(compare-and-swap)으로 읽고-고치고-쓰기를 한 명령으로 만들기(Java `AtomicInteger.incrementAndGet()`), 아예 공유하지 않기(스레드별 상태, 불변 객체, 메시지 전달).
- 자주 하는 오해: "`volatile`을 붙이면 된다". `volatile`은 다른 스레드가 쓴 값이 **보이게**(가시성) 할 뿐, 읽고-고치고-쓰기를 하나로 묶지 않는다. `volatile int count; count++`는 여전히 경쟁 상태다.
- 재현이 어렵다: 끼어드는 타이밍이 드물어 단위 테스트는 통과하고, 부하가 걸린 운영에서 확률적으로 터진다. 재현하려면 스레드 수천 개로 반복하거나 `Thread.sleep`을 끼워 타이밍을 벌린다.

### 실제 활용

- 주문 수량 차감: `SELECT stock … ; if (stock > 0) UPDATE stock = stock - 1` 두 단계로 짜면 동시 주문 때 재고가 음수가 된다. DB에서 `UPDATE … SET stock = stock - 1 WHERE stock > 0`처럼 한 문장으로 만들거나, `SELECT … FOR UPDATE`로 행을 잠근다.
- 좋아요 수 집계: 여러 요청 스레드가 같은 카운터를 올리면 누락된다. `AtomicLong`이나 Redis `INCR`(단일 스레드라 원자적)을 쓴다.
- `HashMap`을 여러 스레드가 동시에 `put` 하면 값이 사라지거나(경쟁 상태) 옛 버전에서는 무한 루프까지 났다. 공유하려면 `ConcurrentHashMap`을 쓴다.
- 싱글턴을 `if (instance == null) instance = new …`로 만들면 두 스레드가 동시에 null을 보고 둘 다 만든다(check-then-act). 정적 초기화나 holder 패턴으로 JVM이 한 번만 만들게 한다.

### 면접 질문

#### 경쟁 상태란 무엇이고, 왜 발생하나요?

여러 흐름이 같은 데이터를 동시에 접근하고 그중 하나라도 쓰기일 때, 실행 순서에 따라 결과가 달라지는 문제입니다.
`count++` 같은 한 줄이 실제로는 읽기·계산·쓰기 여러 명령으로 실행되고, 운영체제가 그 사이 어디서든 스레드를 바꿀 수 있어 두 스레드의 읽기-쓰기가 엇갈리기 때문입니다.
예를 들어 50인 카운터를 두 스레드가 각각 올리면, 둘 다 50을 읽은 뒤 각자 51을 저장해 결과가 52가 아닌 51이 됩니다. 막으려면 그 구간을 락으로 잠그거나 원자적 연산을 쓰거나 아예 공유하지 않아야 합니다.

- 꼬리: 읽기만 하는 스레드가 여럿이면 경쟁 상태인가요?
- 꼬리: 멀티코어에서는 문맥 교환이 없어도 경쟁 상태가 생기나요?

#### `volatile`로 경쟁 상태를 막을 수 있나요?

없습니다. `volatile`은 한 스레드가 쓴 값이 다른 스레드에 즉시 보이게 하는 가시성만 보장하고, 읽고-고치고-쓰기를 하나의 원자적 동작으로 묶지 않기 때문입니다.
`volatile int count`에 두 스레드가 `count++`를 하면 여전히 둘 다 같은 값을 읽고 같은 값을 쓸 수 있습니다.
가시성만 필요한 상태 플래그(`running = false`)에는 `volatile`이 맞고, 증가·누적처럼 이전 값에 의존하는 갱신에는 `AtomicInteger`나 `synchronized`가 필요합니다.

- 꼬리: `AtomicInteger.incrementAndGet()`은 내부적으로 어떻게 원자성을 얻나요?
- 꼬리: `synchronized`와 `AtomicInteger` 중 어느 쪽이 빠른가요, 언제 갈리나요?

#### 재고 1개인 상품에 동시에 주문 두 건이 들어와 재고가 −1이 됐습니다. 원인과 해결책은?

"재고를 읽어 확인하고, 있으면 뺀다"를 두 단계로 실행해서 생긴 check-then-act 경쟁 상태입니다. 두 요청이 동시에 재고 1을 읽고 둘 다 조건을 통과해 둘 다 뺐습니다.
확인과 차감 사이에 다른 요청이 끼어들 수 있기 때문이며, 애플리케이션 서버가 여러 대면 JVM 안의 락으로는 막을 수 없습니다.
해결은 확인과 차감을 한 번에 하는 것입니다 — `UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty > 0`로 만들고 영향받은 행 수가 0이면 품절 처리하거나, `SELECT … FOR UPDATE`로 행을 잠근 뒤 차감하거나, 버전 컬럼으로 낙관적 락을 겁니다. 한계는 인기 상품 한 행에 주문이 몰리면 그 행의 락 대기가 병목이 된다는 점이라, 이때는 재고를 Redis로 빼거나 큐로 직렬화합니다.

- 꼬리: 비관적 락과 낙관적 락은 각각 언제 유리한가요?
- 꼬리: 서버가 여러 대일 때 JVM `synchronized`로 막을 수 없는 이유는?
