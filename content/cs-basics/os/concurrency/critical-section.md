## 개념

경쟁 상태가 "무슨 문제가 생기나"라면, 임계 구역은 "코드의 **어디**를 지켜야 하나"를 가리키는 말이다. 공유 데이터를 읽고 고치는 코드 구간 중, 둘 이상이 동시에 실행하면 결과가 깨지는 부분이 임계 구역이다.

지키는 방법은 한 번에 하나만 들어가게 하는 것(상호 배제)이다. 구간이 짧을수록 다른 스레드가 기다리는 시간이 줄고, 구간을 잘못 잡으면 여전히 깨지거나 필요 없이 느려진다.

계좌 이체 함수를 보자.

- 시작: `from.balance = 100`, `to.balance = 0`. 두 스레드가 같은 계좌 쌍에 각각 30원, 50원을 이체하려 한다.
- 진행: 함수 안에서 `from.balance -= amount; to.balance += amount;` 두 줄이 잔액을 읽고 고친다. 이 두 줄이 임계 구역이다. 로그 남기기, 알림 보내기는 공유 데이터를 안 건드리니 구역 밖이다.
- 결과: 두 줄만 한 번에 하나씩 실행되게 하면 `from = 20`, `to = 80`으로 맞다. 두 줄을 겹쳐 실행하면 한쪽 이체가 사라질 수 있다.

## 왜 나왔나

경쟁 상태를 막으려면 공유 데이터를 만지는 코드를 한 번에 하나만 실행해야 했다. 그런데 프로그램 전체를 하나씩만 돌리면 스레드를 쓰는 의미가 없다.

그래서 **꼭 필요한 최소 구간**만 골라 이름을 붙이고(임계 구역), 그 구간만 상호 배제하기로 했다. 나머지는 마음껏 겹쳐 돈다.

## 확인 질문

- 설명해 보기: 경쟁 상태와 임계 구역은 무엇이 다른가요?
  답: 경쟁 상태는 동시에 고쳐서 결과가 달라지는 문제 자체, 임계 구역은 그 문제가 생길 수 있는 코드 구간. 임계 구역을 찾아 한 번에 하나만 들어가게 하면 경쟁 상태가 사라진다.
- 다음 상태 예측: 이체 함수에서 잔액을 고치는 두 줄과 그 뒤의 "알림 보내기"를 모두 잠갔습니다. 결과는 맞나요? 무엇이 달라지나요?
  답: 결과는 맞다. 다만 알림을 보내는 시간 동안 다른 스레드가 불필요하게 기다린다. 공유 데이터를 안 건드리는 부분까지 잠근 것이다.
- 다음 상태 예측: 잔액을 읽는 줄은 잠그지 않고, 저장하는 줄만 잠갔습니다. 안전한가요?
  답: 안전하지 않다. 읽기와 쓰기 사이에 다른 스레드가 끼어들 수 있어, 낡은 값을 읽고 저장하게 된다. 읽기부터 쓰기까지가 한 구간이어야 한다.

## 심화

### 올바른 해법의 세 조건

임계 구역 문제를 제대로 푼 해법은 세 가지를 만족해야 한다(OSC 6.2). **상호 배제** — 한 번에 하나만 들어간다. **진행** — 아무도 안 들어가 있으면 들어가려는 쪽 중 하나는 반드시 들어간다(서로 양보만 하다 멈추면 안 됨). **유한 대기** — 기다리는 스레드가 영영 밀리지 않는다(기아 방지). 상호 배제만 만족하는 락은 만들기 쉽지만, 셋을 다 만족해야 쓸 만한 락이다.

### 구간은 어떻게 짜이나

진입(락 획득) → 임계 구역 → 퇴출(락 해제) → 나머지 구역. 퇴출을 빠뜨리면 — 예외로 빠져나갈 때가 전형적이다 — 다음 스레드가 들어가지 못한다. 그래서 Java는 `synchronized` 블록처럼 언어가 해제를 보장하는 형태를 쓰거나, `ReentrantLock`이면 `try { … } finally { unlock() }`로 해제를 강제한다.

구간을 잡는 원칙은 두 가지다. 공유 데이터를 **읽는 것부터 쓰는 것까지**가 한 구간이다 — 읽고 나서 잠그면 이미 낡은 값이다. 그리고 I/O·네트워크 호출은 구간 안에 넣지 않는다 — 그 시간 동안 모두가 기다린다.

### 소프트웨어만으로는 왜 안 되나

피터슨 알고리즘처럼 변수 두 개로 상호 배제를 만드는 방법이 있고, 두 스레드에서 세 조건을 만족한다. 그러나 현대 CPU와 컴파일러가 명령 순서를 바꿔 실행하므로 그대로는 안전하지 않다. 실제 락은 하드웨어 원자적 명령(test-and-set, compare-and-swap) 위에 만든다 — 다음 장 뮤텍스다. 커널 안에서는 단일 코어일 때 인터럽트를 잠깐 끄는 것도 보호 수단이지만, 사용자 프로그램은 못 쓰고 멀티코어에서는 다른 코어를 막지 못한다.

### 자주 하는 오해 — "잠그기만 하면 안전"

같은 데이터를 **다른 락**으로 잠그거나, 어떤 경로는 잠그지 않으면 소용없다. 하나의 공유 데이터에는 하나의 락을 정해 그 데이터를 만지는 모든 경로가 그 락을 잡아야 한다. 락이 데이터를 보호하는 게 아니라, "이 데이터는 이 락을 잡고만 만진다"는 **약속**이 보호한다.

### 실무에서는

- `synchronized` 메서드는 메서드 전체가 임계 구역이 된다. 메서드 안에 DB 호출이 있으면 그 시간 동안 다른 스레드가 전부 막히므로, 공유 데이터를 만지는 몇 줄만 `synchronized (lock) { … }` 블록으로 좁힌다.
- DB 트랜잭션은 넓은 의미의 임계 구역이다. `SELECT … FOR UPDATE`부터 `COMMIT`까지가 구간이고, 그 안에서 외부 API를 호출하면 API 응답 시간만큼 행 락이 유지돼 다른 트랜잭션이 밀린다.
- Redis는 명령을 한 스레드로 처리하므로 명령 하나가 곧 임계 구역이다. 여러 명령을 한 구간으로 묶어야 하면 `MULTI`/`EXEC`나 Lua 스크립트로 한 덩어리로 보낸다.
- 서버 여러 대가 같은 자원(예: 일일 정산 배치)을 동시에 실행하면 안 될 때는 JVM 락으로는 부족하고, DB 행 락이나 Redis 분산 락으로 서버들 사이의 임계 구역을 만든다.

### 면접 질문

#### 임계 구역이란 무엇이고, 올바른 해결의 조건은 무엇인가요?

임계 구역은 공유 데이터를 접근하는 코드 중 동시에 실행되면 안 되는 구간이고, 올바른 해결은 상호 배제·진행·유한 대기 세 조건을 만족해야 합니다.
상호 배제는 한 번에 하나만 들어가는 것, 진행은 비어 있을 때 들어가려는 쪽 중 하나는 반드시 들어가는 것, 유한 대기는 기다리는 쪽이 영영 밀리지 않는 것입니다. 상호 배제만 있으면 안전하지만 서로 양보만 하다 멈추거나 특정 스레드가 굶을 수 있어 나머지 둘이 필요합니다.
예를 들어 계좌 이체에서 잔액을 읽어 빼고 더하는 두 줄이 임계 구역이고, 뮤텍스로 이 구간만 감싸면 됩니다. 구간을 너무 넓게 잡으면 안전하지만 느려지고, 좁게 잡거나 한 경로를 빠뜨리면 여전히 깨집니다.

- 꼬리: 상호 배제는 되는데 진행 조건이 깨지는 예를 들어 보세요.
- 꼬리: 유한 대기가 안 지켜지면 무슨 일이 생기나요?

#### `synchronized`를 메서드 전체에 붙이는 것과 블록으로 좁히는 것의 차이는?

메서드 전체에 붙이면 메서드 안의 모든 코드가 임계 구역이 되어 공유 데이터와 무관한 부분까지 다른 스레드를 막고, 블록으로 좁히면 꼭 필요한 구간만 막아 대기 시간이 줄어듭니다.
락을 잡고 있는 시간이 곧 다른 스레드가 기다리는 시간이므로, 구간이 길수록 병렬성이 사라지기 때문입니다.
예를 들어 주문 처리 메서드에 `synchronized`를 붙이면 DB 저장·알림 발송까지 한 번에 하나씩만 처리되지만, 재고 차감 몇 줄만 블록으로 감싸면 나머지는 동시에 돕니다. 다만 좁히다가 읽기와 쓰기를 다른 블록으로 갈라놓으면 그 사이에 끼어들 수 있으니, 읽기부터 쓰기까지는 한 블록이어야 합니다.

- 꼬리: `synchronized (this)`와 `synchronized (별도 lock 객체)`의 차이는?
- 꼬리: 임계 구역 안에서 외부 API를 호출하면 어떤 문제가 생기나요?

#### 서버 두 대에서 같은 배치가 동시에 돌아 중복 정산이 됐습니다. 어떻게 막겠습니까?

서버들 사이에 임계 구역을 만들어야 하므로 JVM 락이 아니라 DB나 Redis 같은 공유 저장소의 락을 씁니다.
`synchronized`는 한 JVM 안의 스레드끼리만 상호 배제하고, 다른 서버의 스레드는 그 락을 모르기 때문입니다.
방법은 배치 실행 기록 테이블에 유일 제약이 있는 행을 먼저 `INSERT`해서 성공한 쪽만 실행하거나, `SELECT … FOR UPDATE`로 잠금 행을 잡거나, Redis `SET key value NX PX 만료시간`으로 분산 락을 잡는 것입니다. 한계는 락을 잡은 서버가 죽으면 락이 남을 수 있어 만료 시간이 필요하고, 만료 시간이 배치보다 짧으면 다시 중복이 생긴다는 점입니다.

- 꼬리: 분산 락의 만료 시간은 어떻게 정하나요?
- 꼬리: DB 유일 제약으로 막는 방법과 분산 락의 장단점은?
