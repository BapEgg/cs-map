## 개념

뮤텍스(mutual exclusion의 줄임)는 **임계 구역 앞에서 잠그고(lock) 나올 때 푸는(unlock) 자물쇠**다.
잠겨 있으면 다른 흐름은 풀릴 때까지 기다리고, 풀리면 기다리던 것 중 하나가 잠그고 들어간다. 잠근 쪽만 풀 수 있다는 것이 뮤텍스의 핵심 규칙이다.
결과적으로 임계 구역은 한 번에 하나만 실행되고, 경쟁 상태가 사라진다.

예를 들어 스레드 1과 2가 `count++`를 하되, 앞뒤에 `lock(m)`과 `unlock(m)`을 두었다고 하자.
스레드 1이 잠그고 50을 읽는 순간 문맥 교환이 나도, 스레드 2는 `lock(m)`에서 멈춘다. 스레드 1이 돌아와 51을 저장하고 푼다.
그제야 스레드 2가 잠그고 51을 읽어 52를 저장한다. 끼어드는 타이밍이 어떻든 결과는 항상 52다.

비유하면 열쇠가 하나뿐인 화장실이다. 열쇠를 가진 사람만 들어가고, 나올 때 열쇠를 돌려준다.
비유가 안 통하는 데는, 화장실 열쇠는 아무나 가져다 돌려줄 수 있지만 뮤텍스는 **잠근 스레드만 풀 수 있다**는 점이다. 그래서 "A가 잠그고 B가 푸는" 신호용으로는 못 쓰고, 그 용도는 세마포어가 맡는다.

## 왜 나왔나

임계 구역을 한 번에 하나만 실행하려면 "지금 누가 들어가 있나"를 나타내는 깃발이 필요했다.
그런데 깃발을 확인하고 세우는 것 자체가 두 명령이라, 그 사이에 끼어들면 둘 다 들어간다 — 깃발에도 경쟁 상태가 생긴다.
그래서 CPU가 **확인과 세우기를 한 명령으로** 해 주는 원자적 명령(test-and-set 등)을 제공했고, 그 위에 잠그기·풀기·기다리기를 갖춘 뮤텍스를 만들었다.
결국 뮤텍스는 하드웨어 원자성을 빌려 프로그래머가 원하는 구간 전체를 원자적으로 보이게 하는 장치다.

## 심화

### 내부 구조

#### 좋은 락의 기준 (OSTEP 28장)

**상호 배제**가 되는가, **공정**한가(기다리는 스레드가 굶지 않는가), **성능**은 어떤가(경합 없을 때 비용, 경합 있을 때 비용).

#### 가장 단순한 구현 — 스핀락

가장 단순한 구현은 **스핀락**: 원자적 test-and-set으로 깃발을 잡을 때까지 반복문을 돈다. 경합이 없거나 임계 구역이 아주 짧고 코어가 여럿이면 빠르지만, 코어 하나에서 락 주인이 밀려나 있으면 기다리는 쪽이 퀀텀을 통째로 태우고, 공정성도 없다.

#### 실제 뮤텍스는 잠든다

그래서 실제 뮤텍스는 **잠든다**: 못 잡으면 대기 큐에 넣고 스레드를 재우고(park), 풀 때 큐에서 하나를 깨운다(unpark). 리눅스는 이걸 futex로 만든다 — 경합이 없으면 사용자 공간에서 원자 연산 한 번으로 끝내고(시스템 호출 없음), 경합이 있을 때만 커널에 들어가 잔다. 깨우고 재우는 데 문맥 교환이 드니, 잠깐 돌다가 안 되면 자는 **2단계 락**(two-phase)을 쓰기도 한다.

#### 소유권

잠근 스레드만 풀 수 있다. 다른 스레드가 풀면 오류(pthread `EPERM`)거나 미정의 동작이다. Java `ReentrantLock`도 소유자가 아닌 스레드가 `unlock()` 하면 예외를 던진다.

#### 재진입

같은 스레드가 이미 잡은 락을 또 잡으면? 기본 pthread 뮤텍스는 교착(자기 자신을 기다림), 재진입 락(`PTHREAD_MUTEX_RECURSIVE`, Java `synchronized`·`ReentrantLock`)은 횟수를 세어 허용한다.

#### 비용

경합 없는 락은 원자 연산 한 번(수십 ns)이라 싸다. 경합이 생기면 잠들고 깨는 문맥 교환(µs)과, 깨어난 스레드가 캐시를 다시 채우는 시간이 든다. 병목은 대개 "락 자체"가 아니라 "락 안에서 보내는 시간 × 경합 빈도"다.

#### 자주 하는 오해

"뮤텍스 = 이진 세마포어". 동작은 비슷해 보여도 뮤텍스는 소유자가 있고(잠근 쪽만 풂, 우선순위 상속 가능), 세마포어는 소유자 개념이 없어 아무나 올릴 수 있다. 용도가 다르다.
### 실제 활용

- Java `synchronized`는 객체마다 붙은 재진입 뮤텍스다(JVM 모니터). `ReentrantLock`은 같은 뮤텍스지만 `tryLock(timeout)`, 공정 모드, 조건 변수 여러 개를 준다. 단순한 경우 `synchronized`, 타임아웃이나 공정성이 필요하면 `ReentrantLock`.
- 읽기가 압도적이면 `ReadWriteLock`: 읽기끼리는 같이 들어가고 쓰기만 배타적으로. 캐시 갱신처럼 "가끔 쓰고 늘 읽는" 데이터에 맞는다.
- DB 행 락(`SELECT … FOR UPDATE`)은 트랜잭션 단위의 뮤텍스다. 커밋·롤백이 곧 unlock이라, 트랜잭션이 길면 락도 길다.
- 스핀락은 커널·고성능 라이브러리가 쓴다. 애플리케이션 코드에서 직접 돌면(busy-wait) CPU만 태우기 쉬우니, JVM이 `synchronized`에서 알아서 잠깐 스핀했다가 재우는 데 맡긴다.
- 락 없이 가는 길: `AtomicInteger`·`ConcurrentHashMap`은 compare-and-swap으로 락 없이 갱신한다(lock-free). 경합이 심하면 재시도가 늘어 락보다 느려질 수도 있다.

### 면접 질문

#### 뮤텍스는 무엇이고, 어떻게 동작하나요?

뮤텍스는 임계 구역에 한 번에 한 스레드만 들어가게 하는 자물쇠로, 들어갈 때 잠그고 나올 때 풀며 잠근 스레드만 풀 수 있습니다.
내부는 하드웨어 원자적 명령으로 "비어 있으면 잠그기"를 한 번에 처리해 깃발 자체의 경쟁 상태를 없애고, 잠겨 있으면 기다리는 스레드를 대기 큐에 넣고 재웠다가 풀릴 때 깨웁니다.
예를 들어 두 스레드가 `count++`를 뮤텍스로 감싸면 결과가 항상 52로 결정됩니다. 한계는 락을 잡고 있는 동안 다른 스레드가 모두 기다리므로 구간이 길거나 경합이 잦으면 병렬성이 사라지고, 락이 둘 이상이면 교착상태가 생길 수 있다는 점입니다.

- 꼬리: 뮤텍스와 이진 세마포어의 차이는?

#### `synchronized`와 `ReentrantLock`은 무엇이 다르고, 어느 쪽을 언제 쓰나요?

둘 다 재진입 가능한 뮤텍스지만, `synchronized`는 언어가 해제를 보장하는 대신 기능이 단순하고, `ReentrantLock`은 직접 `unlock()`해야 하는 대신 타임아웃·공정 모드·조건 변수 여러 개를 줍니다.
`synchronized`는 블록을 벗어나면 예외가 나도 자동으로 풀리므로 실수할 여지가 적고, `ReentrantLock`은 `tryLock(1, SECONDS)`로 기다리다 포기하거나 락 순서를 못 지킬 때 교착을 피하는 등 제어가 필요할 때 씁니다.
예를 들어 카운터 갱신처럼 짧고 단순한 구간은 `synchronized`, 여러 락을 잡는 이체 로직에서 타임아웃으로 교착을 피하고 싶으면 `ReentrantLock`입니다. 성능은 현대 JVM에서 비슷하므로 성능 때문에 고르지는 않습니다.

- 꼬리: `ReentrantLock`을 쓸 때 `finally`에서 `unlock()` 해야 하는 이유는?
- 꼬리: 공정 모드(fair)를 켜면 왜 느려지나요?

#### 락을 걸었더니 처리량이 반토막 났습니다. 어디부터 보겠습니까?

락을 잡고 있는 시간과 경합 빈도부터 봅니다. 락의 비용은 잠그는 행위가 아니라 "락 안에서 보내는 시간 × 동시에 들어오려는 스레드 수"이기 때문입니다.
스레드 덤프에서 많은 스레드가 같은 락에 `BLOCKED`면 그 임계 구역이 병목입니다. 구간 안에 DB 호출·I/O·로그 같은 느린 일이 있으면 밖으로 빼고, 하나의 큰 락을 데이터별 작은 락으로 쪼개거나(락 분할), 읽기가 많으면 `ReadWriteLock`으로, 단순 갱신이면 `AtomicXxx`로 바꿉니다.
예를 들어 전체 캐시를 하나의 `synchronized`로 감쌌다면 `ConcurrentHashMap`으로 바꿔 키별로 경합을 나누는 것만으로 대부분 해결됩니다. 한계는 락을 잘게 쪼갤수록 여러 락을 잡을 일이 생겨 교착 위험과 코드 복잡도가 오른다는 점입니다.
