## 개념

논블로킹 소켓이 1만 개 있다고 하자. 스레드 하나가 1만 개를 차례로 "읽을 거 있어?" 물어보면 대부분 "없음"이라 CPU만 돈다. I/O 멀티플렉싱은 이걸 뒤집는다. **커널에 "이 fd들 중 하나라도 준비되면 깨워 줘"라고 맡기고 잠든다.** 커널이 준비된 fd 목록을 돌려주면 그것들만 읽는다.

그래서 스레드 하나로 연결 수만 개를 돌볼 수 있다. 대부분의 연결은 조용히 기다리고 있고, 실제로 데이터가 오는 건 그중 몇 개뿐이기 때문이다. 이 구조를 반복문으로 돌리는 것이 이벤트 루프다.

연결 3개를 한 스레드로 지키는 상황을 따라가 보자.

- 시작: 소켓 fd 4·5·6을 epoll에 등록하고 `epoll_wait`로 잠든다.
- 진행: 5번에 데이터가 도착한다. 커널이 스레드를 깨우며 "5번 준비됨"을 돌려준다. 스레드가 5번을 읽어 요청을 처리하고 응답을 쓴 뒤 다시 `epoll_wait`로 잠든다.
- 결과: 4·6번을 확인하느라 CPU를 쓰지 않았고, 스레드는 3개 연결 모두를 놓치지 않았다.

## 왜 나왔나

연결마다 스레드를 두면 연결이 늘수록 스레드가 늘고, 대부분은 잠들어 있으면서 스택과 문맥 교환 비용만 쓴다. 논블로킹으로 바꿔도 누가 준비됐는지 계속 물어봐야 하니 CPU가 낭비됐다.

그래서 "준비된 것만 알려 달라"는 시스템 호출(`select` → `poll` → `epoll`)이 생겼다. 스레드 수를 연결 수가 아니라 코어 수에 맞출 수 있게 됐고, 이것이 Node.js·Nginx·Netty 같은 이벤트 기반 서버의 바탕이다.

## 확인 질문

- 설명해 보기: 멀티플렉싱이 "논블로킹으로 하나씩 물어보기"보다 나은 점은?
  답: 커널이 준비된 fd만 알려 주므로, 준비 안 된 수천 개를 확인하느라 CPU를 쓰지 않고 잠들어 있을 수 있다.
- 다음 상태 예측: epoll에 등록한 연결 1만 개 중 3개에 데이터가 왔다. `epoll_wait`는 무엇을 돌려주나?
  답: 그 3개만. 나머지 9,997개는 보지도 않는다.
- 다음 상태 예측: 이벤트 루프 스레드가 한 요청을 처리하며 DB를 2초 블로킹으로 기다리면?
  답: 그 2초 동안 다른 모든 연결의 이벤트가 밀린다. 이벤트 루프에서는 블로킹 호출을 하면 안 된다.

## 심화

### select → poll → epoll

`select`는 fd 집합을 비트로 넘기는데 상한이 1024(`FD_SETSIZE`)이고, 부를 때마다 전체 집합을 커널에 복사하고 전부 훑는다(O(n)). `poll`은 상한이 없지만 여전히 매번 전부 훑는다. `epoll`(리눅스)은 관심 목록을 커널에 한 번 등록해 두고 준비된 것만 돌려주므로 연결 수와 무관하게 준비된 수에 비례한다. macOS·BSD는 `kqueue`, 윈도우는 IOCP가 같은 역할을 한다.

### 레벨 트리거와 에지 트리거

레벨 트리거는 "읽을 게 남아 있는 한" 계속 알려 주고(기본), 에지 트리거는 "새로 생긴 순간" 한 번만 알려 준다. 에지 트리거는 호출 횟수가 줄지만, 알림을 받았을 때 `EAGAIN`이 날 때까지 다 읽어야 한다 — 남겨 두면 다음 알림이 안 온다.

### 무엇이 "준비"인가

읽기 준비는 소켓 버퍼에 데이터가 있다는 뜻이지, 요청 한 건이 완전히 도착했다는 뜻이 아니다. HTTP 요청 하나가 여러 조각으로 오면 애플리케이션이 조각을 모아야 한다. 디스크 파일은 epoll에서 늘 "준비"로 보고되므로(실제 읽기는 블로킹), 파일 I/O는 별도 스레드 풀이나 `io_uring`으로 처리한다 — Node.js가 libuv 스레드 풀을 두는 이유다.

### 실무에서는

- Node.js: 이벤트 루프 하나 + libuv 스레드 풀(파일·DNS·암호화). CPU 계산이 긴 코드가 루프를 막으면 모든 요청이 멈춘다. `worker_threads`나 프로세스 분리로 뺀다.
- Netty·Spring WebFlux: 이벤트 루프 스레드는 코어 수 근처. 블로킹 호출(JDBC, `RestTemplate`)을 넣으면 루프가 막힌다. 블로킹이 불가피하면 `Schedulers.boundedElastic()` 같은 별도 풀로.
- Nginx: 워커 프로세스 몇 개가 각각 epoll 루프를 돌려 수만 연결을 처리한다.
- Tomcat NIO: 연결 수신과 대기는 epoll(Poller)로, 요청 처리는 스레드 풀로. "연결 8192, 처리 스레드 200"이 가능한 이유다.
- `ulimit -n`이 낮으면 epoll에 등록할 fd 자체를 못 만든다. 연결 수 = fd 수.

### 면접 질문

#### I/O 멀티플렉싱이 무엇이고, 왜 스레드 하나로 수만 연결을 처리할 수 있나요?

스레드 하나가 여러 fd를 커널에 맡겨 두고 준비된 것만 돌려받아 처리하는 방식이며, 대부분의 연결은 어느 순간에나 조용히 기다리는 중이라 실제로 할 일은 몇 개뿐이기 때문입니다.
연결마다 스레드를 두면 잠든 스레드가 스택과 문맥 교환 비용을 쓰지만, epoll은 준비된 수에 비례하는 비용만 듭니다.
예를 들어 Nginx 워커 하나가 epoll로 수만 연결을 돌립니다. 한계는 처리 코드가 블로킹되거나 CPU를 오래 쓰면 그 스레드가 맡은 모든 연결이 함께 멈추고, 코드가 콜백·상태 기계로 복잡해진다는 점입니다.

- 꼬리: 이벤트 루프에서 CPU 계산이 긴 작업은 어떻게 처리하나요?

#### Tomcat(요청당 스레드)과 Netty(이벤트 루프) 중 어느 쪽을 언제 고르나요?

요청 처리가 대부분 블로킹 API(JDBC, 동기 HTTP 클라이언트)에 기대고 팀이 그 코드에 익숙하면 Tomcat, 연결 수가 매우 많고 대기가 길며 처리 자체는 짧은(프록시·게이트웨이·채팅·스트리밍) 경우면 Netty 계열이 맞습니다.
요청당 스레드는 코드가 단순하고 블로킹 호출을 그대로 쓸 수 있지만 동시 연결이 스레드 수에 묶이고, 이벤트 루프는 연결 수에 강하지만 블로킹 호출 하나가 전체를 멈추고 DB 드라이버까지 논블로킹(R2DBC)이어야 이득이 납니다.
예를 들어 일반 CRUD 서비스는 Tomcat + 스레드 풀로 충분하고, 수만 클라이언트가 붙는 알림 서버는 이벤트 루프가 맞습니다. Java 21 가상 스레드는 요청당 스레드 모델을 유지하면서 연결 수 문제를 줄이는 세 번째 선택지입니다.
