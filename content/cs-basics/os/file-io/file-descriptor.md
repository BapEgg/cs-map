## 개념

프로그램이 파일을 열면 운영체제는 파일 내용을 넘겨주지 않는다. 대신 "이 프로세스가 이 파일을 열었다"는 기록을 커널 안에 만들고, 그 기록을 가리키는 **작은 정수 번호**를 돌려준다. 이 번호가 파일 디스크립터(fd)다. 이후 읽기·쓰기는 "3번에서 100바이트 읽어 줘"처럼 번호로 부른다.

파일만이 아니다. 네트워크 소켓, 파이프, 터미널도 같은 방식으로 번호를 받는다. 그래서 프로그램은 상대가 디스크든 네트워크든 같은 `read`·`write`로 다룬다. 프로세스마다 0(표준 입력), 1(표준 출력), 2(표준 오류)가 미리 열려 있다.

파일을 열어 읽는 과정을 따라가 보자.

- 시작: 프로세스의 fd 표에 0·1·2만 있다.
- 진행: `open("log.txt")` → 커널이 파일 기록을 만들고 비어 있는 가장 작은 번호 3을 준다. `read(3, buf, 100)` → 커널이 3번 기록을 찾아 파일의 현재 위치에서 100바이트를 `buf`에 넣고, 위치를 100 앞으로 옮긴다. `close(3)` → 기록을 지우고 3번을 비운다.
- 결과: `buf`에 데이터 100바이트. 다음 `open`은 다시 3번을 받는다.

## 왜 나왔나

프로그램이 파일의 실제 위치(디스크 블록 번호)를 직접 다루면 파일 시스템 구조가 프로그램에 새어 나가고, 여러 프로세스가 같은 파일을 열 때 누가 어디까지 읽었는지 관리할 수 없었다.

그래서 커널이 "열린 파일"의 상태(위치, 권한, 모드)를 자기 쪽에 두고 프로그램에는 **번호만** 주기로 했다. 번호는 프로세스마다 따로 세므로 다른 프로세스의 3번과 내 3번은 다른 파일이다.

## 확인 질문

- 설명해 보기: `open`이 파일 내용 대신 정수를 돌려주는 이유는?
  답: 열린 파일의 상태(위치·권한)는 커널이 갖고, 프로그램은 번호로 가리키기만 하면 되기 때문이다. 소켓·파이프도 같은 번호 체계로 다룰 수 있다.
- 다음 상태 예측: 0·1·2만 열린 프로세스가 파일 두 개를 열면 번호는?
  답: 3, 4. 비어 있는 가장 작은 번호부터 준다.
- 다음 상태 예측: 3번을 닫고 다시 파일을 열면?
  답: 다시 3번. 닫힌 번호는 재사용된다 — 닫은 뒤 옛 번호로 읽으면 엉뚱한 파일을 읽을 수 있다.

## 심화

### 커널 안의 세 단계

프로세스별 fd 표(번호 → 열린 파일 항목), 시스템 전체의 열린 파일 표(현재 위치·모드), 그리고 파일 자체(inode)로 이어진다. `fork`하면 자식이 fd 표를 복사하지만 열린 파일 항목은 **공유**하므로 부모와 자식이 같은 위치 포인터로 읽는다. `dup2`로 번호를 바꿔 끼우는 것이 셸의 `>` 리다이렉션이다.

### 한도와 누수

프로세스당 열 수 있는 fd 수에 상한이 있다(`ulimit -n`, 리눅스 배포판 기본 1024가 흔하고 서버는 수만으로 올린다). 소켓도 fd이므로 동시 연결 1만 개를 받으려면 한도가 그 이상이어야 한다. 열고 닫지 않으면(누수) 어느 순간 `Too many open files`로 새 연결·파일 열기가 전부 실패한다.

### 실무에서는

- Java의 `try-with-resources`는 스트림·소켓을 블록 끝에서 닫아 fd 누수를 막는 문법이다. `InputStream`을 열고 예외로 빠져나가면 fd가 새는 전형적 버그를 막는다.
- 커넥션 풀의 연결 하나가 소켓 fd 하나다. 풀 크기 × 서버 수만큼 DB 쪽 fd·프로세스가 든다.
- 로그 파일을 열어 둔 채 로테이션으로 지우면 디스크 공간이 안 돌아온다 — 열린 fd가 파일을 붙들고 있다(`lsof`로 확인).
- `Too many open files`는 코드 어딘가에서 닫지 않는 곳이 있다는 신호지, 한도만 올려서 끝낼 문제가 아니다.

### 면접 질문

#### 파일 디스크립터란 무엇이고 왜 정수인가요?

프로세스가 연 파일·소켓·파이프를 가리키는 프로세스별 정수 번호이며, 커널이 열린 파일의 상태를 자기 쪽에 두고 프로그램에는 그 항목의 색인만 주기 때문에 정수입니다.
프로그램이 상태를 직접 갖지 않으니 파일 시스템 구조가 바뀌어도 프로그램은 그대로고, 디스크·네트워크·터미널을 같은 `read`/`write`로 다룰 수 있습니다.
예를 들어 웹 서버가 연결을 받으면 소켓 fd를 하나 받고, 그 번호로 요청을 읽고 응답을 씁니다. 한계는 프로세스당 개수에 상한이 있어 닫지 않으면 `Too many open files`로 서비스가 멈춘다는 점입니다.

#### `Too many open files` 오류가 났습니다. 어떻게 접근하나요?

먼저 어떤 fd가 쌓이는지 `lsof -p <pid>`로 종류(소켓·파일)를 보고, 닫지 않는 코드 경로를 찾습니다. 한도를 올리는 것은 임시 조치입니다.
fd는 열면 닫아야 하는 자원인데, 예외 경로에서 `close`를 빠뜨리거나 HTTP 클라이언트·스트림을 매 요청 새로 만들고 안 닫으면 시간이 지나며 상한(기본 1024 등)에 닿습니다.
예를 들어 `new FileInputStream`을 `try-with-resources` 없이 쓰고 중간에 예외가 나면 fd가 샙니다. 소켓이 `CLOSE_WAIT` 상태로 쌓여 있다면 응답을 받고도 닫지 않는 클라이언트 코드가 원인입니다. 고친 뒤 필요하면 `ulimit -n`을 서비스 동시 연결 수에 맞게 올립니다.
