## 개념

스레드 풀은 **스레드를 미리 몇 개 만들어 두고, 들어오는 일을 작업 큐에 쌓아 놓으면 놀고 있는 스레드가 하나씩 꺼내 처리하는 구조**다.
일마다 스레드를 새로 만들고 버리는 대신 만들어 둔 것을 돌려쓰니 생성 비용이 사라지고, 동시에 도는 스레드 수에 상한이 생긴다.
일이 스레드보다 많으면 큐에서 기다리고, 큐까지 차면 거절하거나 호출한 쪽이 직접 처리하는 등 정해 둔 규칙을 따른다.

예를 들어 스레드 4개짜리 풀에 요청 10개가 한꺼번에 들어왔다고 하자.
요청 1~4는 즉시 스레드를 받아 처리되고, 5~10은 큐에 줄을 선다. 요청 1이 끝나면 그 스레드가 큐 맨 앞의 5를 꺼낸다.
결과적으로 10개 모두 처리되지만 동시에 도는 건 늘 4개 이하고, 스레드는 단 한 번도 새로 만들어지지 않는다.

비유하면 손님마다 직원을 새로 뽑는 대신 직원 몇 명이 번호표 순서로 손님을 받는 창구다.
비유가 안 통하는 데는, 창구 직원은 손님이 없어도 월급이 나가지만 스레드는 **놀 때 CPU를 거의 안 쓴다**는 점이다. 풀의 비용은 CPU가 아니라 스택 메모리와 커널 자원이다.

## 왜 나왔나

요청이 올 때마다 스레드를 만들면 두 가지가 문제였다.
만들고 없애는 비용이 요청 처리 자체보다 클 수 있고, 요청이 폭주하면 스레드가 무한정 늘어나 메모리가 바닥나거나 문맥 교환만 하다 서버가 멈춘다.
그래서 스레드를 **미리 만들어 두고 돌려쓰며 개수에 상한을 두는** 풀이 나왔다. 넘치는 일은 큐에서 기다리게 해 서버가 감당할 만큼만 동시에 처리한다.
결국 풀은 속도를 올리는 장치라기보다 **폭주에도 무너지지 않게 하는 장치**다.

## 심화

### 내부 구조

- 구성: 작업 큐 + 워커 스레드들 + 크기 규칙 + 거절 정책. 워커는 "큐에서 하나 꺼내 실행하고 다시 큐를 본다"를 무한 반복하며, 큐가 비면 잠든다(잠든 동안 CPU를 안 쓴다).
- Java `ThreadPoolExecutor`의 규칙(JDK 21 문서): 도는 스레드가 `corePoolSize`보다 적으면 **새 스레드**를 만들고, 그 이상이면 **큐에 넣는 걸 우선**하며, 큐가 가득 차야 `maximumPoolSize`까지 스레드를 더 만들고, 그것도 넘으면 거절한다. 큐가 무한(`LinkedBlockingQueue` 기본)이면 `maximumPoolSize`는 영영 쓰이지 않는다 — 실무에서 자주 하는 오해다.
- 거절 정책: 기본은 예외(`AbortPolicy`). `CallerRunsPolicy`는 제출한 스레드가 직접 실행해 제출 속도를 자연스럽게 늦춘다(배압). `Discard`·`DiscardOldest`는 결과를 안 믿어도 되는 일에만 쓴다.
- 크기 정하기(Java Concurrency in Practice): CPU 계산 위주면 코어 수 + 1 근처, I/O 대기가 많으면 코어 수 × (1 + 대기 시간/계산 시간). 대기 비율이 높을수록 스레드를 더 둘 수 있다. 다만 뒷단(DB 커넥션 풀 등)이 감당하는 만큼까지만 의미가 있다.
- 비용과 한계: 스레드마다 스택이 잡히고, 큐가 무한이면 폭주 때 메모리가 큐에서 터진다. 큐 대기 시간은 응답 시간에 그대로 더해지는데 눈에 잘 안 보인다. 한 작업이 락이나 외부 응답을 오래 기다리면 풀의 스레드가 하나씩 묶여 결국 풀 전체가 멈춘다(풀 고갈).
- 오해: "풀을 키우면 빨라진다"는 병목이 CPU나 뒷단일 때는 틀리다. 스레드가 늘어도 DB 커넥션이 10개면 10개만 일하고 나머지는 대기다.

### 실제 활용

- Tomcat(Spring Boot 기본): 요청 처리 스레드 풀 `maxThreads` 기본 200, 동시에 받아 두는 연결 `maxConnections` 기본 8192, 그 위 OS 대기열 `acceptCount` 기본 100. 스레드 200개가 모두 바쁘면 연결은 받아 두되 처리는 기다린다. Spring Boot에서는 `server.tomcat.threads.max`로 바꾼다.
- 풀 고갈의 전형: 외부 API가 30초씩 늦어지면 요청 스레드 200개가 그 API를 기다리며 다 묶이고, 아무 관계 없는 헬스체크 요청까지 응답을 못 해 서버가 죽은 것으로 판정된다. 그래서 외부 호출에는 타임아웃을 짧게 두고, 느린 작업은 별도 풀로 격리한다(벌크헤드).
- `@Async`·`@Scheduled`는 기본 스레드 풀 설정이 작으니(Spring Boot의 `TaskExecutor` 기본 core 8, 큐 무한) 배치를 무심코 던지면 큐에서 하염없이 기다린다. 큐 크기와 거절 정책을 명시한다.
- DB 커넥션 풀(HikariCP)도 같은 발상이다 — 연결을 미리 만들어 돌려쓴다. 스레드 풀보다 커넥션 풀이 작으면 요청 스레드들이 커넥션을 기다리며 대기 상태가 된다. 두 풀의 크기는 함께 정한다.

### 면접 질문

#### 스레드 풀을 쓰는 이유는 무엇인가요?

스레드 생성·소멸 비용을 없애고 동시에 도는 스레드 수에 상한을 두어, 요청이 폭주해도 서버가 무너지지 않게 하기 위해서입니다.
스레드를 요청마다 만들면 만드는 시간이 처리 시간보다 길 수 있고, 폭주 시 스레드가 무한정 늘어 메모리 부족이나 과도한 문맥 교환으로 서버 전체가 느려집니다.
Tomcat이 기본 200개 스레드 풀로 요청을 받고 넘치는 요청은 큐에서 기다리게 하는 게 대표적입니다. 한계는 큐 대기 시간이 응답 시간에 더해지고, 느린 작업 하나가 풀 전체를 묶어 버릴 수 있다는 점입니다.

- 꼬리: 큐가 가득 차면 어떻게 되나요? 거절 정책에는 무엇이 있나요?
- 꼬리: `corePoolSize`와 `maximumPoolSize`가 있는데 왜 스레드가 core를 넘어 늘지 않는 경우가 있나요?

#### 스레드 풀 크기는 어떻게 정하나요?

작업이 CPU 계산 위주인지 I/O 대기 위주인지에 따라 다릅니다. 계산 위주면 코어 수 근처, 대기 위주면 코어 수 × (1 + 대기 시간/계산 시간)에서 출발해 부하 테스트로 맞춥니다.
계산 위주에서 코어보다 많이 두면 CPU를 더 쓰는 게 아니라 문맥 교환만 늘고, 대기 위주에서는 기다리는 동안 CPU가 비므로 더 둘 수 있기 때문입니다.
예를 들어 코어 8개, 요청 하나가 DB 대기 90ms에 계산 10ms라면 8 × (1 + 9) = 80 근처가 출발점입니다. 다만 DB 커넥션 풀이 20개면 80개 중 60개는 커넥션을 기다리므로, 뒷단 자원과 함께 정해야 합니다.

- 꼬리: 스레드 풀보다 커넥션 풀이 작으면 무슨 일이 생기나요?
- 꼬리: 가상 스레드를 쓰면 풀 크기 고민이 사라지나요?

#### 외부 API 하나가 느려졌을 뿐인데 서비스 전체가 멈췄습니다. 왜 그런가요, 어떻게 막나요?

요청 스레드 풀이 고갈됐기 때문입니다. 느린 API를 기다리는 요청이 스레드를 하나씩 붙들고 놓지 않아, 풀의 스레드가 전부 그 API 대기에 묶이면 무관한 요청도 스레드를 못 받아 멈춥니다.
막으려면 외부 호출에 짧은 타임아웃을 두어 스레드를 빨리 돌려주고, 느린 외부 호출은 별도 스레드 풀로 격리해(벌크헤드) 그 풀만 고갈되게 하며, 실패가 반복되면 서킷 브레이커로 호출 자체를 잠시 끊습니다.
예를 들어 Tomcat 200개 스레드 중 결제 API 호출을 20개짜리 별도 풀로 돌리면, 결제사가 멈춰도 나머지 180개는 조회 요청을 계속 처리합니다. 한계는 격리한 풀 안에서는 여전히 기다리므로 타임아웃이 반드시 같이 있어야 한다는 점입니다.

- 꼬리: 타임아웃은 연결 타임아웃과 읽기 타임아웃으로 왜 나누나요?
- 꼬리: 서킷 브레이커는 언제 다시 닫히나요?
