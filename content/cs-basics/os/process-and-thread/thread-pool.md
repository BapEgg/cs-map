## 개념

서버에 요청이 하나 들어올 때마다 스레드를 새로 만들어 맡기고, 끝나면 없앨 수 있다. 하지만 스레드를 만들고 없애는 데도 시간이 들고, 요청이 한꺼번에 몰리면 스레드가 끝없이 늘어난다. 스레드 풀은 **스레드를 몇 개 만들어 두고, 들어오는 일을 줄(작업 큐)에 세워 두면 놀고 있는 스레드가 하나씩 꺼내 처리하는 구조**다.

스레드는 일이 끝나면 없어지지 않고 다시 큐를 본다. 그래서 같은 스레드가 요청 1을 처리한 뒤 요청 5를, 그다음 요청 9를 처리한다. 만들어 두는 개수에 상한이 있으니, 요청이 아무리 몰려도 동시에 도는 스레드 수는 그 상한을 넘지 않는다.

스레드 4개짜리 풀에 요청 10개가 한꺼번에 들어오는 상황을 따라가 보자.

- 시작: 풀에 스레드 4개가 있고 큐는 비어 있다(풀이 이미 몸을 푼 상태라고 하자).
- 진행: 요청 1~4가 스레드 4개에 바로 배정된다. 요청 5~10은 큐에 줄을 선다. 요청 1이 끝나면 그 스레드가 큐 맨 앞의 5를 꺼낸다.
- 결과: 10개가 모두 처리되지만 동시에 도는 것은 늘 4개 이하다. 요청 5~10은 큐에서 기다린 시간만큼 응답이 늦어진다.

풀은 속도를 올리는 장치라기보다 **폭주에도 무너지지 않게 하는 장치**다. 넘치는 일은 큐에서 기다리고, 큐까지 차면 거절하거나 요청한 쪽이 직접 처리하는 등 미리 정한 규칙을 따른다.

## 왜 나왔나

요청마다 스레드를 만들면 두 가지가 문제였다. 스레드를 만들고 없애는 비용이 짧은 요청에서는 처리 자체보다 클 수 있고, 요청이 폭주하면 스레드가 무한정 늘어나 메모리가 바닥나거나 문맥 교환만 하다 서버가 멈춘다.

그래서 스레드를 **만들어 두고 돌려쓰며 개수에 상한을 두는** 풀이 나왔다. 생성 비용은 첫 몇 번으로 끝나고, 동시 실행 수가 묶이니 서버가 감당할 만큼만 처리한다.

## 확인 질문

- 설명해 보기: 스레드 풀이 해결하는 문제 두 가지를 말해 보세요.
  답: 요청마다 스레드를 만들고 없애는 비용, 그리고 폭주 때 스레드가 무한정 늘어나는 것. 만들어 둔 스레드를 돌려쓰고 개수에 상한을 둔다.
- 다음 상태 예측: 스레드 3개짜리 풀이 모두 바쁜데 요청이 하나 더 왔습니다. 어떻게 되나요?
  답: 큐에 들어가 기다린다. 어느 스레드든 일을 끝내면 큐에서 꺼내 처리한다. 큐가 꽉 찼다면 풀의 규칙대로 거절되거나 다른 처리를 받는다.
- 다음 상태 예측: 요청 처리 시간이 100ms인데 스레드 4개짜리 풀에 요청이 동시에 8개 왔습니다. 마지막 요청의 응답은 언제쯤 나오나요?
  답: 약 200ms 뒤. 앞 4개가 100ms에 끝나고 다음 4개가 이어서 100ms 걸린다. 큐 대기 100ms가 응답 시간에 그대로 더해진다.

## 심화

### 풀은 무엇으로 이루어지나

작업 큐, 워커 스레드들, 크기 규칙, 거절 정책 넷이다. 워커는 "큐에서 하나 꺼내 실행하고 다시 큐를 본다"를 반복하며, 큐가 비면 잠든다(잠든 동안 CPU를 안 쓴다). 큐가 유한한지 무한한지, 스레드를 몇 개까지 만들지, 넘치면 어떻게 할지가 풀의 성격을 정한다.

### Java `ThreadPoolExecutor`는 어떻게 움직이나

기초에서 "만들어 둔다"고 했지만 Java 표준 풀은 **필요할 때 만든다**. JDK 21 문서의 규칙은 이렇다.

1. 도는 스레드가 `corePoolSize`보다 적으면, 노는 스레드가 있어도 **새 스레드**를 만들어 맡긴다.
2. core 개수가 다 찼으면 **큐에 넣는 것을 우선**한다.
3. 큐가 가득 찼을 때만 `maximumPoolSize`까지 스레드를 더 만든다.
4. 그것도 넘으면 거절 정책을 부른다.

그래서 큐가 무한(`Executors.newFixedThreadPool`의 `LinkedBlockingQueue`)이면 3번이 영영 오지 않아 `maximumPoolSize`가 쓰이지 않는다 — 자주 하는 오해다. core를 넘어 만든 스레드는 `keepAliveTime` 동안 놀면 없어진다. 처음부터 다 만들어 두고 싶으면 `prestartAllCoreThreads()`를 부른다.

거절 정책은 넷이다. 기본 `AbortPolicy`는 예외를 던지고, `CallerRunsPolicy`는 제출한 스레드가 직접 실행해 제출 속도를 자연히 늦추며(배압), `DiscardPolicy`·`DiscardOldestPolicy`는 결과를 믿지 않아도 되는 일에만 쓴다.

### 크기는 어떻게 정하나

Java Concurrency in Practice의 출발점은 스레드 수 ≈ 코어 수 × 목표 CPU 사용률 × (1 + 대기 시간/계산 시간)이다. 계산만 하는 작업은 코어 수 근처, 대기가 긴 작업은 그 비율만큼 더 둘 수 있다.

| 작업 성격 | 출발점 | 이유 |
|---|---|---|
| CPU 계산 위주 | 코어 수 ~ 코어 수 + 1 | 코어보다 많으면 나눠 쓸 뿐, 문맥 교환만 는다 |
| I/O 대기 위주 (대기 90ms, 계산 10ms) | 코어 수 × 10 | 기다리는 동안 코어가 비니 더 둘 수 있다 |
| 뒷단이 DB 커넥션 20개 | 20을 크게 넘겨도 무의미 | 21번째부터는 커넥션을 기다린다 |

공식은 출발점이고 최종값은 부하 테스트로 정한다. 큐 대기 시간은 응답 시간에 더해지는데 모니터링에 잘 안 잡히니 큐 길이도 함께 본다.

### 풀이 무너지는 방식 — 고갈

한 작업이 락이나 외부 응답을 오래 기다리면 그 스레드는 묶인다. 이런 작업이 스레드 수만큼 쌓이면 풀의 스레드가 전부 기다리는 중이 되어, 무관한 요청도 스레드를 못 받아 멈춘다. 이것이 풀 고갈이다. 막는 방법은 외부 호출에 짧은 타임아웃을 두어 스레드를 빨리 돌려주고, 느린 호출은 별도 풀로 격리해(벌크헤드) 그 풀만 고갈되게 하는 것이다.

### 실무에서는

- Tomcat(Spring Boot 기본): 요청 처리 스레드 풀 `maxThreads` 기본 200, 동시에 받아 두는 연결 `maxConnections` 기본 8192, 그 위 OS 대기열 `acceptCount` 기본 100. 스레드 200개가 모두 바쁘면 연결은 받아 두되 처리는 기다린다. Spring Boot에서는 `server.tomcat.threads.max`로 바꾼다.
- `@Async`·`@Scheduled`의 기본 풀(Spring Boot `TaskExecutor`)은 core 8이고 큐가 설정 전까지 무한이다. 배치를 무심코 던지면 스레드는 8개에서 멈추고 큐만 자란다. 큐 크기와 거절 정책을 명시한다.
- DB 커넥션 풀(HikariCP)도 같은 발상이다 — 연결을 만들어 두고 돌려쓴다. 스레드 풀보다 커넥션 풀이 작으면 요청 스레드들이 커넥션을 기다리며 대기 상태가 되므로 두 풀의 크기는 함께 정한다.
- 가상 스레드(Java 21)는 "요청당 스레드 하나"를 풀 없이 다시 가능하게 한다. 그래도 뒷단 자원(커넥션, 외부 API 동시 호출 수)의 상한은 세마포어 같은 장치로 따로 둬야 한다.

### 면접 질문

#### 스레드 풀을 쓰는 이유는 무엇인가요?

스레드 생성·소멸 비용을 재사용으로 줄이고, 동시에 도는 스레드 수에 상한을 두어 요청이 폭주해도 서버가 무너지지 않게 하기 위해서입니다.
요청마다 스레드를 만들면 짧은 요청에서는 만드는 시간이 처리 시간보다 길 수 있고, 폭주 시 스레드가 무한정 늘어 메모리 부족이나 과도한 문맥 교환으로 서버 전체가 느려집니다.
Tomcat이 기본 200개 스레드 풀로 요청을 받고 넘치는 요청은 큐에서 기다리게 하는 게 대표적입니다. 한계는 큐 대기 시간이 응답 시간에 더해지고, 느린 작업이 스레드를 하나씩 묶어 풀 전체가 고갈될 수 있다는 점입니다.

- 꼬리: 큐가 가득 차면 어떻게 되나요? 거절 정책에는 무엇이 있나요?
- 꼬리: `maximumPoolSize`를 크게 줬는데 스레드가 core 개수에서 안 늘어납니다. 왜일까요?

#### 스레드 풀 크기는 어떻게 정하나요?

작업이 CPU 계산 위주인지 I/O 대기 위주인지에 따라 다릅니다. 계산 위주면 코어 수 근처, 대기 위주면 코어 수 × (1 + 대기 시간/계산 시간)에서 출발해 부하 테스트로 맞춥니다.
계산 위주에서 코어보다 많이 두면 CPU를 더 쓰는 게 아니라 문맥 교환만 늘고, 대기 위주에서는 기다리는 동안 코어가 비므로 더 둘 수 있기 때문입니다.
예를 들어 코어 8개, 요청 하나가 DB 대기 90ms에 계산 10ms라면 8 × (1 + 9) = 80 근처가 출발점입니다. 다만 DB 커넥션 풀이 20개면 80개 중 60개는 커넥션을 기다리므로, 뒷단 자원과 함께 정해야 합니다.

- 꼬리: 스레드 풀보다 커넥션 풀이 작으면 무슨 일이 생기나요?
- 꼬리: 가상 스레드를 쓰면 풀 크기 고민이 사라지나요?

#### 외부 API 하나가 느려졌을 뿐인데 서비스 전체가 멈췼습니다. 왜 그런가요, 어떻게 막나요?

요청 스레드 풀이 고갈됐기 때문입니다. 느린 API를 기다리는 요청이 스레드를 하나씩 붙들고 놓지 않아, 풀의 스레드가 전부 그 API 대기에 묶이면 무관한 요청도 스레드를 못 받아 멈춥니다.
막으려면 외부 호출에 짧은 타임아웃을 두어 스레드를 빨리 돌려주고, 느린 외부 호출은 별도 스레드 풀로 격리해(벌크헤드) 그 풀만 고갈되게 하며, 실패가 반복되면 서킷 브레이커로 호출 자체를 잠시 끊습니다.
예를 들어 Tomcat 200개 스레드 중 결제 API 호출을 20개짜리 별도 풀로 돌리면, 결제사가 멈춰도 나머지 180개는 조회 요청을 계속 처리합니다. 한계는 격리한 풀 안에서는 여전히 기다리므로 타임아웃이 함께 있어야 한다는 점입니다.

- 꼬리: 타임아웃은 연결 타임아웃과 읽기 타임아웃으로 왜 나누나요?
- 꼬리: 서킷 브레이커는 언제 다시 닫히나요?
