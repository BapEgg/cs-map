## 개념

디스크에 있던 프로그램을 운영체제가 메모리에 올리고, **자기만의 주소 공간과 상태 정보를 붙여 실행하는 단위**가 프로세스다.
운영체제는 프로세스마다 코드·데이터·힙·스택 메모리 영역을 잡아 주고, "지금 어디까지 실행했나, 레지스터 값은 뭐였나, 어떤 파일을 열었나"를 PCB라는 카드에 적어 관리한다.
CPU는 한 번에 한 프로세스만 실행하므로, 여러 프로세스는 실행 중 → 준비 → 대기 상태를 오가며 CPU를 번갈아 쓴다.

예를 들어 메모장을 두 번 실행하면 프로세스가 둘 생긴다. 한쪽에서 글을 쓰다가 프로그램이 죽어도 다른 쪽은 멀쩡하다.
두 프로세스는 같은 코드를 쓰지만 변수가 든 메모리는 완전히 따로여서, 한쪽 변수를 아무리 고쳐도 다른 쪽은 모른다.

비유하면 같은 레시피로 두 요리사가 각자 주방에서 요리하는 것이다. 레시피(프로그램)는 하나지만 주방(메모리)은 따로다.
다만 비유가 안 통하는 데가 있다 — 실제로는 주방(CPU)이 하나뿐이고, 요리사들이 아주 빠르게 번갈아 들어가 쓴다. "동시에"는 착시다.

## 왜 나왔나

CPU와 메모리는 하나인데 프로그램은 여러 개를 같이 돌리고 싶었다.
프로그램들이 메모리를 그냥 나눠 쓰면 한 프로그램이 다른 프로그램의 변수를 덮어쓰거나 통째로 죽일 수 있다.
그래서 운영체제가 프로그램마다 **독립된 주소 공간**을 주고, 실행 상태를 PCB에 적어 두었다가 번갈아 실행한다.
결국 프로그램 하나하나는 "컴퓨터를 나 혼자 쓴다"고 믿고 짜도 된다.

## 심화

### 내부 구조

- 상태 전이: 생성 → **준비**(CPU를 기다림) → **실행**(CPU 사용 중) → **대기**(I/O 같은 사건을 기다림) → 종료. 실행 중 타임 퀀텀이 끝나면 준비로, I/O를 요청하면 대기로 가고, I/O가 끝나면 다시 준비로 돌아온다. "대기"는 CPU를 기다리는 게 아니라 다른 사건을 기다리는 상태라는 점이 자주 헷갈린다.
- PCB에는 프로세스 번호, 상태, 레지스터 값과 프로그램 카운터, 페이지 테이블 위치, 열어 둔 파일 목록, 스케줄링 우선순위가 들어간다. 문맥 교환은 결국 PCB에 저장하고 PCB에서 복원하는 일이다.
- 만들기: 유닉스 계열은 `fork()`로 지금 프로세스를 복제한 뒤 `exec()`로 새 프로그램을 덮어씌운다. 복제 직후 두 프로세스는 같은 페이지를 공유하고, 한쪽이 쓰려는 순간에만 복사한다(Copy-on-Write). 그래서 큰 프로세스를 fork해도 순간적으로 메모리가 두 배가 되지 않는다.
- 프로세스끼리는 메모리가 분리돼 있어 데이터를 주고받으려면 파이프·소켓·공유 메모리·시그널 같은 별도 통로(IPC)를 써야 한다. 이 불편이 스레드가 나온 이유 중 하나다.
- 비용: 프로세스 생성은 주소 공간·페이지 테이블·PCB를 새로 만드는 일이라 스레드 생성보다 훨씬 무겁고, 프로세스 간 문맥 교환은 주소 공간이 바뀌어 캐시와 TLB가 비는 간접 비용까지 든다.

### 실제 활용

- 크롬은 탭마다 프로세스를 따로 둔다. 한 탭이 죽거나 뚫려도 다른 탭의 메모리에 손을 못 댄다. 안정성과 보안을 위해 스레드보다 무거운 프로세스를 일부러 고른 예다.
- Nginx·PostgreSQL은 요청·연결마다 스레드가 아니라 **프로세스**(worker)를 쓴다. 하나가 잘못돼도 나머지가 살아남고, 락 없이 각자 메모리를 쓴다는 장점이 있다. 대신 프로세스 간 데이터 공유가 어렵다.
- 백엔드에서 `java -jar app.jar`를 두 번 띄우면 프로세스 둘이고 JVM 힙도 둘이다. 같은 포트를 쓰려 하면 두 번째는 실패한다 — 포트는 운영체제가 프로세스 단위로 준다.
- 컨테이너(도커)는 새로운 실행 단위가 아니라 **격리된 프로세스**다. 리눅스 namespace·cgroup으로 프로세스가 보는 파일·네트워크·자원 한도를 가둔 것이다.

### 면접 질문

#### 프로그램과 프로세스의 차이는 무엇인가요?

프로그램은 디스크에 저장된 실행 파일이고, 프로세스는 그 프로그램이 메모리에 올라가 자기만의 주소 공간과 상태(PCB)를 갖고 실행되는 단위입니다.
프로그램은 정적이라 아무리 오래 있어도 아무 일도 하지 않고, 프로세스는 CPU를 받아 상태가 계속 바뀝니다.
예를 들어 메모장 하나를 두 번 열면 프로그램은 하나지만 프로세스는 둘이고, 두 프로세스는 메모리를 공유하지 않아 한쪽이 죽어도 다른 쪽은 영향이 없습니다.

- 꼬리: PCB에는 어떤 정보가 들어가고 언제 쓰이나요?

#### 프로세스의 상태 전이를 설명하고, "대기"와 "준비"의 차이를 말해 보세요.

준비·실행·대기 세 상태를 오갑니다. 준비는 CPU만 주면 바로 실행할 수 있는 상태, 실행은 CPU를 쓰는 중, 대기는 디스크 읽기나 네트워크 응답 같은 **사건**을 기다리는 상태입니다.
실행 중 타임 퀀텀이 끝나면 준비로 돌아가고, I/O를 요청하면 대기로 갔다가 I/O가 끝나면 준비로 옵니다. 대기 상태의 프로세스는 CPU를 줘도 할 일이 없으므로 스케줄러가 뽑지 않습니다.
DB 조회를 기다리는 웹 요청 스레드가 대기 상태인데, 이때 CPU는 다른 요청을 처리할 수 있습니다. 그래서 I/O가 많은 서버는 코어 수보다 많은 스레드를 둡니다.

- 꼬리: 대기 상태의 프로세스가 많으면 CPU 사용률은 어떻게 되나요?
- 꼬리: I/O 바운드와 CPU 바운드 작업은 스케줄링에서 어떻게 다르게 다루나요?

#### 웹 서버를 멀티프로세스로 만들 때와 멀티스레드로 만들 때 각각 어떤 상황에 유리한가요?

안정성과 격리가 중요하면 멀티프로세스, 데이터 공유와 생성 비용이 중요하면 멀티스레드가 유리합니다.
프로세스는 메모리가 분리돼 하나가 죽어도 나머지가 살고 락 없이 각자 메모리를 쓰지만, 만들기 무겁고 프로세스 간 데이터 공유에 IPC가 필요합니다. 스레드는 가볍고 공유가 쉽지만 한 스레드의 잘못이 프로세스 전체를 죽일 수 있고 동기화가 필요합니다.
Nginx·PostgreSQL이 워커 프로세스를 쓰고, Java 서버(Tomcat)가 스레드 풀을 쓰는 게 각각의 예입니다. 한계는 프로세스 방식도 결국 공유 캐시가 필요해지면 Redis 같은 외부 저장소를 써야 한다는 점입니다.
