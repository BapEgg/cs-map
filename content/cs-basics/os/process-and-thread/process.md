## 개념

프로그램은 디스크에 저장된 파일이다. 아이콘을 눌러 실행하면 운영체제가 그 파일의 내용을 메모리에 올리고, 변수를 둘 자리를 잡아 주고, 첫 줄부터 실행을 시작한다. 이렇게 **메모리에 올라가 실행되고 있는 프로그램 하나**를 프로세스라고 부른다. 프로그램이 레시피라면 프로세스는 지금 진행 중인 요리다.

메모장을 두 번 열면 프로그램 파일은 하나지만 프로세스는 둘이다. 운영체제가 각각에게 **따로** 메모리를 주기 때문에, 한쪽에서 쓴 글이 다른 쪽에 나타나지 않고, 한쪽이 오류로 꺼져도 다른 쪽은 멀쩡하다.

작은 예로 "파일의 줄 수를 세는 프로그램"을 실행해 보자.

- 시작 전: 디스크에 `count` 파일이 있고, 메모리에는 아무것도 없다.
- 실행: 운영체제가 `count`의 코드를 메모리에 올리고 변수 자리를 잡는다. 프로세스가 생겼다. CPU 코어가 첫 명령부터 실행한다.
- 파일 읽기 요청: 디스크는 CPU보다 훨씬 느리다. 데이터가 올 때까지 이 프로세스는 **기다리는 상태**가 되고, 코어는 그동안 다른 프로세스를 실행한다.
- 데이터 도착: 이 프로세스가 다시 코어를 받아 줄을 센다. `42`를 화면에 찍고 끝난다.
- 끝: 운영체제가 이 프로세스의 메모리를 거둬 간다.

프로세스가 여럿이면 어떻게 "동시에" 도는가. 코어가 하나뿐이면 코어는 한 순간에 한 프로세스만 실행하고, 몇 ms마다 다른 프로세스로 바꿔 가며 돌린다 — 사람 눈에는 동시로 보인다. 코어가 여럿이면 코어 수만큼은 진짜로 동시에 돈다. 어느 쪽이든 각 프로세스는 자기 메모리만 보고, "내가 컴퓨터를 혼자 쓴다"고 믿고 돌아간다.

## 왜 나왔나

컴퓨터 한 대에서 프로그램 여러 개를 같이 돌리고 싶은데, 메모리는 하나뿐이었다. 프로그램들이 메모리를 그냥 나눠 쓰면 한 프로그램의 실수로 다른 프로그램의 변수가 덮어써지거나 통째로 죽었다.

그래서 운영체제가 실행 중인 프로그램마다 **자기만의 메모리 구역과 이름표**를 붙여 관리하기로 했다. 이 관리 단위가 프로세스다. 그 덕에 프로그램을 짜는 사람은 다른 프로그램을 신경 쓰지 않고 자기 것만 생각하면 된다.

## 심화

### 언제 실행하고 언제 기다리는가

프로세스는 만들어져서 끝날 때까지 세 상태를 오간다. **준비**는 코어만 주면 바로 실행할 수 있는 상태, **실행**은 코어를 쓰고 있는 중, **대기**는 디스크 읽기나 네트워크 응답처럼 코어가 아닌 다른 **사건**을 기다리는 상태다.

```diagram
생성 -> 준비: 메모리에 올라감
준비 -> 실행: 스케줄러가 뽑음
실행 -> 준비: 할당 시간 끝(타이머)
실행 -> 대기: I/O 요청
대기 -> 준비: I/O 완료
실행 -> 종료: 끝남
```

자주 헷갈리는 것은 대기와 준비의 차이다. 준비 상태는 코어를 기다리고, 대기 상태는 코어가 아닌 사건을 기다린다. 대기 상태의 프로세스에게 코어를 줘도 할 일이 없으므로 스케줄러는 준비 큐에 있는 것만 뽑는다. 그래서 디스크·네트워크 대기가 많은 프로그램(I/O 바운드)은 코어를 거의 안 쓰고, 계산만 하는 프로그램(CPU 바운드)은 코어를 계속 쓴다. 이 구분이 뒤에 나오는 CPU 스케줄링과 스레드 풀 크기의 출발점이다.

### 멈춘 일을 어떻게 이어 하는가

코어가 프로세스 A를 실행하다 B로 바꾸면, A는 "어디까지 했는지"를 잃지 않아야 나중에 이어 할 수 있다. 코어 안에는 지금 계산 중인 값을 담는 작은 저장 공간인 레지스터가 있고, 그중 프로그램 카운터는 "다음에 실행할 명령의 위치"를 가리킨다. 이 값들이 프로세스가 진행 중인 자리 그 자체다.

운영체제는 프로세스마다 정보 카드를 하나씩 두는데, 이것이 PCB다. 프로세스 번호, 지금 상태(준비·실행·대기), 레지스터 값과 프로그램 카운터, 메모리가 어디에 잡혀 있는지(페이지 테이블 위치), 열어 둔 파일 목록, 스케줄링 우선순위가 들어간다. A를 멈출 때 레지스터 값을 A의 PCB에 적고, B의 PCB에서 값을 꺼내 레지스터에 넣으면 B가 멈췄던 자리부터 이어진다. 이 저장·복원이 문맥 교환이고, 비용은 그 장에서 따로 다룬다.

### 어떻게 새로 만드는가

유닉스 계열(리눅스·macOS)은 프로세스를 두 단계로 만든다. `fork()`는 지금 프로세스를 **복제**해 거의 같은 프로세스를 하나 더 만들고, `exec()`는 그 복제본의 내용을 **새 프로그램으로 갈아입힌다**. 셸에서 `ls`를 치면 셸이 자신을 fork한 뒤 자식에서 `ls`를 exec하는 식이다.

```c
pid_t pid = fork();            // 여기서 프로세스가 둘이 된다. 부모는 자식 번호를, 자식은 0을 받는다
if (pid == 0) {
    execlp("ls", "ls", "-l", NULL);   // 자식: ls 프로그램으로 갈아입는다
}
wait(NULL);                    // 부모: 자식이 끝나기를 기다린다
```

복제라고 해서 메모리를 통째로 베끼지는 않는다. 리눅스의 fork는 페이지 테이블만 복사하고 실제 메모리 페이지는 부모와 자식이 **공유**하다가, 어느 한쪽이 쓰려는 순간에 그 페이지만 복사한다(Copy-on-Write). 그래서 메모리를 수 GB 쓰는 프로세스를 fork해도 순간적으로 메모리가 두 배가 되지 않고, 바로 exec로 갈아입히면 복사는 거의 일어나지 않는다. 윈도우는 이 두 단계를 `CreateProcess` 하나로 처리한다 — 제품마다 다르니 "fork"를 일반 원리로 말하지 않는다.

### 어떻게 데이터를 주고받는가

프로세스끼리는 메모리가 분리돼 있어 변수를 그냥 읽을 수 없다. 운영체제가 마련해 준 통로를 써야 하는데, 이를 IPC라고 묶어 부른다.

| 통로 | 어떻게 | 어디에 쓰나 |
|---|---|---|
| 파이프 | 한쪽이 쓰면 다른 쪽이 읽는 바이트 흐름 | 셸의 `ls \| grep` |
| 소켓 | 파이프와 비슷하지만 다른 컴퓨터와도 됨 | 서버 ↔ DB, 서비스 간 HTTP |
| 공유 메모리 | 같은 메모리 페이지를 두 프로세스가 함께 매핑 | 대용량을 빠르게, 단 동기화는 직접 |
| 시그널 | "종료해라" 같은 번호 하나짜리 신호 | `kill`, Ctrl+C |

어느 통로든 스레드끼리 변수를 공유하는 것보다 번거롭고 느리다. 이 불편이 다음 장 스레드가 나온 이유의 절반이다(나머지 절반은 생성 비용).

### 실무에서는 어떻게 고르나

같은 일을 프로세스 여러 개로 나눌지, 프로세스 하나에 스레드 여러 개로 나눌지는 제품마다 다르게 정했다. 이유도 다르다.

| 제품 | 실행 단위 | 왜 그렇게 |
|---|---|---|
| 크롬 | 탭·사이트마다 프로세스 | 한 탭이 죽거나 뚫려도 다른 탭 메모리에 못 닿음(안정성·보안) |
| Nginx | master 1개 + worker 프로세스 몇 개(보통 코어 수). worker 하나가 이벤트 방식으로 연결 수천 개 처리 | 연결마다 단위를 만들지 않아 적은 메모리로 많은 연결 |
| PostgreSQL | 연결마다 백엔드 프로세스 1개를 fork | 한 연결의 문제가 다른 연결에 안 번짐. 대신 연결이 많으면 무거워 커넥션 풀을 앞에 둠 |
| Tomcat(Spring Boot) | 프로세스 1개 + 요청마다 스레드 풀의 스레드 | 요청들이 캐시·설정을 공유하고, 생성이 싸다 |
| 컨테이너(도커) | 새 단위가 아니라 **격리된 프로세스** | 리눅스 namespace·cgroup으로 보이는 파일·네트워크·자원 한도를 가둠 |

비용은 이렇게 갈린다. 프로세스 생성은 주소 공간·페이지 테이블·PCB를 새로 만드는 일이라 스레드 생성보다 무겁다(CoW 덕에 fork 자체는 페이지 테이블 복사 정도로 끝난다). 프로세스 간 문맥 교환은 주소 공간이 바뀌므로 스레드 간 전환보다 비싸다 — 얼마나 비싼지는 CPU가 주소 공간 태그(PCID)를 지원하는지 등 조건에 따라 다르며, 문맥 교환 장에서 다룬다. 메모리는 프로세스마다 따로 잡히므로 같은 코드를 100개 띄우면 100벌이다(공유 라이브러리와 CoW 페이지는 예외).

### 면접 질문

#### 프로그램과 프로세스의 차이는 무엇인가요?

프로그램은 디스크에 저장된 실행 파일이고, 프로세스는 그 프로그램이 메모리에 올라가 자기만의 메모리와 상태 정보(PCB)를 갖고 실행되는 단위입니다.
프로그램은 정적이라 아무 일도 하지 않고, 프로세스는 코어를 받아 상태가 계속 바뀝니다. 같은 프로그램을 두 번 실행하면 프로세스는 둘이고, 운영체제가 각각에 따로 메모리를 주므로 서로의 변수를 볼 수 없습니다.
예를 들어 메모장을 두 번 열면 한쪽이 죽어도 다른 쪽은 영향이 없습니다. 다만 두 프로세스가 같은 파일을 동시에 고치면 파일 쪽에서는 충돌이 나므로, "메모리가 분리됐다"가 "아무 영향이 없다"는 뜻은 아닙니다.

- 꼬리: 프로세스가 갖는 메모리 영역 네 가지를 설명해 보세요.
- 꼬리: PCB에는 어떤 정보가 들어가고 언제 쓰이나요?

#### 프로세스의 상태 전이를 설명하고, "대기"와 "준비"의 차이를 말해 보세요.

준비·실행·대기 세 상태를 오갑니다. 준비는 코어만 주면 바로 실행할 수 있는 상태, 실행은 코어를 쓰는 중, 대기는 디스크 읽기나 네트워크 응답 같은 **사건**을 기다리는 상태입니다.
실행 중 할당 시간이 끝나면 준비로 돌아가고, I/O를 요청하면 대기로 갔다가 I/O가 끝나면 준비로 옵니다. 대기 상태는 코어를 줘도 할 일이 없으므로 스케줄러가 뽑지 않습니다.
예를 들어 DB 조회를 기다리는 웹 요청 스레드는 대기 상태이고, 그동안 코어는 다른 요청을 처리합니다. 그래서 I/O가 많은 서버는 코어 수보다 많은 스레드를 둘 수 있습니다. 반대로 계산만 하는 작업은 대기가 없어 코어 수를 넘는 스레드가 이득이 없습니다.

- 꼬리: 대기 상태의 프로세스가 많으면 CPU 사용률은 어떻게 되나요?
- 꼬리: I/O 바운드와 CPU 바운드 작업은 스케줄링에서 어떻게 다르게 다루나요?

#### 웹 서버를 멀티프로세스로 만들 때와 멀티스레드로 만들 때 각각 어떤 상황에 유리한가요?

격리가 중요하면 멀티프로세스, 데이터 공유와 생성 비용이 중요하면 멀티스레드가 유리합니다.
프로세스는 메모리가 분리돼 하나가 죽어도 나머지가 살고 서로의 메모리를 망가뜨릴 수 없지만, 만들기 무겁고 데이터를 주고받으려면 IPC가 필요합니다. 스레드는 가볍고 공유가 쉽지만, 네이티브 코드에서 한 스레드가 메모리를 망가뜨리면 프로세스 전체가 영향을 받고 공유 데이터에 동기화가 필요합니다.
예를 들어 PostgreSQL은 연결마다 프로세스를 두어 격리를 택했고, Tomcat은 스레드 풀로 공유와 비용을 택했습니다. Nginx는 프로세스 몇 개만 두고 그 안에서 이벤트 방식으로 연결을 처리하는 세 번째 길입니다. 한계는 프로세스 방식도 결국 공유 캐시가 필요해지면 Redis 같은 외부 저장소를 써야 한다는 점입니다.
