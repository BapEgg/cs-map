## 개념

CPU는 한 번에 한 흐름만 실행한다. 다른 프로세스나 스레드로 넘어가려면 **지금 것의 상태를 저장하고 다음 것의 상태를 불러와야** 하는데, 이 일이 문맥 교환이다.
상태란 레지스터 값, 다음에 실행할 명령의 위치(프로그램 카운터), 스택 포인터 같은 것으로, 프로세스면 PCB에, 스레드면 TCB에 적어 둔다.
이 덕분에 CPU 하나로 여러 작업이 동시에 도는 것처럼 보이지만, 저장·복원 자체에 시간이 들고 바꾼 직후에는 캐시가 비어 한동안 느리다.

예를 들어 코어 하나에서 A와 B를 돌린다고 하자. A가 10ms를 쓰면 타이머 인터럽트가 걸린다.
운영체제가 A의 레지스터와 프로그램 카운터를 A의 PCB에 적고, B의 PCB에서 값을 꺼내 레지스터에 넣은 뒤 B가 멈췄던 명령부터 다시 실행한다.
사용자 눈에는 A와 B가 같이 도는 것처럼 보이고, A는 자기가 잠깐 멈췄다는 사실도 모른다.

비유하면 책 여러 권을 번갈아 읽을 때 책갈피를 꽂고 다른 책의 책갈피 자리를 펴는 것이다.
비유가 안 통하는 데는 **머릿속이 비워진다**는 점이다. 책은 펴면 바로 읽히지만, CPU는 캐시와 TLB에 있던 앞 작업의 데이터가 쓸모없어져 다시 채우는 동안 느리다.

## 왜 나왔나

CPU가 하나뿐인데 프로그램 여러 개를 동시에 돌리는 것처럼 보이고 싶었다.
한 프로그램이 끝날 때까지 기다리면 I/O를 기다리는 동안 CPU가 놀고, 화면은 멈춘다.
그래서 짧게 번갈아 실행하되, 멈춘 자리로 정확히 돌아올 수 있게 **상태를 저장하고 복원하는 절차**를 두었다.
다만 이 절차는 프로그램이 원래 하려던 일이 아닌 순수한 오버헤드라, 너무 자주 하면 일보다 전환에 시간을 더 쓴다.

## 심화

### 내부 구조

- 언제 일어나나: 타임 퀀텀이 끝나 타이머 인터럽트가 걸릴 때, 실행 중인 흐름이 I/O나 락을 기다리며 스스로 멈출 때, 더 높은 우선순위 흐름이 준비될 때. 첫 번째는 운영체제가 강제로(선점), 두 번째는 자발적으로 일어난다.
- 순서: 인터럽트나 시스템 호출로 커널 모드에 들어감 → 하드웨어가 레지스터 일부를 커널 스택에 저장 → 스케줄러가 다음 흐름을 고름 → 커널이 나머지 레지스터를 현재 PCB에 저장하고 다음 PCB에서 복원(스택 포인터도 바꿈) → 사용자 모드로 돌아가면 다음 흐름이 이어서 돈다. 프로세스가 바뀌면 페이지 테이블 기준 주소(x86의 CR3)도 바꾼다.
- 직접 비용: 레지스터 저장·복원과 커널 진입. 1996년 측정(lmbench, 200MHz P6)으로 약 6µs, 요즘 하드웨어는 그보다 한 자릿수 작다.
- 간접 비용이 더 크다: 전환 뒤 CPU 캐시·TLB·분기 예측기에 앞 작업의 내용이 남아 있어 새 작업은 한동안 캐시 미스를 내며 돈다. 프로세스 간 전환은 주소 공간이 바뀌어 TLB를 통째로 비우므로(태그가 있는 TLB는 예외) 스레드 간 전환보다 비싸다. "문맥 교환이 비싸다"는 말의 정체는 대부분 이 간접 비용이다.
- 같은 프로세스의 스레드끼리는 주소 공간이 그대로라 페이지 테이블을 안 바꾸고 캐시 내용도 일부 살아 있다. 그래서 스레드 전환이 프로세스 전환보다 싸다.

### 실제 활용

- 스레드를 코어 수보다 훨씬 많이 만들면 문맥 교환만 하다 처리량이 떨어진다. 그래서 스레드 풀 크기를 제한하고, CPU 계산 위주 작업은 코어 수 근처로 잡는다.
- `vmstat 1`의 `cs` 열이 초당 문맥 교환 횟수다. 수만~수십만이면 락 경합이나 과도한 스레드를 의심한다.
- 락을 짧게 잡는데 스레드들이 계속 잠들고 깨면 매번 문맥 교환이다. 그래서 아주 짧은 임계 구역에는 잠들지 않고 잠깐 도는 스핀락을 쓰기도 한다.
- Java 21 가상 스레드는 커널 문맥 교환 대신 JVM 안에서 스택을 바꿔 끼우므로 전환이 훨씬 싸다. I/O를 기다리는 요청이 많을 때 이득이 큰 이유다.

### 면접 질문

#### 문맥 교환은 언제 일어나고, 왜 비용이 드나요?

타임 퀀텀이 끝나 타이머 인터럽트가 걸리거나, I/O·락을 기다리며 스스로 멈추거나, 더 높은 우선순위 작업이 준비될 때 일어납니다.
비용은 두 가지입니다. 레지스터를 PCB에 저장하고 복원하는 직접 비용은 마이크로초 단위로 작지만, 전환 뒤 캐시·TLB에 앞 작업 내용이 남아 새 작업이 한동안 캐시 미스를 내는 간접 비용이 더 큽니다.
예를 들어 코어 4개 서버에 CPU 계산 스레드를 400개 두면 각 스레드가 짧게 돌고 계속 밀려나 캐시를 매번 다시 채우므로, 스레드 4~8개일 때보다 처리량이 떨어질 수 있습니다.

- 꼬리: 스레드 간 문맥 교환이 프로세스 간보다 빠른 이유는?
- 꼬리: PCB에는 어떤 정보가 들어 있나요?

#### 스레드 간 문맥 교환이 프로세스 간 문맥 교환보다 싼 이유는 무엇인가요?

같은 프로세스의 스레드는 주소 공간을 공유하므로 페이지 테이블을 바꾸지 않고, 그래서 TLB를 비우지 않아도 되며 캐시에 있던 공유 데이터도 그대로 쓸 수 있기 때문입니다.
프로세스 간 전환은 페이지 테이블 기준 주소를 바꾸면서 TLB가 무효화되고, 새 프로세스의 코드·데이터는 캐시에 없으므로 한동안 메모리까지 내려가며 돕니다.
다만 스레드 전환도 레지스터 저장·복원과 커널 진입은 똑같이 들고, 두 스레드가 전혀 다른 데이터를 만지면 캐시 이득도 줄어듭니다. "싸다"는 것이지 "공짜"는 아닙니다.

- 꼬리: TLB가 무효화되면 무슨 일이 생기나요?
- 꼬리: 가상 스레드는 이 비용을 어떻게 피하나요?

#### 서버의 CPU 사용률은 낮은데 응답이 느립니다. 문맥 교환과 관련해 어디를 보겠습니까?

먼저 초당 문맥 교환 횟수(`vmstat`의 cs)와 락 경합을 봅니다. CPU가 놀면서 느리다면 스레드들이 일을 하는 게 아니라 락이나 I/O를 기다리며 잠들고 깨기를 반복하고 있을 가능성이 큽니다.
문맥 교환이 초당 수십만 회로 높다면 스레드 수가 과하거나 락 구간이 짧고 자주 걸리는 것이고, 낮다면 스레드들이 DB·외부 API 응답을 오래 기다리는 것이라 커넥션 풀 크기나 외부 지연을 봅니다.
예를 들어 Tomcat 스레드 200개가 커넥션 풀 10개를 기다리면 190개는 락 대기 상태라 CPU는 놀고 응답은 느립니다. 이때는 스레드를 늘리는 게 아니라 병목인 풀과 쿼리를 손봐야 합니다.

- 꼬리: 스레드 덤프에서 `BLOCKED`와 `WAITING` 상태는 무엇을 뜻하나요?
- 꼬리: 스핀락이 잠드는 락보다 나은 상황은?
