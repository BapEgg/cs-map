## 개념

코어 하나는 한 순간에 한 실행 줄기만 실행한다. 그런데 프로세스나 스레드는 코어보다 많다. 그래서 코어는 A를 잠깐 돌리고, B로 바꾸고, 다시 A로 돌아온다. 이때 **A가 어디까지 했는지를 저장해 두고, B가 어디까지 했는지를 다시 꺼내 오는 일**이 문맥 교환이다.

"어디까지 했는지"는 코어 안의 레지스터에 들어 있다. 계산 중인 값들과, 다음에 실행할 명령의 위치(프로그램 카운터)다. 이걸 A의 정보 카드(PCB, 스레드면 TCB)에 적어 두고, B의 카드에서 값을 꺼내 레지스터에 채우면 B는 멈췄던 그 명령부터 이어 간다. A는 자기가 멈췄다는 사실을 모른다.

코어 하나에서 A와 B를 돌리는 상황을 따라가 보자.

- 시작: A가 실행 중이다. 레지스터에는 A의 계산값과 A의 다음 명령 위치가 있다.
- 10ms 뒤: 타이머가 인터럽트를 걸어 운영체제를 깨운다. 운영체제는 레지스터 값을 A의 카드에 적고, B의 카드에서 값을 꺼내 레지스터에 넣는다.
- 결과: 코어가 B의 다음 명령부터 실행한다. 사용자 눈에는 A와 B가 함께 도는 것처럼 보인다.

문맥 교환은 프로그램이 원래 하려던 일이 아니다. 저장하고 복원하는 시간은 순수한 덤이고, 바꾼 직후에는 코어의 캐시에 앞 작업의 데이터가 남아 있어 새 작업이 자기 데이터를 다시 가져오느라 한동안 느리다. 그래서 너무 자주 바꾸면 일보다 바꾸는 데 시간을 더 쓴다.

## 왜 나왔나

코어 하나로 프로그램 여러 개를 함께 돌리는 것처럼 보이고 싶었다. 한 프로그램이 끝날 때까지 기다리면 그 프로그램이 디스크를 기다리는 동안 코어가 놀고, 화면은 멈춘다.

그래서 짧게 번갈아 실행하기로 했는데, 그러려면 **멈춘 자리로 정확히 돌아올 수 있어야** 했다. 진행 상태를 저장하고 복원하는 절차가 그 답이다. 코어가 여럿이 된 지금도 코어 수보다 실행 줄기가 많으면 같은 절차가 필요하다.

## 확인 질문

- 설명해 보기: 문맥 교환 때 저장하는 "상태"란 구체적으로 무엇인가요?
  답: 코어 레지스터의 값들 — 계산 중인 값과 다음에 실행할 명령의 위치(프로그램 카운터), 스택 포인터. 프로세스의 PCB(스레드는 TCB)에 적는다.
- 다음 상태 예측: A가 실행 중에 파일 읽기를 요청했습니다. 문맥 교환이 일어날까요?
  답: 일어난다. A는 데이터를 기다리는 대기 상태가 되어 코어를 내놓고, 운영체제가 준비 상태의 다른 줄기를 골라 복원한다. 타이머가 아니어도 스스로 멈추면 교환이 생긴다.
- 다음 상태 예측: 같은 프로세스의 스레드 A→B로 바꿀 때와 다른 프로세스 A→C로 바꿀 때, 저장·복원할 레지스터의 양이 다른가요?
  답: 레지스터 저장·복원은 같다. 다른 것은 주소 공간이다 — 프로세스가 바뀌면 페이지 테이블을 가리키는 값도 바꾸고, 그 여파로 TLB·캐시 쪽 비용이 더 든다.

## 심화

### 언제 일어나는가

문맥 교환은 세 경우에 일어난다. 실행 중인 줄기가 할당 시간을 다 써서 **타이머 인터럽트**가 걸릴 때(운영체제가 강제로 뺏는 선점), 줄기가 I/O나 락을 기다리며 **스스로 멈출 때**, 더 높은 우선순위의 줄기가 준비되어 스케줄러가 바꿀 때다. 어느 경우든 운영체제 코드(커널)가 코어를 잡은 상태에서 일어난다 — 사용자 프로그램이 직접 레지스터를 바꿔 끼우는 게 아니다.

### 무슨 순서로 일어나는가

1. 인터럽트나 시스템 호출로 커널 모드에 들어간다. 하드웨어가 레지스터 일부(프로그램 카운터 등)를 그 프로세스의 커널 스택에 밀어 넣는다.
2. 스케줄러가 다음에 돌릴 줄기를 고른다.
3. 커널이 나머지 레지스터를 현재 PCB에 저장하고, 다음 PCB의 값을 레지스터에 복원한다. 스택 포인터도 다음 줄기의 커널 스택으로 바꾼다.
4. 프로세스가 바뀌었다면 페이지 테이블의 기준 주소(x86의 CR3)를 다음 프로세스 것으로 바꾼다. 같은 프로세스의 스레드끼리면 이 단계가 없다.
5. 사용자 모드로 돌아간다. 다음 줄기가 멈췄던 명령부터 실행된다.

### 비용은 어디서 오는가

**직접 비용**은 레지스터 저장·복원과 커널 진입·복귀다. 1996년 200MHz P6에서 lmbench로 잰 값이 약 6µs였고, 현대 하드웨어는 그보다 한 자릿수 작다(OSTEP 6장). 이것만 보면 싸다.

**간접 비용**이 대개 더 크다. 코어의 캐시·TLB·분기 예측기에는 앞 작업의 내용이 차 있다. 새 작업은 자기 데이터가 캐시에 없어 처음 한동안 메모리까지 내려가며 돈다. 이 비용은 두 작업이 만지는 데이터가 얼마나 다른지, 캐시가 얼마나 큰지에 따라 달라서 정해진 숫자가 없다.

TLB는 조건에 따라 다르다. 주소 변환 캐시인 TLB는 프로세스가 바뀌면 앞 프로세스의 변환 결과가 새 프로세스에는 틀린 값이 된다. 하드웨어가 TLB 항목마다 "어느 주소 공간 것인지" 표를 붙일 수 없으면 운영체제가 **전부 비운다**. 표를 붙일 수 있으면(x86의 PCID, ARM의 ASID) 비우지 않고 표만 바꾼다 — 리눅스는 4.14부터 x86-64에서 PCID를 쓴다. 그러니 "프로세스 전환 = TLB 플러시"는 그런 하드웨어·설정에서만 맞는 말이다. 같은 프로세스의 스레드 사이에서는 주소 공간이 같아 어느 경우든 TLB를 건드리지 않는다.

### 스레드 전환이 프로세스 전환보다 싼 이유

레지스터 저장·복원과 커널 진입은 둘이 같다. 차이는 주소 공간에서 온다. 같은 프로세스의 스레드는 페이지 테이블을 안 바꾸므로 TLB를 그대로 쓰고, 두 스레드가 공유하는 데이터(힙의 캐시 객체 등)는 CPU 캐시에도 살아 있을 수 있다. 다만 두 스레드가 전혀 다른 데이터를 만지면 캐시 이득은 줄어든다. "싸다"는 것이지 "비용이 없다"는 것은 아니다.

### 실무에서는

- 스레드를 코어 수보다 훨씬 많이 두면 CPU 계산 작업은 문맥 교환과 캐시 미스만 늘어 처리량이 떨어질 수 있다. 그래서 스레드 풀로 상한을 두고 CPU 위주 작업은 코어 수 근처로 잡는다.
- 리눅스 `vmstat 1`의 `cs` 열이 초당 문맥 교환 횟수다. 평소보다 급증했다면 락 경합(잠들고 깨기 반복)이나 과도한 스레드를 의심한다. 절대 기준값은 없다 — 서버마다 평소 수치와 비교한다.
- 임계 구역이 아주 짧을 때는 잠들고 깨는 문맥 교환보다 잠깐 도는 스핀락이 싸다. 뮤텍스 장에서 다룬다.
- Java 21 가상 스레드는 커널 문맥 교환 대신 JVM 안에서 스택을 바꿔 끼우므로 전환이 훨씬 싸다. I/O 대기가 많은 요청이 수만 개일 때 이득이 큰 이유다.

### 면접 질문

#### 문맥 교환은 언제 일어나고, 왜 비용이 드나요?

할당 시간이 끝나 타이머 인터럽트가 걸리거나, I/O·락을 기다리며 스스로 멈추거나, 더 높은 우선순위 작업이 준비될 때 일어납니다.
비용은 두 가지입니다. 레지스터를 PCB에 저장하고 복원하는 직접 비용은 마이크로초 아래로 작지만, 전환 뒤 캐시·TLB에 앞 작업 내용이 남아 새 작업이 한동안 캐시 미스를 내는 간접 비용이 보통 더 큽니다.
예를 들어 코어 4개 서버에 CPU 계산 스레드를 400개 두면 각 스레드가 짧게 돌고 계속 밀려나 캐시를 매번 다시 채우므로, 스레드 4~8개일 때보다 처리량이 떨어질 수 있습니다. 다만 간접 비용의 크기는 작업의 데이터 크기와 하드웨어에 따라 달라 정해진 숫자는 없습니다.

- 꼬리: 스레드 간 문맥 교환이 프로세스 간보다 싼 이유는?
- 꼬리: PCB에는 어떤 정보가 들어 있나요?

#### 스레드 간 문맥 교환이 프로세스 간 문맥 교환보다 싼 이유는 무엇인가요?

같은 프로세스의 스레드는 주소 공간을 공유하므로 페이지 테이블을 바꾸지 않고, 그래서 TLB를 그대로 쓰며 공유 데이터가 캐시에 살아 있을 수 있기 때문입니다.
프로세스 간 전환은 페이지 테이블 기준 주소를 바꿔야 하고, TLB에 주소 공간 표(PCID·ASID)를 붙일 수 없는 하드웨어에서는 TLB를 전부 비웁니다. 표를 붙일 수 있어도 새 프로세스의 코드·데이터는 캐시에 없으므로 한동안 메모리까지 내려가며 돕니다.
다만 스레드 전환도 레지스터 저장·복원과 커널 진입은 똑같이 들고, 두 스레드가 전혀 다른 데이터를 만지면 캐시 이득도 줄어듭니다. "싸다"는 것이지 "비용이 없다"는 뜻은 아닙니다.

#### 서버의 CPU 사용률은 낮은데 응답이 느립니다. 문맥 교환과 관련해 어디를 보겠습니까?

먼저 초당 문맥 교환 횟수(`vmstat`의 cs)와 스레드 덤프를 봅니다. CPU가 놀면서 느리다면 스레드들이 일을 하는 게 아니라 락이나 I/O를 기다리며 잠들고 깨기를 반복하고 있을 가능성이 큽니다.
문맥 교환이 평소보다 크게 늘었다면 스레드 수가 과하거나 락 구간이 짧고 자주 걸리는 것이고, 늘지 않았다면 스레드들이 DB·외부 API 응답을 오래 기다리는 것이라 커넥션 풀 크기나 외부 지연을 봅니다.
예를 들어 Tomcat 스레드 200개가 커넥션 풀 10개를 기다리면 190개는 대기 상태라 CPU는 놀고 응답은 느립니다. 이때는 스레드를 늘리는 게 아니라 병목인 풀과 쿼리를 손봐야 합니다.
