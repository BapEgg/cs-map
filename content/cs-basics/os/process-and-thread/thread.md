## 개념

프로세스 하나는 보통 한 줄기로 실행된다 — 첫 명령부터 차례로. 스레드는 **그 프로세스 안에서 실행 줄기를 여러 개로 늘린 것**이다. 프로세스가 주방이라면 스레드는 그 주방에서 일하는 요리사 한 명 한 명이다. 요리사가 둘이면 한 명이 국을 끓이는 동안 다른 한 명이 채소를 썬다.

같은 프로세스의 스레드들은 **같은 메모리를 본다**. 프로그램 코드, 전역 변수, 힙에 만든 객체를 모두 함께 쓴다. 각자 따로 갖는 것은 함수 호출을 쌓는 자기 스택과, 지금 어느 명령을 실행 중인지 같은 진행 위치다. 그래서 스레드끼리 값을 주고받는 건 같은 변수를 읽고 쓰기만 하면 되지만, 바로 그 이유로 같은 변수를 동시에 고치면 결과가 꼬인다.

웹 서버가 요청 A와 B를 거의 동시에 받는 상황을 따라가 보자.

- 시작: 서버 프로세스 하나에 스레드 1과 2가 있다. 둘 다 힙에 있는 설정 객체와 캐시를 본다.
- 진행: 스레드 1이 A를, 스레드 2가 B를 맡는다. 각자의 지역 변수(요청 내용, 중간 계산)는 각자 스택에 둔다. A 처리 중 DB 응답을 기다리게 되면 스레드 1은 멈추지만 스레드 2는 계속 B를 처리한다.
- 결과: A와 B가 겹쳐 처리된다. 프로세스를 둘 만들 필요도, 캐시를 복사할 필요도 없었다.

코어가 하나면 두 스레드도 프로세스처럼 번갈아 돌고, 코어가 여럿이면 진짜 동시에 돈다. 어느 쪽이든 "같은 메모리를 여러 줄기가 만진다"는 점은 같다.

## 왜 나왔나

프로세스는 메모리가 통째로 따로여서, 하나 더 만들기도 무겁고 프로세스끼리 데이터를 주고받으려면 별도 통로(IPC)를 거쳐야 했다. 한 프로그램 안에서 "파일을 내려받으면서 화면도 그리기"처럼 여러 일을 겹쳐 하고 싶을 때마다 프로세스를 만드는 건 비용이 컸다.

그래서 메모리는 하나로 두고 **실행 줄기만 여러 개** 두는 스레드가 나왔다. 만들기 싸고 데이터 공유가 바로 된다. 대신 공유가 바로 되는 만큼, 같은 데이터를 동시에 고치는 문제는 프로그래머가 직접 막아야 한다 — 그 방법이 다음 장 동시성과 동기화다.

## 확인 질문

- 설명해 보기: 같은 프로세스의 스레드 둘이 공유하는 것과 따로 갖는 것을 각각 하나씩 말해 보세요.
  답: 공유하는 것은 힙(객체)·전역 변수·코드, 따로 갖는 것은 스택(지역 변수)과 진행 위치다.
- 다음 상태 예측: 스레드 1이 힙의 `config.timeout`을 30으로 바꿨습니다. 스레드 2가 읽으면 얼마인가요?
  답: 30이다. 힙은 공유되므로 한 스레드의 변경이 다른 스레드에게 보인다(정확히 언제 보이는지는 심화의 가시성 문제).
- 다음 상태 예측: 스레드 1이 함수 안에서 지역 변수 `n = 5`를 만들었습니다. 스레드 2가 같은 함수를 실행하면 스레드 1의 `n`이 보이나요?
  답: 안 보인다. 지역 변수는 각자의 스택에 있어 스레드 2는 자기 `n`을 새로 만든다.

## 심화

### 무엇을 공유하고 무엇을 따로 갖는가

| | 공유 | 각자 |
|---|---|---|
| 메모리 | 코드, 데이터(전역 변수), 힙 | 스택 |
| 실행 상태 | — | 레지스터, 프로그램 카운터, 스케줄링 상태 |
| 운영체제 자원 | 열어 둔 파일, 페이지 테이블, 시그널 처리기 | 스레드 번호 |

스택이 따로인 이유는 함수 호출 깊이가 스레드마다 다르기 때문이다. 스레드 1이 `a()` 안의 `b()`를 실행 중일 때 스레드 2는 `c()`만 실행 중일 수 있다. 한 스택을 나눠 쓰면 서로의 return 주소를 덮어쓴다.

스택 크기는 만들 때 정해지고 나중에 늘지 않는다. 리눅스 pthread의 기본은 `ulimit -s`(RLIMIT_STACK) 값으로 배포판 대부분이 8MB, 무제한으로 설정돼 있으면 2MB(x86-64)다. JVM 플랫폼 스레드는 64비트 리눅스에서 기본 1MB(`-Xss`)다. 이 크기는 **예약**이라 실제로 다 쓰지 않으면 물리 메모리를 차지하지 않지만, 스레드를 수천 개 만들면 가상 주소 공간과 커널 자원이 그만큼 든다.

### 운영체제는 스레드를 어떻게 만드는가

리눅스는 프로세스와 스레드를 같은 시스템 호출 `clone()`으로 만든다. 주소 공간을 공유하라는 플래그(`CLONE_VM`), 열어 둔 파일을 공유하라는 플래그(`CLONE_FILES`) 등을 켜면 스레드가 되고, 다 끄면 fork와 같은 프로세스가 된다. 커널 입장에서 둘은 다 "실행 단위(task)"이고, **무엇을 공유하느냐**만 다르다. 그래서 "스레드는 가벼운 프로세스"라는 말이 리눅스에서는 비유가 아니라 구현이다.

스레드를 누가 관리하느냐에 따라 모델이 갈린다. 지금의 리눅스·윈도우·JVM 플랫폼 스레드는 프로그램의 스레드 하나에 커널 스레드 하나를 붙이는 **1:1 모델**이다. 커널이 직접 스케줄링하므로 한 스레드가 I/O로 멈춰도 다른 스레드는 다른 코어에서 돈다. 반대로 커널 스레드 몇 개 위에서 런타임이 수많은 흐름을 직접 돌리는 **M:N 모델**(고루틴, Java 21 가상 스레드)은 만들기 훨씬 싸지만, 런타임이 스케줄링을 맡아야 하고 커널이 모르는 흐름이라 디버깅 도구가 따로 필요하다.

### 한 스레드의 잘못은 어디까지 번지는가

"스레드 하나가 죽으면 프로세스가 죽는다"는 말은 절반만 맞다. 언어와 잘못의 종류에 따라 다르다.

| 상황 | 결과 |
|---|---|
| C/C++ 등 네이티브 코드에서 한 스레드가 잘못된 주소를 건드림(세그폴트) | 운영체제가 **프로세스 전체**에 시그널을 보내 종료. 메모리가 공유돼 다른 스레드도 이미 망가졌을 수 있어서 |
| Java에서 한 스레드가 처리되지 않은 예외를 냄 | **그 스레드만** 종료(`UncaughtExceptionHandler` 호출 후). 다른 스레드와 프로세스는 계속 돈다 |
| Java에서 non-daemon 스레드가 모두 끝남 | JVM이 종료 절차 시작 — 스레드가 죽어서가 아니라 남은 일이 없어서 |
| 한 스레드가 공유 객체를 잘못된 상태로 두고 죽음 | 프로세스는 살아 있지만 다른 스레드가 깨진 데이터를 읽음. 죽는 것보다 찾기 어렵다 |

Tomcat에서 요청 하나가 예외로 실패해도 서버가 계속 도는 이유가 두 번째 줄이다. 반대로 JNI로 부른 네이티브 코드가 메모리를 망가뜨리면 첫 줄이라 JVM 전체가 죽는다.

### 실무에서 스레드는 어디에 있나

- Tomcat(Spring Boot 기본 서버)은 요청마다 스레드를 새로 만들지 않고 스레드 풀(기본 최대 200)에서 하나를 꺼내 맡긴다. 요청이 DB를 기다리는 동안 그 스레드는 대기 상태다.
- Spring 싱글턴 빈은 모든 요청 스레드가 공유하는 힙 객체다. 빈의 **필드**에 요청별 값을 두면 요청 A의 값을 요청 B가 읽는다. 요청별 값은 메서드 매개변수·지역 변수(스택)나 `ThreadLocal`에 둔다.
- Node.js는 JS 코드를 스레드 하나(이벤트 루프)로 돌리되, 파일 I/O·암호화 같은 무거운 일은 내부 스레드 풀(libuv, 기본 4개)에 맡긴다. "싱글 스레드"는 JS 실행 줄기가 하나라는 뜻이다.
- Java 21 가상 스레드는 커널 스레드에 1:1로 묶이지 않아 수십만 개를 만들 수 있다. I/O 대기가 많은 서버에서 "요청당 스레드 하나"를 풀 없이 다시 쓸 수 있게 한다. CPU 계산이 병목이면 이득이 없고, `synchronized` 블록 안에서 I/O를 하면 커널 스레드에 고정되는 제약이 있다(JDK 21 기준, JDK 24에서 완화).

### 면접 질문

#### 프로세스와 스레드의 차이를 메모리 구조 관점에서 설명해 주세요.

프로세스는 코드·데이터·힙·스택을 모두 자기만의 주소 공간에 갖고, 스레드는 그중 코드·데이터·힙을 같은 프로세스의 스레드들과 공유하며 스택과 레지스터만 따로 가집니다.
공유하기 때문에 스레드는 만들고 전환하는 비용이 작고 데이터 교환이 변수 접근만으로 되지만, 같은 데이터를 동시에 고치면 경쟁 상태가 생겨 동기화가 필요합니다.
예를 들어 스레드 두 개가 힙의 같은 `count`를 1씩 올리면 결과가 2가 아니라 1이 될 수 있지만, 프로세스 두 개라면 각자의 `count`라 겹치지 않습니다. 대신 프로세스끼리 값을 합치려면 파이프나 소켓 같은 IPC가 필요합니다.

#### 스레드를 많이 만들수록 서버가 빨라지나요?

아닙니다. 병목이 어디인지에 따라 다릅니다. CPU 계산이 많은 작업은 코어 수를 넘는 스레드가 CPU를 더 주는 게 아니라 **나눠 쓰게** 하므로, 문맥 교환 비용만 늘어납니다.
I/O 대기가 많은 작업은 대기 중인 스레드가 코어를 안 쓰므로 코어 수보다 많이 두는 게 이득이지만, 스레드마다 스택 예약과 커널 자원이 들고, DB 커넥션 같은 뒷단 자원도 같이 늘어나야 의미가 있습니다.
그래서 스레드 수는 스레드 풀로 상한을 두고 부하 테스트로 정합니다. I/O 대기가 압도적이라면 가상 스레드나 비동기 I/O가 대안입니다.

- 꼬리: 가상 스레드는 플랫폼 스레드와 무엇이 다른가요?

#### Spring 싱글턴 빈은 여러 요청이 동시에 쓰는데 어떻게 안전한가요?

빈은 하나지만 각 요청은 다른 스레드에서 처리되고, 메서드의 지역 변수는 그 스레드의 스택에 있어 요청끼리 섞이지 않기 때문에 안전합니다.
안전하지 않은 경우는 빈의 **필드**에 요청별 상태를 두는 때입니다. 필드는 힙에 있어 모든 스레드가 공유하므로 요청 A가 넣은 값을 요청 B가 읽습니다.
그래서 서비스·리포지토리 빈은 상태 없이 만들고, 요청별 값은 매개변수로 넘기거나 `ThreadLocal`(Spring Security의 `SecurityContextHolder`가 이 방식)에 둡니다. 가상 스레드에서는 `ThreadLocal`이 스레드 수만큼 늘어나므로 `ScopedValue` 같은 대안을 검토합니다.
