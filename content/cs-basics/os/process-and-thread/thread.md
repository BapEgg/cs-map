## 개념

스레드는 **프로세스 안에서 도는 실행 흐름**이다. 프로세스 하나에 스레드가 여럿이면 같은 프로그램의 여러 부분이 동시에 진행된다.
같은 프로세스의 스레드들은 코드·데이터·힙을 **공유**하고, 함수 호출을 쌓는 스택과 레지스터(프로그램 카운터 포함)만 **각자** 가진다.
그래서 스레드끼리는 변수 하나를 같이 읽고 쓰는 게 그냥 되지만, 바로 그 때문에 같은 변수를 동시에 고치면 결과가 꼬인다.

예를 들어 웹 서버가 요청 A와 B를 동시에 받았다고 하자. 스레드 1이 A를, 스레드 2가 B를 맡는다.
둘 다 같은 설정값(데이터 영역)과 같은 캐시 객체(힙)를 읽고, 각자의 지역 변수는 각자 스택에 둔다.
A가 DB 응답을 기다리는 동안 스레드 1은 멈추지만 스레드 2는 계속 B를 처리한다 — 결과적으로 두 요청이 겹쳐 처리된다.

비유하면 한 주방에서 요리사 여럿이 같은 냉장고(힙)의 재료를 쓰며 각자 도마(스택)만 따로 쓰는 것이다.
비유가 안 통하는 데는, 진짜 주방에선 두 사람이 같은 재료를 동시에 집으면 서로 보이지만 스레드는 **서로가 안 보인다**는 점이다. 그래서 경쟁 상태가 생긴다.

## 왜 나왔나

프로세스는 주소 공간이 통째로 따로라서, 만들기도 무겁고 프로세스끼리 데이터를 주고받으려면 별도 통로(IPC)를 거쳐야 했다.
한 프로그램 안에서 "파일 다운로드하면서 화면도 그리기"처럼 여러 일을 겹쳐 하고 싶은데, 그때마다 프로세스를 만들기엔 비용이 컸다.
그래서 주소 공간은 하나로 두고 **실행 흐름만 여러 개** 두는 스레드가 나왔다. 만들기 싸고 데이터 공유에 별도 통로가 필요 없다 — 같은 변수를 그냥 읽고 쓴다.
대신 공유가 공짜인 만큼 같은 데이터를 동시에 고치는 문제를 프로그래머가 직접 막아야 한다.

## 심화

### 내부 구조

#### 공유하는 것과 각자 갖는 것

공유하는 것: 코드, 데이터(전역 변수), 힙, 열어 둔 파일, 페이지 테이블. 각자 갖는 것: 스택, 레지스터, 프로그램 카운터, 스케줄링 상태. 스레드마다 스택이 따로인 이유는 함수 호출 깊이가 스레드마다 다르기 때문이다 — 한 스택을 나눠 쓰면 return 주소가 뒤섞인다.

#### 스택 크기

스택 크기는 미리 정해진다. 리눅스 pthread의 기본 스택은 `ulimit -s`(RLIMIT_STACK) 값으로 보통 8MB(무제한이면 대부분 2MB), JVM 스레드는 64비트 리눅스에서 기본 1MB(`-Xss`)다. 스레드를 수천 개 만들면 스택 예약 공간만으로 가상 메모리가 수 GB가 된다.

#### 리눅스의 `clone()`

리눅스에서는 프로세스와 스레드를 같은 시스템 호출 `clone()`으로 만든다. 주소 공간·파일 테이블을 **공유하는 플래그**를 켜면 스레드, 끄면 프로세스다. 커널 입장에선 둘 다 "실행 단위(task)"이고 무엇을 공유하느냐만 다르다.

#### 커널 스레드와 사용자 스레드

요즘 리눅스·윈도우·JVM(플랫폼 스레드)은 사용자 스레드 하나에 커널 스레드 하나를 붙이는 1:1 모델이다. 커널이 스케줄링하므로 한 스레드가 I/O로 멈춰도 다른 스레드는 돈다. 반대로 사용자 공간에서만 여러 흐름을 돌리는 방식(고루틴, Java 21의 가상 스레드)은 M:N으로, 만들기 훨씬 싸지만 런타임이 직접 스케줄링해야 한다.

#### 한 스레드의 오류가 미치는 범위

한 스레드가 배열 범위를 벗어나 메모리를 망가뜨리거나 잡히지 않는 오류로 죽으면 **프로세스 전체**가 죽는다. 스레드 사이에 격리가 없는 대가다.
### 실제 활용

- Tomcat(Spring Boot 기본 서버)은 요청마다 스레드를 새로 만들지 않고 스레드 풀에서 하나를 꺼내 맡긴다. 기본 최대 200개. 요청 처리 중 DB를 기다리는 동안 그 스레드는 대기 상태다.
- 스레드가 힙을 공유하기 때문에, Spring의 싱글턴 빈에 요청별 데이터를 필드로 두면 다른 요청의 값이 섞인다. 요청별 값은 메서드의 지역 변수(스택)나 `ThreadLocal`에 둔다.
- Node.js는 JS 코드를 단일 스레드(이벤트 루프)로 돌리되, 파일 I/O 같은 무거운 일은 내부 스레드 풀(libuv)에 맡긴다. "싱글 스레드"라는 말은 JS 실행 흐름이 하나라는 뜻이지 프로세스에 스레드가 하나라는 뜻이 아니다.
- Java 21 가상 스레드는 커널 스레드에 1:1로 묶이지 않아 수십만 개를 만들 수 있다. I/O 대기가 많은 서버에서 "요청당 스레드 하나" 모델을 스레드 풀 없이 다시 쓸 수 있게 한다. CPU 계산이 많은 일에는 이득이 없다.

### 면접 질문

#### 프로세스와 스레드의 차이를 메모리 구조 관점에서 설명해 주세요.

프로세스는 코드·데이터·힙·스택을 모두 자기만의 주소 공간에 갖고, 스레드는 그중 코드·데이터·힙을 같은 프로세스의 스레드들과 공유하며 스택과 레지스터만 따로 가집니다.
공유하기 때문에 스레드는 만들고 전환하는 비용이 작고 데이터 교환이 변수 접근만으로 되지만, 같은 데이터를 동시에 고치면 경쟁 상태가 생겨 동기화가 필요합니다.
예를 들어 스레드 두 개가 같은 `count` 변수를 1씩 올리면 힙의 같은 자리를 건드리므로 결과가 2가 아니라 1이 될 수 있지만, 프로세스 두 개라면 각자의 `count`라 애초에 겹치지 않습니다. 대신 프로세스끼리 값을 합치려면 파이프나 소켓 같은 IPC가 필요합니다.

#### 스레드를 많이 만들수록 서버가 빨라지나요?

아닙니다. 코어 수를 넘는 스레드는 CPU를 더 주는 게 아니라 **나눠 쓰게** 하므로, CPU 계산이 많은 작업은 코어 수를 넘기면 문맥 교환 비용만 늘어납니다.
I/O 대기가 많은 작업은 대기 중인 스레드가 CPU를 안 쓰므로 코어 수보다 많이 두는 게 이득이지만, 그래도 스레드마다 스택(리눅스 기본 8MB 예약, JVM 기본 1MB)과 커널 자원이 들고, DB 커넥션 같은 뒷단 자원도 같이 늘어납니다.
그래서 스레드 수는 무한정 늘리지 않고 스레드 풀로 상한을 두고, 부하 테스트로 적정값을 찾습니다. I/O 대기가 압도적이라면 가상 스레드나 비동기 I/O가 대안입니다.

#### Spring 싱글턴 빈은 여러 요청이 동시에 쓰는데 어떻게 안전한가요?

빈 자체는 하나지만 각 요청은 서로 다른 스레드에서 처리되고, 메서드의 지역 변수는 그 스레드의 스택에 있어 요청끼리 섞이지 않기 때문에 안전합니다.
안전하지 않은 경우는 빈의 **필드**에 요청별 상태를 두는 때입니다. 필드는 힙에 있어 모든 스레드가 공유하므로, 요청 A가 넣은 값을 요청 B가 읽는 사고가 납니다.
그래서 서비스·리포지토리 빈은 상태 없이(무상태) 만들고, 요청별 값은 매개변수로 넘기거나 `ThreadLocal`(Spring Security의 `SecurityContextHolder`가 이 방식)에 둡니다. 가상 스레드에서는 `ThreadLocal`이 스레드 수만큼 늘어나므로 `ScopedValue` 같은 대안을 검토합니다.
