## 개념

컴퓨터 안의 모든 데이터는 0과 1이다. 전기가 켜졌는지 꺼졌는지 하나가 **비트**, 비트 8개를 묶은 것이 **바이트**다. 숫자든 글자든 사진이든 "몇 바이트를 어떤 규칙으로 읽을 것인가"라는 약속이 있어야 뜻이 생긴다. 같은 8비트 `01000001`이 정수 규칙으로 읽으면 65, 문자 규칙(ASCII)으로 읽으면 `A`다.

정수는 칸 수가 정해져 있다. 8비트면 0~255(부호 없음) 또는 −128~127(부호 있음)까지만 담긴다. 그 이상은 담을 수 없어서 넘치는 순간 값이 틀어진다 — 이것이 오버플로다. 소수는 정수와 다른 규칙(부동소수점)으로 담는데, 유효 숫자 칸이 정해져 있어 0.1 같은 수도 정확히 담기지 않는다.

부호 있는 8비트 정수에 1씩 더해 보자.

- 시작: `01111111` = 127. 8비트 부호 있는 정수의 최댓값이다.
- 진행: 1을 더하면 `10000000`이 된다. 부호 있는 규칙(2의 보수)에서 맨 앞 비트가 1이면 음수다.
- 결과: −128. 127 + 1이 −128이 됐다. 오류도 안 나고 조용히 틀린 값이 된다(Java `int`도 같다 — 2,147,483,647 + 1 = −2,147,483,648).

## 왜 나왔나

회로는 켜짐/꺼짐 두 상태가 가장 싸고 안정적이라 모든 것을 0과 1로 두기로 했다. 그런데 0과 1만으로 음수와 소수를 어떻게 적을지가 문제였다.

음수는 **2의 보수**로 정했다 — 덧셈 회로 하나로 뺄셈까지 되고, 0이 하나뿐이다. 소수는 과학 표기(1.23 × 10⁵)처럼 **부호·지수·가수**로 나눠 담는 IEEE 754로 정했다. 둘 다 "칸을 정해 놓고 그 안에서 표현한다"는 타협이라, 칸을 넘치거나 칸에 안 떨어지는 값은 틀어진다.

## 확인 질문

- 설명해 보기: 같은 비트열이 65도 되고 `A`도 되는 이유는?
  답: 비트 자체에는 뜻이 없고, 읽는 규칙(정수/문자 인코딩)이 뜻을 정하기 때문이다.
- 다음 상태 예측: Java `int` 변수가 2,147,483,647일 때 1을 더하면?
  답: −2,147,483,648. 32비트 2의 보수에서 최댓값 다음은 최솟값이고, 예외는 나지 않는다.
- 다음 상태 예측: `0.1 + 0.2 == 0.3`은 참인가?
  답: 거짓. 0.1과 0.2가 2진 부동소수점으로 정확히 담기지 않아 합이 0.30000000000000004가 된다.

## 심화

### 2의 보수

n비트로 −2ⁿ⁻¹ ~ 2ⁿ⁻¹−1을 표현한다. 음수 x는 2ⁿ − |x|의 비트열이다. 어떤 수의 음수를 만들려면 비트를 모두 뒤집고 1을 더한다. 덧셈 회로 하나로 뺄셈이 되고(a − b = a + (−b)), 0이 하나뿐이며, 맨 앞 비트가 부호를 알려 준다. 오버플로는 부호가 같은 두 수를 더했는데 결과 부호가 다를 때 생긴다.

### 부동소수점(IEEE 754)

값 = (−1)^부호 × 1.가수 × 2^(지수 − 편향). `float`(32비트)는 가수 23비트로 유효 숫자 약 7자리, `double`(64비트)는 52비트로 약 15~16자리다. 10진 소수 0.1은 2진으로 무한 순환이라 잘려 들어간다. 그래서 돈 계산은 부동소수점을 쓰지 않고 정수(원 단위)나 십진 타입(`BigDecimal`)을 쓴다. 특수 값으로 `NaN`, `±Infinity`, `−0`이 있고, `NaN == NaN`은 거짓이다.

### 문자 인코딩

ASCII는 7비트로 영문·기호 128개다. 한글을 포함한 전 세계 문자는 유니코드가 번호(코드 포인트)를 매기고, 그 번호를 바이트로 적는 방식이 UTF-8·UTF-16이다. UTF-8은 영문 1바이트, 한글 3바이트로 가변 길이다. "글자 수"와 "바이트 수"가 다르므로 DB 컬럼 길이(`VARCHAR(10)`이 글자인지 바이트인지는 DB마다 다름)와 API 길이 검사에서 어긋난다.

### 실무에서는

- 조회수·재고·금액을 `int`로 두면 21억을 넘는 순간 음수가 된다. 누적 카운터는 `long`(64비트, ±922경)으로.
- MySQL `INT`도 32비트다. auto_increment PK가 21억을 넘으면 삽입이 실패한다. 큰 테이블은 `BIGINT`.
- 금액은 `double` 대신 `BigDecimal`(Java) / `DECIMAL`(MySQL). 부동소수점 누적 오차는 정산에서 1원 차이로 드러난다.
- 한글 3바이트: MySQL `utf8`은 3바이트까지만이라 이모지(4바이트)가 안 들어간다. `utf8mb4`를 쓴다.

### 면접 질문

#### 2의 보수를 쓰는 이유는 무엇인가요?

덧셈 회로 하나로 뺄셈까지 처리할 수 있고, 0이 하나뿐이기 때문입니다.
부호-절댓값 방식은 +0과 −0이 따로 있고 덧셈과 뺄셈 회로를 따로 둬야 하지만, 2의 보수는 a − b를 a + (−b)로 바꿔 같은 회로로 계산하고 넘치는 자리를 버리면 결과가 맞습니다.
예를 들어 8비트에서 5 − 3은 `00000101 + 11111101 = 1 00000010`이고 9번째 비트를 버리면 2입니다. 한계는 표현 범위가 비대칭(−128~127)이고 오버플로가 조용히 일어난다는 점입니다.

- 꼬리: Java에서 `Math.addExact`는 무엇을 해 주나요?

#### 금액 계산에 `double`을 쓰면 안 되는 이유는?

`double`은 2진 부동소수점이라 0.1 같은 10진 소수를 정확히 담지 못하고, 연산을 거듭할수록 오차가 쌓이기 때문입니다.
유효 숫자가 약 15~16자리로 정해져 있어 그 아래는 잘리고, 잘린 값끼리 더하고 곱하면 1원 단위 차이가 생깁니다.
예를 들어 0.1을 10번 더하면 1.0이 아니라 0.9999999999999999입니다. 그래서 금액은 정수(원 단위)나 `BigDecimal`/`DECIMAL`로 다루고, 나눗셈이 필요하면 반올림 규칙을 명시합니다.

- 꼬리: `float`와 `double`의 유효 숫자는 각각 몇 자리인가요?

#### `VARCHAR(10)`에 한글 10자를 넣었더니 잘렸습니다. 왜일까요?

그 DB·문자셋에서 길이 단위가 글자가 아니라 바이트이거나, 인코딩이 4바이트 문자를 지원하지 않기 때문입니다.
UTF-8에서 한글은 3바이트라 10자면 30바이트입니다. 길이를 바이트로 세는 설정이면 3자 근처에서 잘리고, MySQL `utf8`(3바이트)에 이모지를 넣으면 4바이트라 오류가 납니다.
MySQL 8.0의 `utf8mb4`에서 `VARCHAR(10)`은 글자 10개를 뜻하지만, 애플리케이션 쪽 검증이 `String.length()`(UTF-16 코드 단위)로 세면 이모지가 2로 세어져 또 어긋납니다. 저장·검증 양쪽에서 같은 단위를 쓰는지 확인합니다.
