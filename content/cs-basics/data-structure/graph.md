## 개념

트리는 위에서 아래로만 갈라진다. 그래프는 **어느 점이든 어느 점과 이어질 수 있다**. 점을 정점, 선을 간선이라 한다. 친구 관계, 도로망, 서비스 간 호출, 빌드 의존성, 락 대기 관계가 모두 그래프다. 트리는 순환이 없고 뿌리가 있는 특수한 그래프다.

간선에 방향이 있으면 유향 그래프(A → B는 되지만 B → A는 아닐 수 있음), 없으면 무향 그래프다. 간선에 숫자(거리·비용)가 붙으면 가중치 그래프다. 저장은 정점마다 "이웃 목록"을 두는 인접 리스트가 보통이다.

서비스 4개의 호출 관계를 담아 보자. `주문 → 결제`, `주문 → 재고`, `결제 → 알림`, `재고 → 알림`.

- 인접 리스트: 주문: [결제, 재고] / 결제: [알림] / 재고: [알림] / 알림: [].
- "주문이 실패하면 영향받는 서비스"는 주문에서 화살표를 따라 닿는 것 전부 → 결제, 재고, 알림.
- "알림 → 주문" 간선을 하나 추가하면 순환이 생긴다 — 서비스끼리 서로를 기다리는 구조가 되어 장애가 돌게 된다.

## 왜 나왔나

계층으로 표현되지 않는 관계가 많았다. 도로는 여러 길로 이어지고, 친구는 서로 얽히며, 마이크로서비스는 서로를 부른다. 이런 관계에서 "A에서 B로 갈 수 있나", "가장 짧은 길은", "순환이 있나"를 묻기 위해 정점·간선 모델과 그 위의 알고리즘(BFS·DFS·최단 경로·위상 정렬)이 정리됐다.

백엔드에서는 의존성 해석(빌드 순서, 빈 생성 순서), 교착 탐지(락 대기 그래프의 순환), 추천(관계 탐색)으로 나타난다.

## 확인 질문

- 설명해 보기: 트리와 그래프의 차이 하나를 말해 보세요.
  답: 트리는 뿌리가 있고 순환이 없으며 부모가 하나지만, 그래프는 아무 정점끼리 이어질 수 있고 순환이 있을 수 있다.
- 다음 상태 예측: 유향 그래프 `A → B → C → A`에서 A부터 화살표를 따라가면?
  답: 끝없이 돈다. 순환이 있다. 방문한 정점을 기록하지 않으면 무한 루프다.
- 다음 상태 예측: 정점 100만 개, 간선 200만 개인 그래프를 인접 행렬로 저장하면 메모리는?
  답: 100만 × 100만 = 1조 칸. 불가능하다. 인접 리스트면 간선 수(200만)에 비례한다.

## 심화

### 저장 방법

인접 행렬은 n×n 표로 "i와 j가 이어졌나"를 O(1)에 답하지만 메모리가 O(n²)라 정점이 많고 간선이 적은(희소) 그래프에는 못 쓴다. 인접 리스트는 정점마다 이웃 목록을 두어 메모리 O(n + m), 이웃 순회가 빠르다. 실무 그래프는 대부분 희소하므로 인접 리스트가 기본이다.

### 순환과 위상 정렬

유향 그래프에 순환이 없으면(DAG) "선행 관계를 지키는 순서"를 만들 수 있다 — 위상 정렬. 빌드 도구(Gradle 작업 순서), 스프링 빈 생성 순서, 스케줄러의 선행 작업이 이것이다. 순환이 있으면 순서를 만들 수 없고, 락 대기 그래프에서 순환은 곧 교착이다(교착상태 장).

### 최단 경로

가중치가 없으면 BFS가 간선 수 기준 최단 경로를 준다. 가중치가 있으면 다익스트라(음수 가중치 없음, 힙으로 O((n+m) log n)), 음수가 있으면 벨만-포드. 지도 길찾기, 네트워크 라우팅(링크 상태 프로토콜)이 다익스트라 계열이다.

### 실무에서는

- 스프링 빈 순환 참조 오류(`BeanCurrentlyInCreationException`)는 빈 의존 그래프에 순환이 있다는 뜻이다. 생성자 주입이면 시작 때 바로 드러난다.
- 마이크로서비스 호출 그래프에 순환이 있으면 한 서비스 장애가 돌아서 자기에게 온다. 호출 방향을 한쪽으로 정리한다.
- DB 교착 탐지는 트랜잭션 대기 그래프에서 순환을 찾는 것이다.
- 추천·소셜 그래프처럼 관계 탐색이 핵심이면 그래프 DB(Neo4j)를 쓰지만, 대부분의 서비스는 관계형 DB의 조인으로 충분하다.

### 면접 질문

#### 그래프를 저장하는 두 방법과 각각의 장단점은?

인접 행렬은 n×n 표로 두 정점의 연결 여부를 O(1)에 답하지만 메모리가 O(n²)이고, 인접 리스트는 정점마다 이웃 목록을 두어 메모리가 O(n+m)이고 이웃 순회가 빠르지만 연결 여부 확인은 이웃 수만큼 걸립니다.
실무 그래프는 정점에 비해 간선이 적은 희소 그래프가 대부분이라 인접 리스트가 기본입니다. 행렬은 정점이 적고 간선이 촘촘할 때나 연결 여부를 자주 물을 때 씁니다.
예를 들어 서비스 100개의 호출 관계는 리스트로 담고, "A가 B를 부르나"를 O(1)로 자주 물어야 하면 이웃 목록을 해시 집합으로 두면 됩니다.

- 꼬리: 간선이 200만 개인 그래프에서 BFS의 복잡도는?

#### 서비스 간 호출 관계에 순환이 있는지 어떻게 찾고, 왜 문제인가요?

호출 관계를 유향 그래프로 만들고 DFS로 "지금 방문 중인 경로"에 다시 닿는 간선이 있는지 확인하거나, 위상 정렬을 시도해 모든 정점을 처리하지 못하면 순환이 있다고 판단합니다.
순환이 있으면 한 서비스의 지연·장애가 화살표를 따라 돌아 자기 자신에게 되돌아오고, 배포·시작 순서를 정할 수 없으며, 동기 호출이면 스레드 풀 고갈이 서로를 키웁니다.
예를 들어 주문 → 결제 → 알림 → 주문이면 알림이 느려질 때 주문 스레드가 묶이고 그것이 다시 결제를 막습니다. 해결은 한쪽 방향을 이벤트(메시지 큐)로 바꿔 동기 순환을 끊는 것입니다.

- 꼬리: 스프링에서 빈 순환 참조가 나면 어떻게 푸나요?
