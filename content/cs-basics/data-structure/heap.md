## 개념

힙은 **"부모는 자식보다 작다"(최소 힙)** 하나만 지키는 트리다. 형제 사이의 순서는 상관없다. 그래서 전체가 정렬돼 있지는 않지만 맨 위에는 항상 가장 작은 값이 있다. 가장 작은 것을 보는 데 O(1), 새로 넣거나 맨 위를 빼는 데 O(log n)이다.

노드를 위에서 아래, 왼쪽에서 오른쪽으로 빈틈없이 채우므로(완전 이진 트리) 포인터 없이 **배열**로 담을 수 있다. i번 노드의 자식은 2i+1, 2i+2, 부모는 (i−1)/2다.

작업 마감이 가까운 순으로 처리하는 상황을 보자(최소 힙, 값은 마감 시각).

- 시작: `[3, 8, 5]` — 맨 위 3.
- 넣기 2: 맨 끝에 붙이고 `[3, 8, 5, 2]`, 부모 8보다 작으니 교환 `[3, 2, 5, 8]`, 부모 3보다 작으니 교환 `[2, 3, 5, 8]`. 두 번 올라갔다.
- 빼기: 맨 위 2를 꺼내고 맨 끝 8을 위로 올린 뒤 `[8, 3, 5]`, 자식 중 작은 3과 교환 `[3, 8, 5]`. 다음 최솟값 3이 맨 위다.
- 결과: 정렬을 유지하지 않고도 매번 최솟값을 O(log n)에 꺼냈다.

## 왜 나왔나

"가장 급한 것부터"를 하려면 정렬된 상태를 유지해야 했는데, 정렬 배열은 삽입이 O(n)이고 탐색 트리는 되지만 최솟값만 필요한 일에는 과했다. 힙은 "최솟값만 빠르면 된다"로 요구를 좁혀 배열 하나로 O(log n)을 얻었다.

우선순위 큐, 다익스트라 최단 경로, 스케줄러, 타이머 관리, 힙 정렬이 여기서 나온다. 참고로 프로세스 메모리의 "힙 영역"은 이름만 같고 자료구조 힙과 무관하다.

## 심화

### 배열 표현과 두 연산

배열 `a`에서 부모 `(i−1)/2`, 자식 `2i+1`, `2i+2`. 삽입은 끝에 붙이고 부모보다 작은 동안 위로 올린다(sift-up). 삭제는 맨 끝을 맨 위로 옮기고 자식 중 작은 쪽보다 큰 동안 아래로 내린다(sift-down). 둘 다 높이만큼이라 O(log n). 배열 n개를 통째로 힙으로 만드는 것은 O(n)이다(뒤에서부터 sift-down).

### 힙 정렬과 상위 k개

힙에서 하나씩 빼면 정렬된다 — 힙 정렬 O(n log n), 추가 메모리 O(1)이지만 캐시 친화성이 나빠 퀵 정렬보다 느리다. "가장 큰 k개"는 크기 k의 최소 힙을 유지하면 O(n log k)로, 전체 정렬 O(n log n)보다 싸다.

### 실무에서는

- Java `PriorityQueue`는 이진 최소 힙. 최대 힙은 역순 비교자로. 반복자 순서는 정렬 순이 아니다.
- 타이머·스케줄러: "가장 먼저 만료되는 작업"을 힙 맨 위에 두고 그것만 기다린다(`ScheduledThreadPoolExecutor`, Kafka·Netty 타이머).
- 다익스트라 최단 경로는 "가장 가까운 정점"을 힙에서 뽑는다.
- CPU 스케줄러의 우선순위 큐, 리눅스 CFS는 레드-블랙 트리(가장 적게 실행된 것을 빠르게 찾기).
- 로그·지표에서 상위 N개(top-N)를 뽑을 때 크기 N 힙으로 전체 정렬을 피한다.

### 면접 질문

#### 힙과 이진 탐색 트리의 차이는 무엇인가요?

힙은 부모-자식 사이의 대소만 지키고 최솟값(또는 최댓값)만 O(1)에 보장하며, 이진 탐색 트리는 왼쪽 < 나 < 오른쪽을 지켜 임의의 키 검색과 범위·정렬 순회가 됩니다.
힙은 요구가 작아 배열 하나로 구현되고 삽입·삭제가 단순하며, 탐색 트리는 균형 유지가 필요하지만 할 수 있는 일이 많습니다.
예를 들어 "가장 급한 작업 하나"만 필요하면 힙(`PriorityQueue`), "10~20 사이의 키"나 "정렬 순 순회"가 필요하면 탐색 트리(`TreeMap`)입니다. 힙에서 임의의 키를 찾는 것은 O(n)입니다.

- 꼬리: 힙을 배열로 담을 때 부모·자식 인덱스는?
- 꼬리: `PriorityQueue`를 순회하면 정렬 순으로 나오나요?

#### 1억 개 숫자 중 가장 큰 100개를 뽑으려면?

크기 100인 최소 힙을 유지합니다. 숫자를 하나씩 보며 힙 맨 위(현재 100개 중 최솟값)보다 크면 맨 위를 빼고 넣습니다.
전체 정렬은 O(n log n)이고 메모리에 1억 개를 다 올려야 하지만, 이 방법은 O(n log 100)이고 메모리는 100개면 되며 스트림으로 흘려보내도 됩니다.
끝나면 힙에 남은 100개가 답이고, 필요하면 100개만 정렬합니다. 한계는 "상위 k개"에만 맞고 k가 n에 가까우면 그냥 정렬하는 게 낫다는 점입니다.

- 꼬리: 최소 힙을 쓰는 이유는(최대 힙이 아니라)?
- 꼬리: 데이터가 여러 서버에 나뉘어 있으면 어떻게 하나요?
