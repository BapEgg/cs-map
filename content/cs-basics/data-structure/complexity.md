## 개념

같은 일을 하는 코드라도 데이터가 10개일 때와 100만 개일 때 걸리는 시간이 다르게 는다. 시간 복잡도는 **입력 크기 n이 커질 때 일의 양이 어떤 비율로 느는가**를 적은 것이다. 실제 초 단위가 아니라 "n에 비례한다(O(n))", "n의 제곱에 비례한다(O(n²))"처럼 증가율만 본다. 공간 복잡도는 같은 방식으로 메모리를 잰다.

자주 나오는 것은 다섯 개다. O(1)은 입력이 커져도 같은 시간(배열 인덱스 접근), O(log n)은 입력이 2배 될 때 한 걸음 더(이진 탐색), O(n)은 비례(전체 훑기), O(n log n)은 좋은 정렬, O(n²)는 이중 반복문.

주문 목록에서 중복 주문을 찾는 두 방법을 비교해 보자.

- 방법 A: 주문마다 나머지 전부와 비교한다. 주문 1,000건이면 약 100만 번 비교 — O(n²).
- 방법 B: 주문 번호를 해시 집합에 넣으며 이미 있는지 본다. 1,000건이면 약 1,000번 — O(n).
- 결과: 1,000건에선 둘 다 순식간이지만, 100만 건이면 A는 1조 번(수십 분), B는 100만 번(수십 ms)이다. 데이터가 늘수록 차이가 벌어진다.

## 왜 나왔나

"빠르다"를 초로 재면 컴퓨터·언어·데이터마다 달라서 비교가 안 됐다. 그래서 기계와 무관하게 **입력이 늘 때 일이 느는 비율**만 남기기로 했다. 상수(2n이든 100n이든)와 낮은 차수(n² + n에서 n)는 버린다 — n이 커지면 의미가 없어지니까.

이 자가 있어야 "이 쿼리는 데이터가 10배 되면 100배 느려진다" 같은 예측을 코드를 돌려 보기 전에 할 수 있다.

## 확인 질문

- 설명해 보기: O(n)과 O(n²)의 차이를 "데이터가 10배 늘면"으로 말해 보세요.
  답: O(n)은 시간도 10배, O(n²)는 100배. 비율이 다르다.
- 다음 상태 예측: 정렬된 100만 개에서 이진 탐색으로 하나를 찾는 데 20번 비교했다. 200만 개면?
  답: 약 21번. O(log n)은 입력이 2배 될 때 한 번만 더 본다.
- 다음 상태 예측: 이중 반복문 안에 배열 `contains`(O(n))가 하나 더 있으면 전체는?
  답: O(n³). 반복이 겹칠 때마다 곱한다.

## 심화

### 상수와 낮은 차수를 버리는 이유

O 표기는 n → ∞일 때의 상한이다. 3n² + 100n + 5는 n이 커지면 n²이 지배하므로 O(n²)로 적는다. 그래서 O 표기가 같아도 실제 속도는 다를 수 있고, n이 작으면 상수가 큰 O(n log n)보다 단순한 O(n²)가 빠르기도 하다(Java `Arrays.sort`가 작은 구간에서 삽입 정렬로 바꾸는 이유).

### 최악·평균·상환

퀵 정렬은 평균 O(n log n)이지만 최악 O(n²), 해시 테이블 조회는 평균 O(1)이지만 충돌이 몰리면 O(n)이다. `ArrayList.add`는 가끔 배열을 늘려 O(n)이 들지만 여러 번에 걸쳐 나누면(상환) O(1)이다. 어떤 값을 말하는지 밝혀야 한다.

### 공간 복잡도

추가로 쓰는 메모리를 같은 방식으로 잰다. 병합 정렬은 O(n)의 보조 배열이 필요하고, 힙 정렬은 O(1)이다. 재귀는 호출 깊이만큼 스택을 쓴다 — 깊이가 n이면 공간 O(n)이고, 크면 스택 오버플로다.

### 실무에서는

- N+1 쿼리는 코드로는 O(n)처럼 보여도 쿼리 n번 = 네트워크 왕복 n번이다. 복잡도의 단위를 "쿼리 횟수"로 세면 병목이 보인다.
- 반복문 안의 `list.contains`·`list.remove(Object)`는 O(n)이라 전체가 O(n²)가 된다. `HashSet`으로 바꾸면 O(n).
- DB에서 인덱스 없는 조회는 O(n)(풀 스캔), B-tree 인덱스는 O(log n). 데이터가 10배가 될 때 전자는 10배, 후자는 거의 그대로다.
- 문자열을 반복문에서 `+`로 이어 붙이면 매번 새로 복사해 O(n²). `StringBuilder`는 O(n).

### 면접 질문

#### 시간 복잡도란 무엇이고, 왜 실제 시간 대신 쓰나요?

입력 크기가 커질 때 걸리는 일의 양이 느는 비율을 O 표기로 나타낸 것이며, 실제 시간은 기계·언어·데이터에 따라 달라 비교가 안 되기 때문입니다.
상수와 낮은 차수를 버리고 증가율만 남기므로 "데이터가 10배 되면 시간이 얼마나 느는가"를 코드를 돌려 보기 전에 예측할 수 있습니다.
예를 들어 중복 검사를 이중 반복문(O(n²))으로 짜면 100만 건에서 1조 번 비교지만 해시 집합(O(n))이면 100만 번입니다. 한계는 n이 작을 때는 상수가 큰 알고리즘이 오히려 느릴 수 있고, 캐시·메모리 접근 패턴처럼 O 표기가 못 담는 요인이 실제 속도를 좌우하기도 한다는 점입니다.

- 꼬리: O(n log n)과 O(n²) 중 n=10에서 어느 쪽이 빠른가요?
- 꼬리: 해시 테이블 조회가 O(1)이 아닌 경우는?

#### 코드 리뷰에서 "이 부분 O(n²)예요"라는 말을 들었습니다. 무엇을 봐야 하나요?

반복문이 겹치는 곳과, 반복문 안에서 부르는 메서드가 내부적으로 전체를 훑는지를 봅니다.
겉보기에 반복문이 하나여도 안에서 `list.contains`, `list.remove(Object)`, 문자열 `+` 연결, 쿼리 호출을 하면 각각 O(n)이라 전체가 O(n²)가 됩니다.
예를 들어 주문 목록을 돌며 `customers.contains(order.customerId)`를 하면 고객이 1만 명일 때 주문 1만 건에 1억 번 비교입니다. `customers`를 `HashSet`으로 바꾸면 O(n)이 됩니다. 한계는 데이터가 항상 작다면 고칠 가치가 없을 수도 있으니, 입력 크기의 실제 범위를 먼저 확인하는 것입니다.

- 꼬리: 쿼리 횟수로 복잡도를 세면 N+1은 어떻게 보이나요?
