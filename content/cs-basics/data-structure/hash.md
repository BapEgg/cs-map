## 개념

배열은 "몇 번째"로만 찾는다. 해시는 **키(이름·번호·문자열)를 해시 함수로 숫자 하나로 바꿔** 그 숫자를 배열 칸 번호로 쓴다. 넣을 때도 찾을 때도 같은 계산을 하므로, 100만 개가 있어도 한 번의 계산과 한 칸 확인으로 끝난다 — 평균 O(1).

서로 다른 키가 같은 칸에 떨어지는 것이 충돌이다. 그 칸에 목록을 달아 두고(체이닝) 그 안에서 찾는다. 칸 수에 비해 키가 많아지면 충돌이 늘어 느려지므로, 일정 비율(적재율)을 넘으면 배열을 늘리고 전부 다시 배치한다.

칸 8개짜리 해시 테이블에 사용자 ID로 이름을 저장해 보자. 해시 함수는 "ID를 8로 나눈 나머지"다.

- 넣기: ID 21 → 21 % 8 = 5 → 5번 칸에 (21, "김"). ID 13 → 13 % 8 = 5 → 5번 칸이 이미 있으므로 목록에 (13, "이")를 덧붙인다(충돌).
- 찾기: ID 13 → 5번 칸 → 목록에서 키 13을 확인 → "이". 두 번 비교.
- 결과: 100만 명이 있어도 "칸 계산 + 그 칸의 목록"만 본다. 목록이 길어지지 않게 칸을 늘리는 것이 핵심이다.

## 왜 나왔나

이름으로 찾으려면 배열은 처음부터 훑어야 했고(O(n)), 정렬해 두고 이진 탐색해도 O(log n)에 정렬 유지 비용이 들었다. "키에서 자리를 바로 계산할 수 없을까"가 해시다.

대가는 순서다. 해시 테이블은 키를 순서대로 꺼낼 수 없고, "10 이상 20 이하"같은 범위 조회도 못 한다. 그래서 순서·범위가 필요하면 트리(DB 인덱스의 B-tree)를 쓴다.

## 확인 질문

- 설명해 보기: 해시 테이블이 100만 개 중 하나를 O(1)에 찾는 원리는?
  답: 키를 해시 함수로 칸 번호로 바꿔 그 칸만 보기 때문이다. 훑지 않는다.
- 다음 상태 예측: 해시 함수가 모든 키를 0번 칸으로 보내면?
  답: 모든 키가 한 목록에 몰려 찾기가 O(n)이 된다. 해시 함수의 분산이 성능을 정한다.
- 다음 상태 예측: 칸 16개짜리 테이블에 키가 13개 들어갔다(적재율 0.75 초과). 다음에 무슨 일이?
  답: 칸을 32개로 늘리고 13개를 전부 다시 배치한다(리해시). 그 한 번은 O(n)이다.

## 심화

### 좋은 해시 함수

키가 조금만 달라도 값이 크게 달라져 칸에 고르게 퍼져야 하고, 같은 키는 항상 같은 값이어야 한다. Java는 `hashCode()`가 이 역할이고, `HashMap`은 그 값을 한 번 더 섞어(상위 비트 XOR) 칸을 고른다. `equals`가 같으면 `hashCode`도 같아야 한다는 계약을 깨면 넣은 키를 못 찾는다(Java의 equals/hashCode 장).

### 충돌 처리

체이닝은 칸마다 연결 리스트(Java 8+는 8개 넘으면 트리로 바꿔 최악 O(log n)). 개방 주소법은 충돌하면 옆 칸으로 옮겨 가며 빈 칸을 찾는다(배열 하나라 캐시 친화적, 삭제가 까다로움). 어느 쪽이든 적재율이 높아지면 느려지므로 리사이즈가 필요하다.

### 리사이즈

Java `HashMap`은 기본 16칸, 적재율 0.75를 넘으면 2배로 늘리고 전부 다시 배치한다. 크기를 미리 알면 `new HashMap<>(예상 크기 / 0.75)`로 리해시를 없앤다. 리사이즈 중인 `HashMap`을 여러 스레드가 동시에 고치면 구조가 깨진다 — `ConcurrentHashMap`을 쓴다.

### 해시의 다른 얼굴들

같은 원리가 여러 곳에 있다. 암호 저장은 되돌릴 수 없는 해시(bcrypt)로, 데이터 무결성은 SHA-256으로, 캐시 서버 분산은 일관된 해싱으로, DB 인덱스에는 등호 조회 전용 해시 인덱스(MySQL MEMORY 엔진, PostgreSQL hash index)로 쓴다. 공통점은 "키 → 고정 크기 숫자"다.

### 실무에서는

- `HashMap`의 키로 쓰는 클래스는 `equals`/`hashCode`를 함께 재정의한다. 한쪽만 하면 조회가 실패한다.
- 가변 객체를 키로 쓰고 나중에 필드를 바꾸면 해시가 바뀌어 못 찾는다. 키는 불변으로.
- Redis는 키-값 저장소 자체가 거대한 해시 테이블이다. 키 설계가 곧 분산과 조회 패턴을 정한다.
- 해시 인덱스는 `=` 조회만 되고 `BETWEEN`·`ORDER BY`는 못 쓴다. 범위가 필요하면 B-tree.

### 면접 질문

#### 해시 테이블은 어떻게 O(1)에 찾고, 언제 O(1)이 깨지나요?

키를 해시 함수로 칸 번호로 바꿔 그 칸만 보기 때문에 평균 O(1)이고, 충돌이 한 칸에 몰리거나 적재율이 높아 목록이 길어지면 O(n)에 가까워집니다.
해시 함수가 고르게 퍼뜨리고 적재율을 낮게 유지(리사이즈)하면 칸당 항목 수가 상수로 유지됩니다. Java `HashMap`은 0.75를 넘으면 2배로 늘리고, 한 칸에 8개가 넘으면 트리로 바꿔 최악을 O(log n)으로 막습니다.
예를 들어 `hashCode`가 모두 같은 값을 돌려주는 키를 쓰면 전부 한 칸에 몰려 사실상 리스트가 됩니다. 한계는 순서·범위 조회가 안 되고, 리사이즈 순간에 O(n)이 든다는 점입니다.

- 꼬리: `equals`만 재정의하고 `hashCode`를 안 하면 `HashMap`에서 무슨 일이 생기나요?
- 꼬리: 체이닝과 개방 주소법의 차이는?

#### DB 인덱스는 왜 해시가 아니라 B-tree가 기본인가요?

해시는 `=` 조회만 되고 범위·정렬·접두 검색이 안 되는데, 실제 쿼리는 `BETWEEN`, `ORDER BY`, `LIKE 'abc%'`가 많기 때문입니다.
B-tree는 키를 정렬된 채로 두어 등호 조회 O(log n)에 범위 스캔까지 되고, 노드가 디스크 페이지 크기라 I/O 횟수가 적습니다. 해시는 등호 조회에서 조금 빠를 뿐입니다.
그래서 MySQL InnoDB는 B-tree만 제공하고(해시는 내부 적응형 해시 인덱스로 보조), PostgreSQL은 hash index를 따로 만들 수 있지만 등호 전용입니다. 한계는 B-tree가 정렬 유지 비용을 치른다는 점이지만 그 비용이 범위 조회의 이득보다 작습니다.
