## 개념

연결 리스트는 데이터 칸(노드)이 붙어 있지 않다. 각 노드가 **자기 값과 다음 노드의 주소**를 들고 있어서, 첫 노드부터 주소를 따라가면 전체를 순서대로 만난다. 노드를 끼우거나 빼는 건 앞뒤 노드의 주소만 바꾸면 되므로 다른 노드를 옮길 필요가 없다.

대신 "i번째"로 바로 갈 수 없다. 첫 노드부터 i번 따라가야 한다. 앞뒤 주소를 둘 다 들면 이중 연결 리스트로, 뒤로도 갈 수 있고 어느 노드든 자기 앞뒤만 알면 O(1)에 뺄 수 있다.

`10 → 20 → 30` 리스트에서 두 가지를 해 보자.

- 20 뒤에 25 끼우기: 새 노드 25를 만들고, 25의 다음을 30으로, 20의 다음을 25로 바꾼다. 옮긴 노드는 없다 — 주소 두 개만 바꿨다.
- 3번째 값 읽기: 10 → 20 → 30, 세 번 따라간다. 노드가 100만 개면 100만 번.
- 결과: 위치를 쥐고 있을 때의 삽입은 O(1), 위치를 찾아가는 것은 O(n).

## 왜 나왔나

배열은 중간에 하나 끼우려면 뒤 전부를 밀어야 했고, 크기를 미리 정해야 했다. 노드마다 다음 주소를 들게 하면 어디든 끼우고 뺄 수 있고, 크기도 필요할 때마다 노드 하나씩 늘면 된다.

그 대가로 인덱스 접근과 순회 속도를 잃었다. 노드가 메모리 곳곳에 흩어지므로 CPU 캐시가 옆 데이터를 미리 가져오는 이득이 사라진다. 그래서 실무에서 "연결 리스트가 배열을 이기는" 경우는 생각보다 드물고, 큐·LRU 캐시처럼 양 끝이나 이미 쥔 노드를 다루는 구조에서 산다.

## 확인 질문

- 설명해 보기: 연결 리스트에서 중간 삽입이 O(1)인 조건은?
  답: 끼울 위치의 앞 노드를 이미 쥐고 있을 때. 그 위치까지 찾아가는 것은 O(n)이다.
- 다음 상태 예측: `10 → 20 → 30`에서 20을 빼면 무엇을 바꾸나?
  답: 10의 다음을 30으로. 20 노드는 버린다(단일 연결 리스트면 10을 알아야 하고, 이중이면 20만 알아도 된다).
- 다음 상태 예측: 노드 100만 개 리스트를 처음부터 끝까지 훑는 시간은 같은 크기 배열보다?
  답: 이론상 둘 다 O(n)이지만 실제로는 리스트가 몇 배 느리다. 노드가 흩어져 캐시 미스가 매번 난다.

## 심화

### 단일·이중·원형

단일 연결 리스트는 다음 주소만, 이중은 앞뒤 주소를 든다. 이중이어야 "이 노드를 빼라"를 O(1)에 할 수 있다(앞 노드를 알아야 하니까). 원형은 마지막이 처음을 가리켜 끝이 없다. Java `LinkedList`는 이중 연결 리스트다.

### LRU 캐시 — 연결 리스트가 진짜 쓰이는 곳

해시맵으로 키 → 노드를 O(1)에 찾고, 이중 연결 리스트로 "최근 사용 순서"를 유지한다. 접근한 노드를 맨 앞으로 옮기고(앞뒤 주소 4개 수정), 꽉 차면 맨 뒤를 뗀다. 배열이었다면 옮길 때마다 O(n)이다. Java `LinkedHashMap(accessOrder=true)`가 이 구조다.

### 왜 실무에서 드문가

`LinkedList.get(i)`는 O(n)이고, `add(i, x)`도 i까지 가는 데 O(n)이라 `ArrayList`의 이동 O(n)과 다를 게 없다. 게다가 노드마다 객체 헤더 + 앞뒤 포인터로 메모리를 3배쯤 더 쓰고 캐시 미스가 잦다. 반복자(iterator)로 순회하며 그 자리에서 `remove`하는 경우처럼 위치를 이미 쥔 때에만 이득이다.

### 실무에서는

- Java 목록은 `ArrayList`가 기본. `LinkedList`는 큐로 쓸 때조차 `ArrayDeque`보다 느리다.
- LRU 캐시(Redis `allkeys-lru`의 근사, `LinkedHashMap`), 리눅스 페이지 캐시의 active/inactive 리스트가 연결 리스트다.
- 해시맵의 버킷 충돌 목록도 연결 리스트다(Java 8+는 8개 넘으면 트리로 바꿈).
- 메시지 큐·작업 큐의 노드 연결(`ConcurrentLinkedQueue`)은 락 없는 연결 리스트다.

### 면접 질문

#### 연결 리스트는 언제 배열보다 유리한가요?

끼우거나 뺄 위치를 이미 쥐고 있을 때, 그리고 양 끝에서만 넣고 뺄 때 유리합니다. 인덱스로 접근하거나 전체를 훑는 일이 많으면 배열이 낫습니다.
연결 리스트의 삽입·삭제 O(1)은 그 위치의 노드를 알고 있을 때의 이야기이고, 찾아가는 데 O(n)이 들면 배열의 이동 비용과 같아집니다. 게다가 노드가 흩어져 있어 캐시 이득이 없습니다.
예를 들어 LRU 캐시는 해시맵이 노드를 O(1)에 찾아 주므로 연결 리스트의 O(1) 이동이 살아납니다. 반대로 "목록 중간에 자주 넣는다"는 이유로 `LinkedList`를 고르면 위치를 찾는 O(n) 때문에 이득이 없습니다.

- 꼬리: `LinkedList`를 큐로 쓰는 것과 `ArrayDeque`의 차이는?

#### LRU 캐시를 O(1)로 구현해 보세요.

키 → 노드를 저장하는 해시맵과 사용 순서를 담는 이중 연결 리스트를 함께 씁니다.
조회·삽입 때 해당 노드를 리스트 맨 앞으로 옮기고(앞뒤 포인터 수정), 용량을 넘으면 맨 뒤 노드를 떼고 해시맵에서도 지웁니다. 찾기는 해시맵이, 순서 유지는 리스트가 맡아 둘 다 O(1)입니다.
Java에서는 `LinkedHashMap`을 `accessOrder=true`로 만들고 `removeEldestEntry`를 재정의하면 됩니다. 한계는 여러 스레드가 동시에 쓰면 리스트 포인터가 꼬이므로 락이 필요하고, 그러면 O(1)이어도 경합이 병목이 된다는 점입니다.
