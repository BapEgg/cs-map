## 개념

트리는 하나의 뿌리에서 가지가 갈라지고 갈라진 가지가 또 갈라지는 **계층** 구조다. 폴더 안의 폴더, 조직도, 이 앱의 개념 지도가 트리다. 각 칸(노드)은 자식 노드들을 가리키고, 자식이 없는 노드를 잎이라 한다.

찾기에 쓰는 트리는 규칙을 하나 더 둔다. **이진 탐색 트리**는 왼쪽 자식은 나보다 작고 오른쪽 자식은 크다. 그러면 뿌리에서 시작해 "작으면 왼쪽, 크면 오른쪽"으로 내려가며 한 번에 후보를 절반씩 줄인다 — 균형이 맞으면 O(log n). 해시와 달리 정렬이 유지되므로 "10 이상 20 이하"나 "가장 큰 것 5개"도 바로 뽑는다.

값 `50, 30, 70, 20, 40`을 이진 탐색 트리에 넣고 40을 찾아 보자.

- 넣기: 50이 뿌리. 30은 50보다 작으니 왼쪽. 70은 오른쪽. 20은 50 왼쪽 → 30 왼쪽. 40은 50 왼쪽 → 30 오른쪽.
- 찾기 40: 50보다 작다 → 왼쪽(30). 30보다 크다 → 오른쪽(40). 찾았다 — 비교 3번.
- 결과: 5개 중 3번 비교. 100만 개라도 균형이 맞으면 약 20번이다. 범위 30~50을 물으면 30, 40, 50을 순서대로 뽑을 수 있다.

## 왜 나왔나

해시는 이름으로 찾기는 빠르지만 순서가 없어 범위·정렬 조회가 안 됐다. 정렬된 배열은 범위 조회는 되지만 중간 삽입이 O(n)이었다. 정렬을 유지하면서 삽입·삭제·조회를 모두 O(log n)에 하려고 탐색 트리가 나왔다.

이진 탐색 트리는 넣는 순서에 따라 한쪽으로 기울어 리스트가 될 수 있어서, 스스로 균형을 맞추는 트리(레드-블랙 트리, AVL)와 노드 하나에 키를 수백 개 담아 디스크에 맞춘 B-tree가 뒤따랐다. DB 인덱스가 B-tree인 이유다.

## 확인 질문

- 설명해 보기: 이진 탐색 트리가 O(log n)에 찾는 원리는?
  답: 뿌리부터 "작으면 왼쪽, 크면 오른쪽"으로 내려가며 비교 한 번에 후보가 절반으로 준다. 단, 균형이 맞을 때.
- 다음 상태 예측: 이진 탐색 트리에 1, 2, 3, 4, 5를 순서대로 넣으면 모양은?
  답: 오른쪽으로만 뻗은 한 줄. 찾기가 O(n)이 된다. 균형 트리가 필요한 이유.
- 다음 상태 예측: 해시맵과 트리맵에 같은 키들을 넣고 "키가 10~20인 것"을 뽑으려면?
  답: 트리맵은 범위를 바로 뽑는다(`subMap`). 해시맵은 전부 훑어야 한다.

## 심화

### 균형 트리

레드-블랙 트리와 AVL 트리는 삽입·삭제 때 회전으로 높이를 log n 근처로 유지한다. Java `TreeMap`·`TreeSet`이 레드-블랙 트리이고, `HashMap`의 한 버킷에 8개가 넘으면 이것으로 바뀐다. 리눅스 커널의 스케줄러(CFS)와 메모리 영역 관리에도 쓰인다.

### B-tree — 디스크를 위한 트리

디스크는 한 번에 페이지(보통 4~16KB) 단위로 읽으므로, 노드 하나에 키를 수백 개 담아 트리 높이를 3~4로 낮춘다. 100만 행이어도 디스크 읽기 3~4번이면 찾는다. B+tree는 잎 노드끼리 연결돼 범위 스캔이 이어진다. MySQL InnoDB·PostgreSQL 인덱스가 이것이다. 자세한 것은 데이터베이스의 인덱스 장.

### 순회

트리 전체를 도는 방법이 세 가지다. 중위 순회(왼쪽 → 나 → 오른쪽)는 이진 탐색 트리를 정렬 순으로 꺼내고, 전위·후위는 폴더 복사·삭제처럼 부모를 먼저/나중에 처리할 때 쓴다. 깊이 우선(DFS)은 재귀나 스택, 너비 우선(BFS)은 큐로 한다.

### 실무에서는

- 정렬된 상태로 유지하며 범위·최소·최대를 자주 물으면 `TreeMap`, 아니면 `HashMap`(트리는 O(log n), 해시는 O(1)).
- DB 인덱스는 B-tree라 `WHERE a = ?`, `a BETWEEN`, `ORDER BY a`, `LIKE 'ab%'`를 다 탄다. `LIKE '%ab'`는 못 탄다.
- 복합 인덱스 `(a, b)`는 a로 정렬한 뒤 b로 정렬한 트리다. b만으로는 못 찾는다(맨 왼쪽 접두 규칙).
- JSON·HTML DOM·파일 시스템·이 앱의 개념 지도는 탐색 트리가 아니라 계층을 표현하는 일반 트리다.

### 면접 질문

#### 해시 테이블과 트리(TreeMap)는 언제 각각 쓰나요?

키로 하나를 찾는 일만 있으면 해시(평균 O(1)), 정렬 순서·범위·최소·최대가 필요하면 트리(O(log n))를 씁니다.
해시는 키를 칸 번호로 바꾸므로 순서가 없고, 트리는 정렬을 유지하므로 범위 조회와 순서 순회가 됩니다. 대신 조회 비용이 상수가 아니라 로그입니다.
예를 들어 사용자 ID → 세션은 `HashMap`, "가격 1만~2만 원 상품"이나 "만료 시각이 가장 이른 것"은 `TreeMap`입니다. 같은 이유로 DB 인덱스는 범위 쿼리를 위해 B-tree가 기본입니다.

- 꼬리: 이진 탐색 트리가 O(n)이 되는 경우와 막는 방법은?
- 꼬리: `HashMap`이 버킷을 트리로 바꾸는 이유는?

#### B-tree가 이진 탐색 트리보다 DB에 맞는 이유는?

디스크는 페이지 단위로 읽으므로 노드 하나에 키를 수백 개 담아 높이를 3~4로 낮추면 디스크 읽기 횟수가 그만큼 줄기 때문입니다.
이진 트리는 100만 개에 높이 20이라 디스크 읽기 20번인데, B-tree는 페이지 하나에 수백 키를 담아 3~4번이면 됩니다. 잎끼리 연결된 B+tree는 범위 스캔도 이어서 읽습니다.
MySQL InnoDB는 PK로 정렬된 클러스터드 B+tree에 행을 저장하고, 보조 인덱스 잎에는 PK를 둡니다. 한계는 삽입·삭제 때 노드 분할·병합이 일어나고, 무작위 PK(UUID)는 삽입 위치가 흩어져 분할이 잦아진다는 점입니다.

- 꼬리: 클러스터드 인덱스와 보조 인덱스의 차이는?
- 꼬리: UUID를 PK로 쓰면 B-tree에 무슨 일이 생기나요?
