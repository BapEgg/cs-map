## 개념

큐는 **뒤로 넣고(enqueue) 앞에서 뺀다(dequeue)**. 먼저 들어온 것이 먼저 나온다 — 선입선출(FIFO). "온 순서대로 처리한다"가 필요한 모든 곳에 있다. 프린터 대기열, 스레드 풀의 작업 대기열, 메시지 큐, 운영체제의 준비 큐가 전부 큐다.

배열로 만들 때는 앞에서 빼면 뒤 전부를 밀어야 하므로(O(n)), 머리·꼬리 인덱스를 두고 끝에 닿으면 처음으로 돌아가는 **원형 버퍼**로 만들어 O(1)을 얻는다. 양 끝 모두에서 넣고 빼면 덱(deque), 순서가 아니라 우선순위로 빼면 우선순위 큐다.

스레드 2개짜리 풀에 요청 A·B·C·D가 순서대로 온 상황을 따라가 보자.

- 시작: 큐가 비었다. A와 B는 바로 스레드에 배정된다.
- 진행: C·D가 큐에 들어간다 `[C, D]`. A가 끝나면 그 스레드가 큐 앞의 C를 뺀다 `[D]`. B가 끝나면 D를 뺀다.
- 결과: C가 D보다 먼저 처리됐다 — 온 순서 그대로. C의 응답 시간에는 큐에서 기다린 시간이 더해졌다.

## 왜 나왔나

한꺼번에 처리할 수 없는 요청들을 순서대로 보관할 자리가 필요했다. 순서를 지키지 않으면 먼저 온 요청이 영영 밀릴 수 있다(기아). 큐는 "먼저 온 순서"라는 가장 공정한 규칙을 자료구조로 못 박은 것이다.

배열의 앞에서 빼는 비용을 없애려고 원형 버퍼가, 순서 대신 중요도로 빼려고 힙 기반의 우선순위 큐가 나왔다.

## 확인 질문

- 설명해 보기: 큐에 1, 2, 3을 넣고 하나 빼면?
  답: 1. 먼저 넣은 것이 먼저 나온다.
- 다음 상태 예측: 배열로 만든 큐에서 `remove(0)`으로 앞을 빼면 비용은?
  답: O(n). 뒤 전부를 한 칸씩 민다. 원형 버퍼(`ArrayDeque`)면 O(1).
- 다음 상태 예측: 처리 속도보다 들어오는 속도가 계속 빠르면 큐는?
  답: 끝없이 자란다. 상한을 두고 넘치면 거절하거나(스레드 풀 거절 정책), 넣는 쪽을 늦춰야(배압) 한다.

## 심화

### 원형 버퍼

크기 n인 배열에 `head`, `tail`을 둔다. 넣으면 `tail = (tail + 1) % n`, 빼면 `head = (head + 1) % n`. 이동이 없어 양쪽 O(1)이다. Java `ArrayDeque`가 이 구조이고, 꽉 차면 배열을 늘린다. 로그 버퍼, 네트워크 소켓 버퍼도 원형 버퍼다.

### 우선순위 큐

순서가 아니라 값(우선순위)이 가장 작은/큰 것을 먼저 뺀다. 힙으로 만들면 넣기·빼기 O(log n). CPU 스케줄러의 우선순위 큐, 다익스트라 최단 경로, 타이머(가장 빨리 만료되는 것부터)가 쓴다. Java `PriorityQueue`.

### 블로킹 큐 — 생산자·소비자

큐가 비면 빼는 쪽이 잠들고, 차면(유한 큐) 넣는 쪽이 잠든다. 스레드 풀의 작업 큐(`LinkedBlockingQueue`, `ArrayBlockingQueue`)가 이것이다. 세마포어 장의 생산자-소비자가 큐로 구현된 형태다. 큐 길이가 곧 대기 시간이라 모니터링 지표로 삼는다.

### 실무에서는

- 스레드 풀 작업 큐: 무한 큐면 폭주 때 메모리가 터지고, 유한 큐면 거절 정책이 필요하다. 큐 길이가 응답 시간에 그대로 더해진다.
- 메시지 큐(Kafka·RabbitMQ)는 큐를 프로세스 밖·서버 밖으로 꺼낸 것이다. 순서 보장 범위(파티션 안에서만)와 재처리가 새로 문제가 된다.
- BFS는 큐로, DFS는 스택으로 — 자료구조가 탐색 순서를 정한다.
- 큐를 `LinkedList`로 만들면 노드 할당이 잦아 `ArrayDeque`보다 느리다.

### 면접 질문

#### 큐를 배열로 만들 때의 문제와 해결법은?

앞에서 빼면 뒤 요소 전부를 한 칸씩 밀어야 해 O(n)이 되는 것이 문제이고, 머리·꼬리 인덱스를 두고 끝에 닿으면 처음으로 돌아가는 원형 버퍼로 해결합니다.
원형 버퍼는 넣기·빼기 모두 인덱스 계산만 하므로 O(1)이고, 연결 리스트와 달리 메모리가 연속돼 캐시 효율이 좋습니다.
Java `ArrayDeque`가 이 구조이며 `LinkedList`보다 큐로 쓰기에 빠릅니다. 한계는 꽉 찼을 때 배열을 늘려 복사하는 순간이 있다는 것인데, 상환 O(1)이고 크기를 미리 잡으면 피할 수 있습니다.

- 꼬리: 원형 버퍼에서 "비었다"와 "꽉 찼다"를 어떻게 구분하나요?
- 꼬리: 우선순위 큐는 왜 힙으로 만드나요?

#### 스레드 풀의 큐가 계속 길어집니다. 무엇을 뜻하고 어떻게 하나요?

들어오는 속도가 처리 속도를 넘었다는 뜻이며, 큐 길이만큼 응답이 늦어지므로 처리량을 올리거나 들어오는 양을 제한해야 합니다.
큐는 순간 폭주를 흡수하는 완충이지 처리 능력을 늘리지 않습니다. 계속 자란다면 완충이 아니라 지연을 쌓는 중이고, 무한 큐면 결국 메모리가 바닥납니다.
병목이 CPU면 스레드를 늘려도 소용없고 코어나 서버를 늘려야 하며, 병목이 DB·외부 API 대기면 그쪽을 손봅니다. 그동안은 큐에 상한을 두어 넘치는 요청을 빨리 거절하고(fail fast) 호출한 쪽이 재시도·백오프하게 하는 것이 무한정 기다리게 하는 것보다 낫습니다.

- 꼬리: 배압(backpressure)이란?
