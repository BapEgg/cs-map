## 개념

이체는 "A에서 빼기"와 "B에 더하기" 두 번의 쓰기다. 첫 번째 뒤에 서버가 죽으면 돈이 사라진다. 트랜잭션은 **여러 쓰기를 한 덩어리로 묶어, 끝에 커밋하면 전부 반영되고 중간에 실패하면 롤백으로 전부 취소**되게 하는 단위다. DB가 로그를 남겨 두었다가 되돌린다.

ACID는 트랜잭션이 보장하는 네 성질이다. **원자성**(전부 아니면 전무), **일관성**(제약이 깨진 상태로 끝나지 않음), **격리성**(동시에 도는 트랜잭션이 서로의 중간을 안 봄 — 정도는 격리 수준으로 조절), **지속성**(커밋했으면 장애가 나도 남음).

이체 트랜잭션을 따라가 보자.

- 시작: `BEGIN`. A 잔액 100, B 잔액 0.
- 진행: `UPDATE accounts SET balance = balance - 30 WHERE id = 'A'` → `UPDATE … + 30 WHERE id = 'B'`. 여기서 서버가 죽으면 DB는 재시작 때 로그를 보고 A의 변경을 되돌린다 — A 100, B 0.
- 커밋: `COMMIT`. DB가 로그를 디스크에 확실히 쓴 뒤 성공을 돌려준다. 이 뒤 서버가 죽어도 A 70, B 30은 남는다.
- 결과: 중간 상태(A 70, B 0)는 바깥에서 보이지 않고(격리), 어느 시점에 죽어도 돈의 합은 100이다.

## 왜 나왔나

여러 쓰기가 얽힌 작업에서 "반만 된 상태"가 데이터를 망가뜨렸다. 장애·오류가 나도 반만 남지 않게, 그리고 동시에 여럿이 고쳐도 서로 뒤엉키지 않게 하려고 "작업 단위"와 그 보장을 DB에 넣었다. 로그를 먼저 쓰고 데이터를 나중에 쓰는 WAL 방식이 원자성과 지속성의 구현이고, 격리성은 락과 MVCC가 맡는다.

## 확인 질문

- 설명해 보기: ACID 네 글자를 각각 한 마디로.
  답: 원자성 = 전부 아니면 전무, 일관성 = 제약을 지킨 채 끝남, 격리성 = 동시 트랜잭션이 서로의 중간을 안 봄, 지속성 = 커밋은 장애에도 남음.
- 다음 상태 예측: 출금 UPDATE 뒤, 입금 UPDATE 전에 애플리케이션이 예외를 던졌다. 롤백하면 잔액은?
  답: 둘 다 원래대로. 출금이 취소된다. 롤백을 안 하고 연결을 반납하면(커넥션 풀) 다음 사용자가 그 열린 트랜잭션을 이어받는 사고가 난다.
- 다음 상태 예측: `COMMIT`이 성공을 돌려준 직후 DB 서버 전원이 나갔다. 데이터는?
  답: 남는다. 커밋은 로그가 디스크에 쓰인 뒤에야 성공을 돌려준다(지속성).

## 심화

### 어떻게 되돌리고 어떻게 남기나 — 로그

DB는 데이터 페이지를 고치기 전에 "무엇을 어떻게 바꾸는지"를 로그에 먼저 순서대로 쓴다(Write-Ahead Logging). 커밋은 이 로그가 디스크에 닿는 순간이다. 장애 뒤 재시작하면 로그를 읽어 커밋된 것은 다시 적용(redo)하고 커밋 안 된 것은 되돌린다(undo). InnoDB는 redo 로그와 undo 로그를 따로 두고, undo는 MVCC의 옛 버전 읽기에도 쓰인다.

### 일관성은 DB 혼자 못 지킨다

제약(NOT NULL, FK, CHECK)은 DB가 지키지만 "잔액의 합이 보존된다" 같은 업무 규칙은 애플리케이션이 트랜잭션 안에서 지켜야 한다. ACID의 C는 "A·I·D를 제대로 쓰면 애플리케이션이 일관성을 만들 수 있다"에 가깝다.

### 트랜잭션의 범위와 길이

범위는 "함께 성공하거나 실패해야 하는 것"까지다. 넓으면 락을 오래 잡아 동시성이 떨어지고, 좁으면 반만 되는 상태가 생긴다. 트랜잭션 안에서 외부 API를 부르면 응답 시간만큼 락이 유지되고, 외부는 롤백이 안 되므로 "DB는 롤백됐는데 결제는 됨"이 생긴다 — 외부 호출은 트랜잭션 밖으로, 보상 트랜잭션이나 아웃박스 패턴으로.

### 실무에서는

- Spring `@Transactional`은 메서드 시작에 `BEGIN`, 정상 종료에 `COMMIT`, 예외(기본은 RuntimeException)에 `ROLLBACK`. 검사 예외는 기본 롤백 안 됨 — Spring 트랜잭션 장.
- 자동 커밋(auto-commit) 모드에서는 문장 하나가 트랜잭션 하나다. 여러 문장을 묶으려면 명시적으로 시작해야 한다.
- 커넥션 풀에 트랜잭션이 열린 채 연결이 돌아가면 다음 요청이 남의 트랜잭션을 이어받는다. 풀이 반납 때 롤백하지만 설정에 따라 다르니 코드에서 확실히 끝낸다.
- 지속성은 디스크 동기화 설정(`innodb_flush_log_at_trx_commit`, PostgreSQL `synchronous_commit`)에 달렸다. 성능 때문에 늦추면 마지막 몇 트랜잭션을 잃을 수 있다.

### 면접 질문

#### 트랜잭션의 ACID를 설명해 주세요.

원자성은 트랜잭션의 쓰기가 전부 반영되거나 전부 취소되는 것, 일관성은 제약과 규칙이 깨진 상태로 끝나지 않는 것, 격리성은 동시에 도는 트랜잭션이 서로의 중간 상태를 보지 않는 것, 지속성은 커밋된 결과가 장애 뒤에도 남는 것입니다.
원자성과 지속성은 로그를 먼저 쓰는 WAL로 구현되고(장애 뒤 redo/undo), 격리성은 락과 MVCC로, 일관성은 제약과 애플리케이션 로직이 함께 만듭니다.
예를 들어 이체에서 출금 뒤 장애가 나면 undo로 되돌리고, 커밋 뒤 장애가 나면 redo로 다시 적용합니다. 한계는 격리성이 완전하면 동시성이 떨어져 실제 DB는 격리 수준으로 타협하고, 트랜잭션 밖의 외부 시스템(결제 API)은 롤백되지 않는다는 점입니다.

- 꼬리: 커밋은 정확히 언제 "성공"이 되나요?
- 꼬리: 트랜잭션 안에서 외부 API를 호출하면 무슨 문제가 생기나요?

#### 주문 저장과 결제 API 호출을 한 트랜잭션에 넣었더니 문제가 생겼습니다. 무엇이고 어떻게 고치나요?

두 가지 문제입니다 — 결제 API 응답을 기다리는 동안 DB 락과 커넥션이 묶이고, 결제는 됐는데 그 뒤 DB 쓰기가 실패해 롤백되면 "결제만 된" 상태가 됩니다. 외부 시스템은 DB 롤백에 따라오지 않기 때문입니다.
고치는 방향은 트랜잭션을 DB 쓰기만으로 짧게 두고 외부 호출을 밖으로 빼는 것입니다. 순서를 "주문을 '결제 대기'로 커밋 → 결제 API 호출(멱등 키 포함) → 결과를 새 트랜잭션으로 반영"으로 바꾸고, 결제 뒤 반영이 실패하면 재시도하거나 결제 취소(보상)를 합니다.
확실히 하려면 "결제 요청" 이벤트를 주문과 같은 트랜잭션에서 아웃박스 표에 넣고 별도 워커가 API를 부르게 합니다. 한계는 그 사이 "결제 대기" 상태가 사용자에게 보이므로 화면과 상태 모델이 이를 다뤄야 한다는 점입니다.
