## 개념

**관계형 DB**(SQL: MySQL·PostgreSQL)는 데이터를 정해진 열을 가진 표에 넣고, 표 사이를 외래키로 잇고, 조인으로 합쳐 읽으며, 트랜잭션으로 여러 표의 변경을 한 번에 지킨다. 스키마가 먼저 있고 데이터가 거기 맞춘다. **NoSQL**은 "관계형이 아닌 것"의 통칭이라 종류가 다르다 — **문서**(MongoDB: JSON 덩어리 하나를 저장·조회), **키-값**(Redis·DynamoDB: 키로 값 하나), **와이드 컬럼**(Cassandra: 행마다 열이 달라도 되는 큰 표), **그래프**(Neo4j: 관계 탐색). 공통점은 조인·강한 스키마·(전통적으로) 다중 레코드 트랜잭션을 줄이거나 없앤 대신 **한 덩어리를 빠르게, 여러 대로 쉽게**를 택한 것이다.

선택 기준은 "무엇이 더 좋은가"가 아니라 **데이터를 어떻게 읽고 쓰나**(접근 패턴)다. 여러 표를 조합해 다양한 질문을 던지고 정합성이 생명이면 관계형. 한 덩어리를 통째로 읽고 쓰며 구조가 자주 바뀌고 쓰기·읽기가 수평 확장돼야 하면 NoSQL. 대부분의 서비스는 관계형을 기본으로 두고 특정 데이터만 NoSQL로 뺀다(폴리글랏).

#### 예시 — 같은 주문 데이터, 두 모델

```sql
-- 관계형: 정규화된 표 셋, 조인으로 합침
orders(id, member_id, status, created_at)
order_items(id, order_id, product_id, qty, price)
products(id, name, price)
SELECT o.id, p.name, i.qty FROM orders o
  JOIN order_items i ON i.order_id = o.id
  JOIN products p ON p.id = i.product_id WHERE o.member_id = 7;
```

```json
// 문서: 주문 하나가 품목까지 품은 덩어리. 한 번에 읽고 씀. 상품명은 복사됨
{ "_id": 42, "memberId": 7, "status": "PAID",
  "items": [ { "productId": 9, "name": "키보드", "qty": 1, "price": 89000 } ] }
```

#### 비교 — 무엇을 얻고 무엇을 내주나

| | 관계형(SQL) | NoSQL(문서·키-값 기준) |
|---|---|---|
| 스키마 | 먼저 정하고 마이그레이션으로 바꿈 | 문서마다 달라도 됨(스키마는 코드에 있음) |
| 조합 조회 | 조인·집계로 어떤 질문이든 | 미리 넣어 둔 모양대로만 빠름, 다른 질문은 느리거나 불가 |
| 정합성 | 외래키·제약·트랜잭션이 DB에서 강제 | 애플리케이션이 지킴(중복 데이터 갱신 책임) |
| 트랜잭션 | 여러 표 원자적 | 한 문서는 원자적, 다중 문서는 제한적(MongoDB 4.0+ 지원, 비용 큼) |
| 확장 | 읽기는 복제, 쓰기는 샤딩이 어려움 | 처음부터 파티션 키로 수평 확장 설계 |
| 잘 맞는 데이터 | 주문·결제·회원·재고(관계·정합성) | 세션·캐시·로그·이벤트·카탈로그·프로필(덩어리·대량) |

## 왜 나왔나

2000년대 후반 구글·아마존·페이스북 규모에서 관계형 DB 한 대의 쓰기 한계와 스키마 변경 비용이 문제가 됐다. 조인과 강한 일관성을 포기하면 데이터를 키로 쪼개 수백 대에 나눠 둘 수 있었고(Dynamo 2007, BigTable 2006), 개발 쪽에서는 객체(JSON)를 표로 쪼개는 불일치(임피던스 불일치)를 없애고 싶었다(MongoDB 2009). 그 뒤 관계형도 JSON 열·수평 확장(NewSQL·분산 SQL)을 얻고 NoSQL도 트랜잭션·스키마 검증을 더해 경계가 좁아졌지만, "조인과 정합성을 DB가 맡느냐 애플리케이션이 맡느냐"라는 축은 남았다.

## 확인 질문

- 설명해 보기: NoSQL을 고르는 기준을 한 문장으로?
  답: 접근 패턴이 "한 덩어리를 통째로 읽고 쓴다"로 분명하고, 조인·강한 정합성보다 유연한 구조와 수평 확장이 더 중요할 때. 그 외에는 관계형이 기본.
- 다음 상태 예측: 문서 DB에 주문마다 상품명을 복사해 넣었는데 상품명이 바뀌면?
  답: 이미 저장된 주문의 상품명은 그대로다. 그것이 의도(주문 당시 이름 보존)면 맞고, 최신 이름이 보여야 한다면 모든 주문 문서를 갱신해야 한다 — 정합성 책임이 애플리케이션으로 온 것.
- 다음 상태 예측: 관계형에서 "회원별 최근 주문 5개"가 느려서 NoSQL로 옮기자는 제안이 나왔다면 먼저 볼 것은?
  답: 인덱스(`(member_id, created_at)`)와 실행 계획. 대부분의 "관계형이 느리다"는 인덱스·쿼리 문제이고, 저장소를 바꾸면 조인·트랜잭션을 잃는다.

## 심화

### 접근 패턴이 먼저다

관계형은 "데이터를 정규화해 두면 어떤 질문이든 조인으로"라 질문을 나중에 정해도 된다. NoSQL은 "어떤 질문을 할지 먼저 정하고 그 모양대로 저장"이다 — DynamoDB 설계는 접근 패턴 목록에서 시작한다. 요구가 바뀌어 새 질문이 생기면 관계형은 인덱스 하나, NoSQL은 데이터를 다시 모양 잡아야 한다. 초기 서비스처럼 질문이 계속 바뀌는 단계에서 관계형이 기본인 이유다.

### 임베딩과 참조

문서 모델에서 관계를 표현하는 두 길. 함께 읽히고 함께 바뀌고 크기가 유한하면 임베딩(주문 안의 품목). 여러 곳에서 참조되거나 독립적으로 바뀌거나 무한히 자라면 참조(회원 ID만 저장, 필요하면 앱이 두 번 조회). 임베딩은 지역성(한 번에 읽음)을 주고, 참조는 정합성(한 곳만 갱신)을 준다 — 정규화·역정규화의 문서판이다.

### 일관성 모델

전통 NoSQL은 복제본 간 최종 일관성(방금 쓴 것을 다른 노드에서 잠시 못 볼 수 있음)이 기본이고, 읽기 옵션으로 강한 일관성을 고르면 지연·비용이 든다. 관계형의 단일 노드는 강한 일관성이 기본이고 복제 지연은 읽기 복제본에서만. "잔고를 읽고 차감"처럼 읽기-갱신이 묶여야 하는 로직을 최종 일관성 저장소에 두면 경쟁 상태가 난다 — 그런 데이터는 관계형이나 조건부 쓰기(DynamoDB `ConditionExpression`)로.

### 관계형이 NoSQL을 흡수한 부분

PostgreSQL `jsonb`·MySQL `JSON` 열은 유연한 속성(상품별 다른 옵션)을 관계형 안에서 다루고 인덱스도 건다. 읽기 복제·파티셔닝(복제·샤딩 장)으로 규모도 상당히 간다. "구조가 유연해야 한다"만으로 NoSQL을 고르기 전에 JSON 열로 되는지 먼저 본다.

### 실무에서는

- 주문·결제·회원·재고는 관계형. 세션·캐시·순위·잠금은 Redis. 로그·검색은 Elasticsearch. 이벤트 스트림은 Kafka. 하나로 다 하려 하지 않는다.
- NoSQL을 넣으면 정합성 코드(중복 갱신, 검증)와 운영(백업·복제·모니터링)이 하나 더 는다. 그 비용을 감당할 이유를 적어 둔다.
- 스키마리스는 "스키마가 없다"가 아니라 "스키마가 코드에 있다"다. 오래된 문서 형식을 읽는 코드가 계속 남는다 — 버전 필드를 둔다.
- 면접에서 "왜 NoSQL 안 썼나"에는 "접근 패턴이 관계형이고 규모가 아직 아니라서"가 정직한 답이다.

### 면접 질문

#### SQL과 NoSQL의 차이와, 어떤 기준으로 선택하나요?

관계형은 정해진 스키마·조인·트랜잭션으로 정합성을 DB가 강제하고, NoSQL(문서·키-값·와이드 컬럼·그래프)은 조인과 강한 스키마, 다중 레코드 트랜잭션을 줄이는 대신 유연한 구조·한 덩어리 접근·수평 확장을 얻습니다. 선택 기준은 접근 패턴입니다 — 여러 데이터를 조합하는 다양한 질문과 정합성이 중요하면 관계형, 한 덩어리를 통째로 읽고 쓰며 구조가 자주 바뀌고 규모가 한 대를 넘으면 NoSQL.
NoSQL은 "관계형보다 좋은 것"이 아니라 조인과 정합성 책임을 애플리케이션으로 옮기는 대가로 확장과 유연성을 산 것이기 때문입니다.
예를 들어 주문·결제는 관계형에, 세션·캐시는 Redis에, 상품 카탈로그처럼 속성이 제각각인 것은 문서 DB나 JSON 열에 둡니다. 한계는 경계가 좁아져(관계형의 JSON 열·분산 SQL, MongoDB의 트랜잭션) 이름보다 실제 보장(일관성·트랜잭션 범위)을 봐야 하고, 초기 서비스는 질문이 계속 바뀌므로 관계형이 기본이라는 점입니다.

- 오답: "NoSQL은 스키마가 없어서 편하다" — 스키마가 코드로 옮겨간 것이고, 옛 형식을 읽는 부담이 남는다.
- 오답: "확장이 필요하면 NoSQL" — 읽기 복제·인덱스·파티셔닝으로 관계형이 가는 범위가 먼저다.
- 꼬리: 문서 DB에서 임베딩과 참조는 언제 무엇을 고르나요?
- 꼬리: 최종 일관성 저장소에 두면 안 되는 데이터는?

#### 트래픽이 늘어 DB가 느립니다. NoSQL로 옮기자는 의견에 어떻게 답하나요?

먼저 "무엇이 느린가"를 봅니다 — 느린 쿼리 로그·실행 계획으로 인덱스 누락·N+1·잠금 대기인지, 읽기 부하면 캐시(Redis)·읽기 복제본으로, 특정 표만 크면 파티셔닝으로. 저장소 교체는 이것들이 안 통하고 접근 패턴이 NoSQL에 맞을 때(한 덩어리 접근, 쓰기 수평 확장) 그 데이터만 옮깁니다.
"관계형이 느리다"의 대부분은 쿼리·인덱스·캐시 문제이고, 저장소를 바꾸면 조인·트랜잭션·정합성 강제를 잃어 애플리케이션이 그 책임을 지게 되기 때문입니다.
예를 들어 상품 조회가 병목이면 Redis 캐시가 먼저이고, 초당 수만 건의 이벤트 기록이면 그 표만 Cassandra·DynamoDB 같은 쓰기 확장 저장소로. 한계는 옮긴 데이터와 남은 데이터 사이의 조인이 사라져 애플리케이션에서 합쳐야 하고, 두 저장소의 운영 비용이 든다는 점입니다.

- 오답: "MongoDB로 전부 옮기면 확장된다" — 주문·결제의 다중 문서 트랜잭션·조인이 사라지고 정합성 코드가 폭증한다.
- 꼬리: 읽기 복제본으로 해결되는 문제와 안 되는 문제는?
