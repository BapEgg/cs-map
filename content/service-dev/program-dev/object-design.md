## 개념

설계가 좋다는 말은 **바꿀 때 고칠 곳이 적고 예측 가능하다**는 뜻이다. 그것을 재는 두 자가 **응집도**와 **결합도**다. 응집도는 한 클래스(모듈)의 내용이 얼마나 한 가지 목적으로 뭉쳐 있나 — 주문 서비스가 주문 규칙만 다루면 높고, 메일 발송·PDF 생성까지 하면 낮다. 결합도는 한 클래스가 다른 클래스의 **내부**를 얼마나 알아야 하나 — 인터페이스만 알면 낮고, 필드·구현 순서까지 알면 높다. 목표는 **높은 응집, 낮은 결합**.

**SOLID**는 이 목표를 지키는 다섯 원칙이다. 단일 책임(S: 한 클래스는 한 가지 이유로만 바뀐다), 개방-폐쇄(O: 기능을 추가할 때 기존 코드를 고치지 않고 새 코드를 더한다), 리스코프 치환(L: 자식은 부모 자리에 들어가도 동작이 깨지지 않는다), 인터페이스 분리(I: 쓰는 쪽이 필요한 메서드만 있는 작은 인터페이스), 의존 역전(D: 구체 클래스가 아니라 추상에 의존한다). **패턴**은 자주 나오는 문제의 검증된 해법 — 전략은 "알고리즘을 바꿔 끼우기", 팩토리는 "어떤 구현을 만들지 숨기기".

#### 예시 — 할인 계산을 바꿔 끼우기

```java
// 결합 높음: 새 할인이 생길 때마다 OrderService를 고친다
class OrderService {
    Money discount(Order o) {
        if (o.member().isVip()) return o.total().times(0.1);
        else if (o.hasCoupon()) return o.coupon().amount();
        return Money.ZERO;
    }
}

// 전략: 할인 규칙을 인터페이스 뒤로. OrderService는 규칙의 종류를 모른다
interface DiscountPolicy { Money discount(Order o); }
class VipDiscount implements DiscountPolicy { … }
class CouponDiscount implements DiscountPolicy { … }

class OrderService {
    private final List<DiscountPolicy> policies;   // 스프링이 구현체를 전부 주입
    Money discount(Order o) {
        return policies.stream().map(p -> p.discount(o)).reduce(Money.ZERO, Money::plus);
    }
}
```

새 할인(`FirstOrderDiscount`)은 클래스 하나 추가로 끝난다(개방-폐쇄). `OrderService`는 `DiscountPolicy`라는 추상에만 의존한다(의존 역전). 할인 규칙이 바뀌는 이유와 주문 흐름이 바뀌는 이유가 분리됐다(단일 책임).

#### 비교 — 전략과 팩토리는 무엇을 푸나

| 패턴 | 푸는 문제 | 고르는 신호 | 스프링에서 |
|---|---|---|---|
| 전략 | 같은 일을 하는 방법이 여럿이고 실행 중에 고른다 | `if/switch`로 타입 분기하는 코드가 여러 곳에 반복 | 인터페이스 구현체들을 `List`·`Map`으로 주입 |
| 팩토리 | 어떤 구현을 만들지 결정하는 코드를 한 곳에 모은다 | `new` 뒤에 조건 분기, 생성 규칙이 흩어짐 | 컨테이너 자체가 팩토리. 요청 값으로 고를 땐 `Map<Type, Bean>` |
| 템플릿 메서드 | 절차는 같고 일부 단계만 다르다 | 복붙된 메서드에서 몇 줄만 다름 | 추상 클래스 상속(조합이 가능하면 전략이 낫다) |

## 왜 나왔나

프로그램은 만들 때보다 고칠 때 비용이 더 든다. 한 요구 변경이 파일 열 개를 건드리고, 한 곳을 고치면 다른 곳이 깨지는 경험이 쌓이면서 "변경이 퍼지는 구조"와 "갇히는 구조"의 차이를 이름 붙인 것이 응집·결합(1970년대 구조적 설계)이고, 객체 지향에서 그것을 다시 정리한 것이 SOLID(2000년대 초)다. 패턴은 그보다 앞서(1994) "이 문제엔 이 구조가 반복해서 잘 먹혔다"를 목록으로 만든 것이다. 즉 원칙과 패턴은 발명이 아니라 관찰이고, 문제가 없는 곳에 적용하면 이득 없이 복잡도만 든다.

## 심화

### SOLID를 실제 코드 냄새로

| 원칙 | 깨졌을 때 보이는 것 | 고치는 방향 |
|---|---|---|
| S 단일 책임 | 클래스가 커지고 import가 다양, 수정 이유가 여럿 | 바뀌는 이유별로 클래스 분리 |
| O 개방-폐쇄 | 기능 추가마다 같은 `switch`·`if`를 고침 | 전략·다형성으로 분기 제거 |
| L 리스코프 치환 | 자식에서 `throw new UnsupportedOperationException` | 상속 대신 조합, 인터페이스 재정의 |
| I 인터페이스 분리 | 구현체에 빈 메서드가 많음 | 쓰는 쪽 기준으로 인터페이스 쪼개기 |
| D 의존 역전 | 서비스가 `new MysqlUserRepository()` | 추상에 의존, 구현은 주입(IoC/DI 장) |

### 결합을 낮추는 도구들

인터페이스(구현을 모름), 의존 주입(생성을 모름), 이벤트(호출 대상을 모름 — `ApplicationEventPublisher`로 "주문됨"만 알리고 알림·통계는 각자 구독), 값 객체(원시값 대신 `Money`·`Email`로 규칙을 값에 붙임). 결합을 낮출수록 "무슨 일이 일어나는지"를 따라가기는 어려워지므로, 이벤트는 정말 독립적인 후속 처리에만.

### 패턴 남용의 신호

클래스 이름에 `Manager`·`Handler`·`Factory`·`Strategy`가 붙었는데 구현이 하나뿐이다. 추상 클래스 계층이 3단을 넘는다. 인터페이스를 열려면 구현체를 찾아 두 번 점프해야 하는데 구현체가 항상 하나다. 이럴 땐 패턴을 걷어내는 것이 설계다. 원칙은 "지금 아픈 곳"에 쓴다 — 아직 안 바뀐 코드를 위한 유연성은 추측이다.

### 스프링과의 관계

스프링 컨테이너는 의존 역전(D)을 기본으로 강제한다 — 빈은 인터페이스나 다른 빈을 주입받는다. AOP는 횡단 관심사를 분리해 단일 책임(S)을 돕는다. `@Component`가 붙은 구현체 여럿을 `List<Policy>`로 받는 것이 전략 패턴의 스프링식이고, `@Bean` 메서드가 팩토리다. 패턴을 따로 "구현"하기보다 컨테이너가 주는 형태를 쓴다.

### 실무에서는

- 새 코드를 쓸 때 "이게 바뀌면 어디를 고치나"를 한 번 묻는다. 두 곳 이상이면 응집이 낮거나 결합이 높다.
- `if (type == …)` 분기가 두 번째 파일에 나타나는 순간 전략으로 바꾼다. 한 곳뿐이면 그대로 둔다.
- 상속은 `is-a`이고 부모가 상속을 위해 설계됐을 때만(oop 장). 코드 재사용은 조합.
- 리뷰에서 원칙 이름을 들먹이기보다 "이 변경이 어디까지 퍼지나"로 말한다. 원칙은 그 판단의 근거일 뿐.

### 면접 질문

#### SOLID 원칙을 설명하고, 실제 코드에서 가장 자주 쓰는 것을 예로 들어 주세요.

단일 책임(한 클래스는 한 가지 이유로만 바뀜), 개방-폐쇄(추가는 새 코드로, 기존 코드는 안 고침), 리스코프 치환(자식은 부모 자리에 들어가도 동작이 유지됨), 인터페이스 분리(쓰는 쪽에 필요한 메서드만), 의존 역전(구체가 아니라 추상에 의존)입니다. 실무에서 가장 자주 만나는 것은 개방-폐쇄와 의존 역전으로, 타입별 `if/switch` 분기가 여러 곳에 반복될 때 인터페이스와 구현체들로 바꾸고 스프링이 구현체를 주입하게 하는 형태입니다.
다섯 원칙은 결국 "변경이 한 곳에 갇히게" 하려는 것이고, 응집도를 높이고 결합도를 낮추는 구체적 방법입니다.
예를 들어 할인 규칙을 `DiscountPolicy` 구현체 목록으로 두면 새 할인은 클래스 하나 추가로 끝나고 주문 서비스는 손대지 않습니다. 한계는 구현이 하나뿐인 곳에 인터페이스·패턴을 미리 깔면 유연성 없이 복잡도만 늘어나므로, 실제로 변경이 반복되는 지점에만 적용한다는 점입니다.

- 오답: "모든 클래스에 인터페이스를 두는 것이 SOLID다" — 의존 역전은 변경 가능성이 있는 경계에 추상을 두라는 것이지 모든 클래스에 두라는 것이 아니다.

- 꼬리: 응집도와 결합도는 SOLID와 어떤 관계인가요?

#### 결제 수단별 `switch`문이 서비스 여러 곳에 있습니다. 어떻게 바꾸고, 그 방법이 왜 나은가요?

`Payment` 인터페이스를 두고 수단별 구현체를 만든 뒤, 스프링이 구현체들을 `Map<PaymentType, Payment>`로 주입하게 하여 서비스는 요청의 타입으로 구현체를 꺼내 호출만 합니다(전략 + 컨테이너가 팩토리 역할).
수단이 늘 때 기존 서비스 코드를 고치지 않고 구현체 하나를 추가하면 끝나므로(개방-폐쇄) 분기를 빠뜨리는 버그가 사라지고, 각 수단의 규칙이 자기 클래스에 모여(응집) 테스트를 따로 할 수 있습니다.
예를 들어 `payments.get(request.type()).pay(amount)` 한 줄이 세 곳의 `switch`를 대체합니다. 한계는 수단마다 필요한 입력이 다르면 인터페이스 시그니처가 넓어지므로 요청 객체를 수단별로 나누거나 검증을 구현체 안에 두어야 하고, 분기가 한 곳뿐이라면 `switch`가 더 읽기 쉬울 수 있다는 점입니다.

- 오답: "추상 클래스 `AbstractPayment`를 만들어 상속한다" — 공통 절차가 없다면 상속은 결합만 늘린다. 역할은 인터페이스로.
- 꼬리: 스프링에서 같은 인터페이스의 빈 여럿을 `Map`으로 받는 방법은?
