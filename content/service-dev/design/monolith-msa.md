## 개념

**모놀리스**는 주문·회원·결제·상품이 하나의 애플리케이션(하나의 배포 단위, 보통 하나의 DB)에 있는 구조다. 함수 호출로 서로를 부르고 한 트랜잭션으로 묶을 수 있다. **MSA**(마이크로서비스)는 기능별로 별도 서비스로 나눠 각자 배포하고 각자 DB를 가지며 HTTP·메시지로 대화하는 구조다.

기준은 코드 크기가 아니라 **배포·운영 단위**다. MSA의 이득은 팀이 독립적으로 배포하고, 서비스별로 확장하고, 한 서비스 장애가 격리되는 것. 비용은 함수 호출이 네트워크 호출이 되어(타임아웃·재시도·멱등 장) 느리고 실패하며, DB가 나뉘어 **트랜잭션이 사라지고**, 운영할 것(배포·관측·인프라)이 서비스 수만큼 는다는 것. 그래서 순서는 모놀리스 → 안에서 모듈 경계를 분명히(**모듈러 모놀리스**) → 정말 필요한 것만 떼기다.

"주문 생성 시 재고 차감·결제"를 두 구조에서 비교해 보자.

- 모놀리스: `orderService.place()` 안에서 `stockService.decrease()`, `paymentService.pay()`를 부르고 `@Transactional` 하나로 묶는다. 결제 실패면 재고 차감도 롤백. 50ms.
- MSA: 주문 서비스가 재고 서비스에 HTTP `POST /stocks/decrease`, 결제 서비스에 `POST /payments`. 각자 DB에 각자 커밋.
- 결제가 실패했다: 재고는 이미 차감돼 커밋됐다. 되돌리려면 재고 서비스에 "다시 늘려 줘"(**보상 트랜잭션**)를 보내야 하고, 그것도 실패할 수 있다. 이것이 **사가**.
- 재고 서비스가 타임아웃: 차감됐는지 모른다 → 멱등 키로 재시도 → 그래도 안 되면 주문을 "확인 중"으로 두고 나중에 정리.
- 결과: 모놀리스에서 애노테이션 하나였던 것이 MSA에서는 보상·재시도·상태 머신이 된다. 그 비용을 감당할 이유(팀 규모, 독립 배포·확장 필요)가 있을 때만 나눈다.

## 왜 나왔나

큰 조직에서 모놀리스는 수백 명이 한 코드베이스·한 배포에 묶여 배포가 주 1회로 느려지고, 한 부분의 부하 때문에 전체를 확장해야 했으며, 한 부분의 버그가 전체를 내렸다. 서비스를 나누면 팀이 각자 속도로 갈 수 있다 — 넷플릭스·아마존이 그 규모였다. 그러나 그 이득은 조직이 클 때 크고, 비용(분산 시스템의 모든 문제)은 규모와 무관하게 든다. 그래서 "MonolithFirst"가 반동으로 나왔고, 최근에는 모놀리스 안에서 모듈 경계를 강제하는 도구(Spring Modulith)가 그 절충이다.

## 확인 질문

- 설명해 보기: 모놀리스와 MSA를 나누는 기준은?
  답: 배포·운영 단위와 DB의 분리. 한 프로세스·한 DB면 모놀리스, 서비스마다 따로 배포하고 따로 DB면 MSA. 코드를 패키지로 잘 나눈 것은 여전히 모놀리스(모듈러 모놀리스).
- 다음 상태 예측: 주문·재고·결제를 세 서비스로 나눴다. "결제 실패 시 재고 원복"은 어떻게 되나?
  답: 한 트랜잭션으로 못 묶는다. 재고 서비스에 보상 요청(원복)을 보내는 사가로 처리하고, 보상도 실패할 수 있으니 재시도·멱등·수동 정리 경로가 필요하다.
- 다음 상태 예측: 5명 팀이 첫 서비스를 MSA 8개로 시작하면?
  답: 기능 하나 만들 때마다 서비스 여러 개를 고치고 배포하며, 인프라·관측·네트워크 실패 처리에 시간을 쓴다. 이득(독립 배포)은 팀이 하나라 없다. 모놀리스로 시작해 경계가 보이면 떼는 것이 낫다.

## 심화

### 티어와 레이어 — 물리와 논리를 섞지 않기

**레이어**(layer)는 **코드 안의 논리적 구분**이다 — 표현(컨트롤러), 업무(서비스·도메인), 데이터 접근(리포지토리). 같은 프로세스 안에서 위 레이어가 아래 레이어를 부른다(레이어드 아키텍처). **티어**(tier)는 **물리적으로 떨어진 실행 단위**다 — 브라우저(클라이언트 티어), 애플리케이션 서버(앱 티어), DB 서버(데이터 티어)의 3-tier가 대표다. 티어 사이는 네트워크를 건너고, 레이어 사이는 메서드 호출이다.

| | 레이어 | 티어 |
|---|---|---|
| 나누는 것 | 코드의 책임(표현·업무·데이터 접근) | 배포·실행 위치(장비·프로세스) |
| 경계를 건너는 방식 | 메서드 호출 | 네트워크(HTTP·JDBC) |
| 바꾸면 | 코드 구조 | 인프라·비용·지연·장애 지점 |
| 예 | Controller → Service → Repository | 브라우저 → WAS → DB |

둘은 독립이다. 스프링 부트 하나(앱 티어 1개)에 레이어 3개가 있고, 그 앱을 서버 3대에 올려도 티어는 여전히 3-tier다. MSA는 **티어(배포 단위)를 기능별로 더 쪼갠 것**이고, 각 서비스 안에는 다시 레이어가 있다. "레이어를 나눴으니 확장된다"(레이어는 배포와 무관)와 "서버를 나눴으니 코드가 정리된다"(티어는 코드 구조와 무관)가 흔한 혼동이다. 면접에서 "3-tier"를 물으면 물리 배치(클라이언트·앱·DB)를, "레이어드 아키텍처"를 물으면 코드 구조(컨트롤러·서비스·리포지토리와 의존 방향)를 답한다.

### 모듈러 모놀리스

한 배포 단위 안에서 `order`, `stock`, `payment` 패키지(모듈)를 두고, 모듈끼리는 공개 API(인터페이스·이벤트)로만 부르며 다른 모듈의 리포지토리·엔티티를 직접 쓰지 않는다. Spring Modulith나 ArchUnit으로 경계 위반을 테스트에서 잡는다. 트랜잭션·배포·운영은 모놀리스의 단순함을 유지하면서, 나중에 뗄 때 경계가 이미 있다. 대부분의 서비스는 여기서 끝나도 된다.

### 나눌 때의 데이터

서비스마다 DB를 따로 두는 것이 원칙이다(DB를 공유하면 스키마가 결합돼 독립 배포가 안 된다). 그러면 조인이 사라진다 — 주문 목록에 상품명을 보이려면 API 호출·캐시·데이터 복제(이벤트로 상품명을 주문 서비스에 복사) 중 하나. 트랜잭션은 사가(순차 호출 + 보상) 또는 이벤트 기반 최종 일관성으로.

### 서비스 간 통신

동기 HTTP(gRPC)는 단순하지만 호출 사슬이 길어지면 지연이 더해지고 한 서비스 장애가 전파된다 — 타임아웃·서킷 브레이커 필수. 비동기 메시지는 분리되지만 "지금 결과"를 못 준다. 조회는 동기, 상태 변경의 후속은 비동기가 흔한 배치. API 게이트웨이가 인증·라우팅·요청 제한을 한 곳에서 하고, 트레이스 ID를 전 서비스에 전파한다.

### 나눌 이유가 있는지 묻기

- 팀이 여럿이고 서로의 배포에 발이 걸리나?
- 한 기능의 부하·기술 요구(GPU, 다른 언어)가 나머지와 크게 다른가?
- 한 부분의 장애를 반드시 격리해야 하나(결제)?
- 위 셋이 아니라면 모듈러 모놀리스.

### 실무에서는

- 첫 분리 후보는 경계가 분명하고 의존이 적은 것 — 알림, 검색, 파일 처리. 주문·결제처럼 트랜잭션이 얽힌 것은 마지막.
- 분리 전에 그 모듈이 다른 모듈의 표를 직접 읽는 곳을 전부 없앤다. 그게 안 되면 분리도 안 된다.
- 서비스 수가 늘면 인프라 표준(템플릿, 공통 라이브러리, 관측 자동 연결)이 없으면 운영이 무너진다.
- "분산 모놀리스"(나눴는데 항상 함께 배포해야 하는 상태)가 최악이다 — 둘의 비용만 합쳐진다.

### 면접 질문

#### 모놀리스와 MSA 중 무엇을 택하고, 그 근거는 무엇인가요?

기본은 모놀리스, 그 안에서 모듈 경계를 코드와 테스트로 강제하는 모듈러 모놀리스이고, 팀이 여럿이라 독립 배포가 필요하거나 특정 기능의 부하·장애 격리 요구가 나머지와 크게 다를 때만 그 부분을 떼어 냅니다.
MSA의 이득(독립 배포·확장·격리)은 조직 규모에 비례해 커지지만 비용(네트워크 호출의 실패·지연, 트랜잭션 상실과 사가, 서비스 수만큼의 운영)은 규모와 무관하게 처음부터 들기 때문입니다.
예를 들어 주문·재고·결제를 나누면 `@Transactional` 하나였던 것이 보상 트랜잭션과 재시도·멱등·상태 정리로 바뀝니다. 먼저 뗄 후보는 알림·검색처럼 경계가 분명하고 트랜잭션이 안 얽힌 것입니다. 한계는 모놀리스도 모듈 경계 없이 자라면 "큰 진흙 덩어리"가 되므로, 구조의 선택보다 경계를 지키는 규율이 먼저라는 점입니다.

- 꼬리: 모듈러 모놀리스에서 모듈 간 호출 규칙은?
- 꼬리: 분산 모놀리스란 무엇이고 왜 최악인가요?

#### 3-tier 아키텍처와 레이어드 아키텍처는 같은 말인가요?

아닙니다. 3-tier는 클라이언트·애플리케이션 서버·DB 서버처럼 **물리적으로 분리된 실행 단위**(티어)의 배치이고, 레이어드 아키텍처는 한 애플리케이션 **코드 안의 논리적 구분**(표현·업무·데이터 접근)입니다. 티어 사이는 네트워크를 건너고 레이어 사이는 메서드 호출입니다.
레이어는 코드의 책임과 의존 방향을 정리하는 것이고, 티어는 확장·장애 격리·비용을 정하는 것이라 서로 독립적으로 결정됩니다.
예를 들어 스프링 부트 앱 하나에 컨트롤러·서비스·리포지토리 세 레이어가 있고, 그 앱과 DB가 다른 서버에 있으면 티어는 둘(브라우저까지 셋)입니다. 한계는 실무에서 "티어"를 레이어 뜻으로 섞어 쓰는 경우가 많으므로, 답할 때 "물리인지 논리인지"를 먼저 구분해 말해야 한다는 점입니다.

- 오답: "컨트롤러·서비스·리포지토리가 3-tier다" — 그것은 레이어(논리)이고, 3-tier는 클라이언트·앱 서버·DB의 물리 배치다.
- 꼬리: 레이어 사이의 의존 방향은 어느 쪽이어야 하고, 왜인가요?
- 꼬리: MSA는 티어와 레이어 중 무엇을 쪼갠 것인가요?

#### 서비스를 나눈 뒤 주문·재고·결제를 어떻게 일관되게 처리하나요?

한 트랜잭션이 불가능하므로 사가로 처리합니다 — 주문 생성 → 재고 차감 → 결제를 순서대로 부르고, 중간에 실패하면 앞 단계에 보상 요청(재고 원복, 주문 취소)을 보냅니다. 조율은 주문 서비스가 상태 머신으로 하거나(오케스트레이션), 각 서비스가 이벤트에 반응해 다음을 진행합니다(코레오그래피).
각 서비스가 자기 DB에 따로 커밋하기 때문에 "전부 되거나 전부 안 되거나"를 원자적으로 만들 수 없고, 대신 "결국 정합한 상태로 수렴"을 보장하는 것입니다.
모든 호출은 타임아웃·재시도·멱등 키를 갖추고, 보상도 실패할 수 있으니 재시도 큐와 수동 정리 화면을 둡니다. 사용자에게는 중간 상태("결제 확인 중")를 보여 줍니다. 한계는 보상이 완료되기 전까지 다른 요청이 중간 상태를 볼 수 있고(격리 없음), 이 복잡도가 MSA를 택한 이유만큼 값어치가 있는지 매번 물어야 한다는 점입니다.
