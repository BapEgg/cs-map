## 개념

결제 API를 호출했는데 3초가 지나도 답이 없다. 세 가지 중 하나다 — 요청이 안 갔거나, 갔는데 처리 중이거나, 처리됐는데 응답이 안 왔거나. 클라이언트는 구분할 수 없다. 여기서 그냥 다시 보내면 세 번째 경우에 **결제가 두 번** 된다.

그래서 셋을 함께 설계한다. **타임아웃**: 무한정 기다리지 않는다 — 기다리는 동안 스레드·연결이 묶이고, 사용자는 이미 떠났다. **재시도**: 일시적 실패(네트워크 흔들림, 순간 과부하)는 잠시 뒤 다시 하면 된다 — 단, 간격을 점점 늘리고(지수 백오프) 무작위를 섞어(지터) 모두가 동시에 재시도하지 않게. **멱등성**: 같은 요청이 두 번 와도 결과가 한 번과 같게 — 클라이언트가 요청마다 고유한 **멱등 키**를 만들어 보내고, 서버는 그 키를 본 적 있으면 처리하지 않고 저장해 둔 응답을 돌려준다.

결제 요청을 따라가 보자.

- 클라이언트가 `POST /payments` 본문과 헤더 `Idempotency-Key: 7f3a…`(UUID)를 보낸다. 타임아웃 3초.
- 서버: 키 `7f3a…`가 처음 → "처리 중"으로 저장 → PG사 승인 → DB 기록 → 응답 저장 → 200. 그런데 응답이 네트워크에서 유실.
- 클라이언트: 3초 타임아웃 → 1초 뒤 같은 키로 재시도.
- 서버: 키 `7f3a…`를 이미 봤다 → 저장된 응답을 그대로 200. PG사 재승인 없음.
- 결과: 결제 한 번, 응답도 받았다. 멱등 키가 없었다면 두 번째 요청이 새 결제가 됐고, 재시도가 없었다면 사용자는 "결제됐는지 모르는" 상태로 남았다.

## 왜 나왔나

한 프로세스 안의 함수 호출은 "했거나 안 했거나" 둘뿐이다. 네트워크 너머의 호출은 "했는지 모르는" 세 번째 상태가 생긴다 — 분산 시스템의 근본 문제다. 없앨 수 없으니 "모르면 다시 하되, 다시 해도 안전하게"로 흡수한다. HTTP가 GET·PUT·DELETE를 멱등으로 정의한 것이 그 출발이고, POST에 멱등 키를 붙이는 관행(Stripe 등)이 결제·주문에 정착했다.

## 확인 질문

- 설명해 보기: 타임아웃이 난 요청의 세 가지 가능한 상태는?
  답: 서버에 도착 안 함 / 도착해서 처리 중 / 처리 완료했으나 응답 유실. 클라이언트는 구분 못 한다.
- 다음 상태 예측: 멱등 키 없이 `POST /orders`를 타임아웃 후 재시도하면?
  답: 첫 요청이 실제로 처리됐다면 주문이 두 건. 서버가 "같은 사용자·같은 상품·최근 몇 초"로 추정해 막을 수는 있지만 정확하지 않다.
- 다음 상태 예측: 외부 API가 죽어 모든 호출이 30초 타임아웃에 걸린다. 서버 스레드 200개면?
  답: 초당 7건만 와도 200개가 전부 대기 상태로 고갈된다. 타임아웃을 짧게(1~2초) 하고 서킷 브레이커로 아예 빠르게 실패시켜야 한다.

## 심화

### 멱등 키 구현

키 → (상태, 응답) 저장소는 DB 표(유니크 제약)나 Redis(TTL 24시간 등). 흐름: 키 삽입 시도 → 이미 있고 완료면 저장된 응답, 처리 중이면 409(또는 대기) → 처음이면 처리 → 응답 저장. 키 삽입과 처리 시작을 원자적으로(유니크 제약 위반으로 판단) 해야 동시에 온 두 요청이 둘 다 처리하지 않는다. 키는 요청 본문과 함께 저장해 같은 키·다른 본문은 422로 거절.

### 서버 쪽 멱등

클라이언트가 키를 안 보내도 서버가 멱등하게 만들 수 있는 경우: `PUT /users/7 {name}`(덮어쓰기), `DELETE /orders/42`(이미 없으면 그대로 성공), 상태 전이(`PAID → SHIPPED`는 이미 SHIPPED면 무시). 유니크 제약(`order_id + event_type`)이 가장 단단한 멱등 장치다 — 큐 소비자도 같은 원리.

### 재시도해도 되는 실패

연결 실패·타임아웃·503·429는 재시도. 400·401·403·404·422는 재시도해도 같으므로 안 한다. 500은 애매 — 멱등 키가 있으면 한다. 재시도는 최대 3회 안팎, 지수 백오프(0.5s, 1s, 2s) + 지터. 재시도가 폭주(retry storm)를 만들지 않게 전체 재시도 예산을 둔다.

### 서킷 브레이커·격리

상대가 계속 실패하면 재시도는 부하만 더한다. 서킷 브레이커는 실패율이 임계를 넘으면 회로를 열어 호출을 즉시 실패시키고, 일정 시간 뒤 시험 호출로 회복을 확인한다. 격리(벌크헤드)는 외부 호출마다 별도 스레드 풀·세마포어를 두어 하나가 죽어도 다른 기능의 스레드를 잡아먹지 않게 한다. Resilience4j가 이 셋을 애노테이션으로 준다.

### 실무에서는

- 모든 외부 호출에 연결 타임아웃·읽기 타임아웃을 명시한다. 기본값 "무한"인 클라이언트가 많다.
- 돈·재고가 걸린 POST에는 멱등 키. 클라이언트(앱·프런트)가 요청 생성 시 UUID를 만들어 재시도 때 같은 값을 보낸다.
- 타임아웃 층: DB 쿼리 < 외부 API < 내 API 응답 < 클라이언트. 안쪽이 바깥보다 짧게.
- 재시도는 한 층에서만. 클라이언트도 재시도하고 서버도 재시도하고 LB도 재시도하면 3×3×3 = 27배.
- 타임아웃 뒤 "처리됐는지 모름" 상태를 사용자에게 정직하게 보여 주고(“결제 확인 중”), 뒤에서 조회로 확정한다.

### 면접 질문

#### 결제가 두 번 되는 것을 어떻게 막나요?

클라이언트가 결제 요청마다 고유한 멱등 키를 만들어 헤더로 보내고, 서버는 키를 유니크 제약이 있는 저장소에 넣어 처음이면 처리하고 응답을 저장하며, 같은 키가 다시 오면 처리 없이 저장된 응답을 돌려줍니다.
타임아웃이 난 요청은 처리됐는지 안 됐는지 클라이언트가 알 수 없어 재시도가 필요한데, 재시도가 안전하려면 같은 요청을 서버가 알아봐야 하기 때문입니다.
예를 들어 첫 요청의 응답이 유실돼 재시도하면 서버는 같은 키를 보고 PG사에 재승인 없이 200을 돌려줍니다. 키 삽입과 처리 시작은 원자적이어야 동시에 온 두 요청 중 하나만 처리되고, 처리 중인 키가 다시 오면 409로 응답합니다. 한계는 클라이언트가 재시도 때 키를 새로 만들면 무용지물이고, 키 저장소에 TTL이 있어 그 뒤 재시도는 막지 못한다는 점입니다.

#### 외부 API가 느려지면서 우리 서비스 전체가 멈췄습니다. 왜 그렇고 어떻게 막나요?

요청당 스레드 모델에서 외부 호출을 기다리는 스레드가 풀을 점유하면, 그 API와 무관한 요청까지 스레드를 못 받아 전체가 멈춥니다. 타임아웃이 길거나 없으면 몇 초 만에 고갈됩니다.
막는 순서는 짧은 타임아웃(1~2초)으로 대기 상한을 두고, 서킷 브레이커로 실패율이 높으면 호출을 즉시 실패시켜 스레드를 안 쓰게 하며, 벌크헤드로 그 외부 호출 전용 스레드 풀·세마포어를 두어 다른 기능과 격리합니다.
실패했을 때의 대체 동작(캐시된 값, "잠시 후 다시", 기능 비활성)을 정해 두어 부분 장애로 끝나게 합니다. 한계는 타임아웃을 짧게 하면 정상적으로 느린 호출도 실패로 보게 되므로 p99 응답 시간을 근거로 정해야 하고, 서킷이 열린 동안의 요청은 실패이므로 그것을 사용자에게 어떻게 보여 줄지도 설계라는 점입니다.
