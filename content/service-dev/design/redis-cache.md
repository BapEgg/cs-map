## 개념

상품 상세 페이지는 초당 수천 번 읽히지만 상품 정보는 하루에 몇 번 바뀐다. 매번 DB에 가면 DB가 먼저 지친다. **Redis**는 메모리에 키-값을 두는 저장소로, 조회가 1ms 미만이고 여러 서버가 공유한다(각 서버의 로컬 캐시와 달리 서버가 여럿이어도 같은 값). 문자열 외에 해시·리스트·셋·정렬셋을 지원하고, 키마다 만료 시간(**TTL**)을 둘 수 있다.

가장 흔한 쓰임은 **cache-aside**: 읽을 때 캐시를 먼저 보고, 없으면(miss) DB에서 읽어 캐시에 넣고 돌려준다. 쓸 때는 DB를 갱신하고 캐시를 **지운다**(무효화) — 다음 읽기가 새로 채운다. 그리고 안전망으로 TTL을 둔다.

상품 42 조회를 따라가 보자.

- `GET /products/42` → 서비스가 `redis.get("product:42")` → 없음(miss).
- DB `SELECT … WHERE id = 42` → 결과를 JSON으로 `redis.set("product:42", json, EX 600)`(10분 TTL) → 응답.
- 다음 1,000번의 조회: 전부 Redis에서 hit, DB에 안 간다.
- 관리자가 가격 수정 → DB `UPDATE` → `redis.del("product:42")`.
- 다음 조회: miss → DB → 새 값으로 캐시 채움.
- 결과: DB 부하가 1/1000. 대신 무효화를 빠뜨린 경로(다른 서비스, 배치)가 있으면 최대 10분 낡은 가격이 보인다 — 그래서 TTL은 필수 안전망이다.

## 왜 나왔나

CPU 캐시와 지역성(캐시 메모리 장)의 원리 — "자주 쓰는 것을 가까이" — 를 서비스 층에 적용한 것이다. 처음엔 서버 안 메모리(로컬 캐시)에 뒀지만 서버가 여럿이면 서로 다른 값을 갖게 됐고, 세션도 서버마다 흩어졌다. 서버들 밖에 공유 메모리 저장소를 두면 둘 다 풀린다. Redis가 널리 쓰인 이유는 단순한 키-값에 자료구조·TTL·원자 연산(`INCR`, `SET NX`)이 붙어 캐시 외에도 세션·카운터·락·큐에 쓸 수 있었기 때문이다.

## 확인 질문

- 설명해 보기: cache-aside에서 쓰기 때 캐시를 갱신하지 않고 지우는 이유는?
  답: 갱신하면 "DB 쓰기와 캐시 쓰기 순서가 엇갈려 낡은 값이 남는" 경합이 생긴다. 지우면 다음 읽기가 DB의 최신값으로 채우므로 단순하고 안전하다.
- 다음 상태 예측: 인기 상품의 캐시가 만료된 순간 요청 1,000개가 동시에 오면?
  답: 1,000개가 모두 miss → DB에 같은 쿼리 1,000번(캐시 스탬피드). 락으로 한 요청만 채우게 하거나, 만료 전에 미리 갱신하거나, TTL에 무작위를 섞어 동시에 만료되지 않게 한다.
- 다음 상태 예측: Redis 메모리가 꽉 찼다. 새 키를 넣으면?
  답: 설정에 따라 다르다. `noeviction`(기본)이면 쓰기 오류, `allkeys-lru`면 오래 안 쓴 키를 밀어낸다. 캐시 용도면 후자.

## 심화

### 무엇을 캐시하나

읽기 ≫ 쓰기이고, 조금 낡아도 되는 것. 상품 정보·설정·집계·세션·인기 목록. 반대로 잔고·재고처럼 정확해야 하는 것은 캐시하지 않거나 DB를 진실로 두고 캐시는 힌트로만 쓴다. 키는 `도메인:ID:버전`처럼 규칙을 두고, 값은 JSON 등 직렬화 형식을 고정한다.

### 전략 비교

| 전략 | 읽기 | 쓰기 | 특징 |
|---|---|---|---|
| cache-aside | 캐시 miss면 앱이 DB 읽어 채움 | DB 쓰고 캐시 삭제 | 가장 흔함. 앱이 로직 소유 |
| read-through | 캐시가 DB에서 읽어 채움 | — | 캐시 라이브러리가 대신 |
| write-through | | 캐시와 DB 동시 쓰기 | 캐시가 DB와 같이 갱신됨, 쓰기 지연 ↑ |
| write-behind | | 캐시에 쓰고 DB는 나중에 | 빠르지만 유실 위험 |

스프링은 `@Cacheable`(읽기)·`@CacheEvict`(삭제)·`@CachePut`로 cache-aside를 선언으로 만든다 — AOP 프록시이므로 자기 호출 제약이 같다.

### 낡음과 일관성

캐시는 DB의 복사본이라 항상 조금 낡다. "얼마나"를 TTL이 정한다. 무효화가 완벽하면 TTL은 길어도 되고, 무효화 경로를 다 못 믿으면 TTL을 짧게. 쓰기 직후 캐시 삭제와 다른 요청의 "miss → 옛 값 읽기 → 캐시 채움"이 엇갈리면 옛 값이 남는 짧은 창이 있다. 대부분 TTL로 감수하고, 안 되면 버전 키나 지연 이중 삭제.

### Redis의 다른 쓰임

세션 저장(서버 무상태화), 카운터(`INCR` — 원자적이라 좋아요 수·요청 제한), 분산 락(`SET key val NX PX 3000` — 서버 여럿 중 하나만 배치 실행), 정렬셋 랭킹, 간단한 큐. Redis는 단일 스레드로 명령을 처리해 명령 하나하나가 원자적이지만, 그래서 `KEYS *`·큰 컬렉션 조작 하나가 전체를 막는다.

### 실무에서는

- TTL 없는 캐시 키를 두지 않는다. 무효화가 빠진 경로가 반드시 생긴다.
- 캐시 hit율을 지표로 본다. 낮으면 키 설계나 TTL이 잘못됐다.
- 캐시 장애 시 DB로 fallback하되, DB가 캐시 없는 부하를 못 견디면 그것도 장애다. 서킷 브레이커와 함께.
- 큰 값(수 MB)은 캐시하지 않는다. 네트워크와 Redis 처리 시간을 잡아먹는다.
- 스탬피드가 걱정되는 키는 만료 전 갱신(백그라운드)이나 단일 채움 락.
- 로컬 캐시(Caffeine) + Redis 2단 구성은 hit율을 더 올리지만 로컬 캐시 무효화가 어렵다 — 아주 짧은 TTL로만.

### 면접 질문

#### 캐시를 어떤 전략으로 쓰고, 데이터가 바뀌면 어떻게 하나요?

읽을 때 캐시를 먼저 보고 없으면 DB에서 읽어 채우는 cache-aside를 쓰고, 데이터가 바뀌면 DB를 갱신한 뒤 캐시 키를 삭제해 다음 읽기가 새로 채우게 하며, 안전망으로 모든 키에 TTL을 둡니다.
갱신 대신 삭제하는 이유는 DB 쓰기와 캐시 쓰기 순서가 엇갈려 낡은 값이 남는 경합을 피하기 위해서이고, TTL은 무효화를 빠뜨린 경로가 있어도 낡은 값이 영원히 남지 않게 하기 위해서입니다.
예를 들어 상품 상세는 10분 TTL로 캐시하고 관리자 수정 때 삭제합니다. 한계는 삭제와 다른 요청의 채움이 엇갈리는 짧은 창에 옛 값이 남을 수 있고, 인기 키 만료 순간에 요청이 몰리면 DB에 같은 쿼리가 쏟아지는 스탬피드가 생겨 단일 채움 락이나 사전 갱신이 필요하다는 점입니다.

#### Redis가 죽으면 서비스는 어떻게 되나요? 어떻게 대비하나요?

캐시 용도라면 모든 조회가 miss가 되어 DB로 가므로, DB가 그 부하를 견디면 느려지기만 하고 못 견디면 전체 장애가 됩니다. 세션·락 용도라면 로그인이 풀리거나 배치가 중복 실행됩니다.
캐시는 "없어도 되는 것"으로 설계돼야 하지만 실제로는 캐시가 있다는 전제로 DB 용량을 잡기 때문에, 캐시 장애가 곧 DB 장애로 번집니다.
대비는 Redis를 복제·센티널이나 클러스터로 고가용성 구성하고, 앱은 Redis 호출에 짧은 타임아웃과 서킷 브레이커를 두어 Redis 대기로 스레드가 묶이지 않게 하며, 캐시 없이 DB가 견딜 최소 트래픽을 알아 두고 필요하면 요청 제한을 겁니다. 세션은 Redis 복제로, 분산 락은 잃어도 되는 작업에만. 한계는 완전한 fallback은 없으므로 "얼마나 낡은 값까지 허용하나"를 정해 로컬 캐시에 짧게라도 남겨 두는 것이 현실적 완충이라는 점입니다.
