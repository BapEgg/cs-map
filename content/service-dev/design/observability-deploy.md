## 개념

배포 장(stages/deploy)이 "서버에 올린다"였다면 여기서는 **올린 뒤 어떻게 보고, 어떻게 끊기지 않게 바꾸나**다.

**관측**은 세 가지 신호다. **로그**: 무슨 일이 있었나의 기록(요청 ID로 한 요청분을 이을 수 있어야). **메트릭**: 숫자의 시계열 — 초당 요청 수, 응답 시간 분포(p50·p95·p99), 오류율, 스레드 풀·커넥션 풀 사용률, CPU·메모리. 알림의 근거. **트레이스**: 요청 하나가 거친 구간별 시간(LB → 서버 → DB → 외부 API) — 어디서 늦었나. 셋을 요청 ID·트레이스 ID로 잇는다.

**무중단 배포**는 새 버전을 올리는 동안 사용자가 끊김을 못 느끼게 하는 것이다. 핵심은 둘 — 서버가 여럿이고 LB가 헬스 체크로 준비된 것만 받는다(롤링), 그리고 내리는 서버는 받던 요청을 다 처리하고 죽는다(graceful shutdown).

주문 API 응답이 느려졌다는 알림부터 새 버전 배포까지를 따라가 보자.

- 알림: 메트릭 `http_server_requests p95 > 1s` 5분 지속 → 담당자 호출.
- 메트릭 보드: 오류율은 정상, 커넥션 풀 대기 시간이 함께 올랐다. DB 쪽.
- 트레이스: 느린 요청 하나를 열어 보니 `SELECT … FROM orders WHERE member_id = ?`가 900ms — 인덱스 없음.
- 로그: 트레이스 ID로 그 요청의 로그를 보니 어제 배포된 "회원별 주문 조회" 기능. 원인 확정.
- 수정 → 인덱스 추가 마이그레이션 + 배포. 롤링: 서버 3대 중 1대를 LB에서 빼고 → graceful shutdown(진행 중 요청 완료) → 새 버전 기동 → 헬스 체크 통과 → LB에 넣음 → 다음 서버. 그동안 나머지 2대가 받는다.
- 결과: 알림 → 메트릭(어느 자원) → 트레이스(어느 구간) → 로그(무슨 요청) 순으로 좁혔고, 배포 중 사용자는 끊김이 없었다. 관측이 없었다면 "느리대요"에서 시작해 추측했을 것이다.

## 왜 나왔나

서버가 한 대일 때는 SSH로 들어가 로그를 보면 됐다. 서버가 여럿이고 요청 하나가 여러 서비스를 지나자 "어느 서버의 어느 로그"를 찾을 수 없게 됐고, 그래서 로그를 모으고(중앙 집중), 숫자로 요약하고(메트릭), 요청 ID로 잇는(트레이스) 체계가 필요했다. 배포도 마찬가지 — 한 대를 내리면 서비스가 멈추던 시절에서, 여러 대를 한 대씩 바꾸고 문제가 보이면 되돌리는 방식으로 옮겨 갔다. 관측이 있어야 "문제가 보이면"이 가능하다.

## 확인 질문

- 설명해 보기: 로그·메트릭·트레이스는 각각 어떤 질문에 답하나?
  답: 로그 — 무슨 일이 있었나(사건), 메트릭 — 지금 얼마나 정상인가(숫자·추세·알림), 트레이스 — 이 요청은 어디서 시간을 썼나(구간).
- 다음 상태 예측: 평균 응답 시간은 100ms인데 사용자 불만이 많다. 무엇을 봐야 하나?
  답: p95·p99. 평균은 소수의 매우 느린 요청을 가린다. 1%가 5초면 평균은 거의 안 움직이지만 100명 중 1명은 5초를 겪는다.
- 다음 상태 예측: 롤링 배포 중 새 버전이 DB 열 `phone`을 `mobile`로 이름을 바꿨다. 구 버전 서버가 아직 돌고 있다면?
  답: 구 버전의 `phone` 쿼리가 실패한다. 스키마 변경은 "열 추가 → 양쪽 쓰기 → 코드 전환 → 옛 열 삭제"처럼 두 버전이 공존해도 되게 단계로 나눈다.

## 심화

### 네 가지 골든 시그널

지연(latency, p95·p99), 트래픽(초당 요청), 오류(오류율, 5xx), 포화(saturation — 스레드 풀·커넥션 풀·CPU·큐 길이). 대시보드 첫 화면은 이 넷이면 된다. 알림은 "사용자가 느끼는 것"(오류율·지연)에 걸고, 포화는 경고로. CPU 80%는 사용자가 못 느끼면 알림이 아니다.

### 로그를 쓸모 있게

한 줄에 한 사건, 구조화(JSON), 요청 ID·사용자 ID·트레이스 ID를 MDC로 자동 포함. 레벨: ERROR는 사람이 봐야 할 것만, WARN은 예상된 실패(외부 타임아웃), INFO는 주요 사건(주문 생성), DEBUG는 개발용. 개인정보·토큰은 마스킹. 로그가 너무 많으면 비용과 노이즈 — 샘플링.

### 배포 방식

| 방식 | 하는 일 | 장점 | 주의 |
|---|---|---|---|
| 롤링 | 한 대(또는 일부)씩 교체 | 추가 서버 불필요 | 두 버전 공존, 되돌리기 느림 |
| 블루/그린 | 새 환경 전체를 띄우고 LB를 한 번에 전환 | 즉시 되돌림 | 서버 2배, DB는 공유 |
| 카나리 | 새 버전에 트래픽 1~10%만 → 지표 보고 확대 | 문제를 작은 범위에서 발견 | 지표 자동 비교 필요 |

셋 다 헬스 체크와 graceful shutdown이 전제다. 스프링 부트는 `server.shutdown=graceful`과 Actuator `/health`(readiness·liveness 분리)를 준다.

### 두 버전이 공존하는 순간

롤링·카나리 중에는 구·신 버전이 같은 DB와 같은 클라이언트를 상대한다. 그래서 DB 변경은 **하위 호환**(열 추가는 되고 이름 변경·삭제는 단계로), API 변경은 **추가만**(필드 삭제·의미 변경은 버전 올리기), 큐 메시지도 양쪽이 읽을 수 있게. "배포 = 코드만 바뀜"이 아니라 "배포 = 코드·스키마·메시지의 호환 계획".

### 실무에서는

- 새 기능을 배포하기 전에 "이 기능이 잘못되면 어느 지표가 움직이나"를 정하고 그 지표를 보드에 올린다.
- 기능 플래그로 배포와 공개를 분리한다. 배포는 했지만 꺼 둔 채로 → 일부 사용자에게 켬 → 문제면 끔(배포 없이).
- 되돌리기(rollback)는 앞으로 나가기보다 빨라야 한다. 이전 이미지를 바로 올릴 수 있게.
- 알림은 적게, 실제 조치가 필요한 것만. 무시되는 알림이 늘면 중요한 것도 무시된다.
- 장애 뒤에는 원인·타임라인·재발 방지를 적는 회고(포스트모템). 사람 탓이 아니라 "왜 시스템이 그걸 허용했나".

### 면접 질문

#### 장애가 났을 때 어떻게 원인을 찾나요?

알림이 가리키는 지표(오류율·지연)에서 시작해 메트릭 보드로 어느 자원이 포화됐는지(스레드 풀·커넥션 풀·DB·외부 API) 좁히고, 트레이스로 느린 요청 하나의 구간별 시간을 보고 어느 호출인지 찾은 뒤, 트레이스 ID로 그 요청의 로그를 읽어 무슨 입력·무슨 코드였는지 확정합니다. 최근 배포·설정 변경이 있었는지를 먼저 보는 것이 가장 빠릅니다.
메트릭은 "무엇이" 이상한지, 트레이스는 "어디서", 로그는 "왜"에 답하므로 이 순서로 좁히면 추측 없이 갑니다.
예를 들어 p95 상승 → 커넥션 풀 대기 증가 → 트레이스에서 900ms 쿼리 → 어제 배포된 기능의 인덱스 누락, 식입니다. 한계는 이 셋이 평소에 수집·연결돼 있어야 하고(요청 ID 전파), 없으면 장애 중에 붙일 수 없어 스레드 덤프와 DB 프로세스 목록 같은 즉석 도구에 의존하게 된다는 점입니다.

- 꼬리: 평균 대신 p99를 보는 이유는?
- 꼬리: 알림은 어떤 지표에 거나요?

#### 무중단 배포를 하려면 무엇이 필요하고, DB 스키마 변경은 어떻게 하나요?

서버가 둘 이상이고 로드밸런서가 헬스 체크로 준비된 서버에만 트래픽을 보내며, 내려가는 서버는 새 요청을 거절하고 진행 중 요청을 마친 뒤 종료(graceful shutdown)해야 합니다. 그 위에서 한 대씩 교체(롤링)하거나 새 환경으로 전환(블루/그린)하거나 일부 트래픽부터(카나리) 갑니다.
배포 중 구·신 버전이 같은 DB를 함께 쓰는 순간이 반드시 있기 때문에, 스키마 변경은 두 버전 모두와 호환되게 단계로 나눕니다.
열 이름 변경이라면 새 열 추가 → 코드가 양쪽에 쓰기 → 데이터 이관 → 코드가 새 열만 읽기 → 옛 열 삭제, 배포를 여러 번에 걸쳐 합니다. 한계는 단계가 늘어 느리고 중간 상태의 코드가 복잡해지므로, 잦은 이름 변경보다 처음부터 열을 잘 짓고 삭제는 서두르지 않는 것이 현실적이라는 점입니다.

- 꼬리: readiness와 liveness 헬스 체크는 무엇이 다른가요?
- 꼬리: 기능 플래그는 배포와 무엇을 분리하나요?
