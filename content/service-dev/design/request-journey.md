## 개념

브라우저에 `https://shop.example/orders/42`를 치면 이런 일이 순서대로 일어난다. **DNS**로 도메인을 IP로 바꾸고(캐시돼 있으면 생략), 그 IP와 **TCP 연결**을 맺고(3-way), **TLS 핸드셰이크**로 암호화 통로를 연다. **로드밸런서**(또는 리버스 프록시·게이트웨이)가 요청을 받아 여러 서버 중 하나에 넘긴다. 서버(Tomcat)는 **스레드 풀**의 스레드 하나에 요청을 맡기고, 필터 → 컨트롤러 → 서비스가 돌며, DB가 필요하면 **커넥션 풀**에서 연결을 빌려 쿼리를 보내고, DB는 **인덱스**로 행을 찾아 돌려준다. 응답은 같은 길을 거꾸로 — JSON 직렬화 → LB → TLS → 브라우저 렌더링.

응답 시간은 이 구간들의 **합**이다. 어느 구간이 얼마인지 모르면 "느리다"를 고칠 수 없다.

`GET /orders/42`의 여정을 구간별 시간과 함께 따라가 보자(대략의 감각).

- DNS 조회: 브라우저·OS 캐시에 있으면 0, 없으면 수십 ms.
- TCP + TLS 연결: 왕복 2~3회, 국내 서버면 수십 ms. keep-alive로 이미 열린 연결이 있으면 0.
- LB → 서버 전달: 1ms 안팎. LB는 서버 상태(헬스 체크)를 보고 죽은 서버는 뺀다.
- 서버 스레드 배정: 풀에 여유가 있으면 즉시, 풀이 꽉 차면 큐에서 대기(이 시간은 앱 로그에 안 찍힌다).
- 필터(인증 토큰 검증) → 컨트롤러 → 서비스: 순수 계산은 1ms 미만.
- 커넥션 풀에서 연결 빌림 → `SELECT … WHERE id = 42`: 인덱스 조회는 1ms 안팎, 풀이 비면 대기.
- 직렬화 → 응답 전송 → 브라우저: 수 ms + 네트워크.
- 결과: 정상이면 전체 20~100ms. 200ms를 넘으면 어느 구간인지 찾는다 — 보통 DB(인덱스 없음, N+1) 또는 대기(스레드 풀·커넥션 풀·외부 API).

## 왜 나왔나

각 구간은 서로 다른 단원(네트워크, OS, DB, 스프링)에서 따로 배운다. 그런데 장애와 성능 문제는 늘 "구간 사이"에서 생긴다 — 커넥션 풀이 작아 스레드가 기다리고, 스레드가 다 기다려 LB가 타임아웃을 내고, LB가 재시도해 부하가 두 배가 되는 식이다. 전체 길을 한 줄로 그려 놓아야 "지금 어디가 병목인가"를 물을 수 있다. 이 장이 서비스 설계의 첫 장인 이유다.

## 확인 질문

- 설명해 보기: 브라우저가 서버에 첫 요청을 보내기 전에 이미 일어난 일 세 가지는?
  답: DNS 조회(도메인 → IP), TCP 연결(3-way 핸드셰이크), TLS 핸드셰이크(암호화 키 합의).
- 다음 상태 예측: 커넥션 풀 크기가 10인데 느린 쿼리(3초)를 내는 요청이 동시에 30개 오면?
  답: 10개만 DB에 가고 20개는 풀을 기다린다. 기다리는 동안 요청 스레드도 묶여 스레드 풀까지 고갈될 수 있다. 다른 빠른 API도 함께 느려진다.
- 다음 상태 예측: 로드밸런서 뒤 서버 3대 중 1대가 응답이 없다. 사용자는?
  답: 헬스 체크가 실패를 감지할 때까지(수초~수십 초) 1/3의 요청이 타임아웃을 겪고, 그 뒤엔 나머지 2대로만 간다.

## 심화

### 각 구간을 담당하는 단원

| 구간 | 하는 일 | 단원 | 흔한 병목 |
|---|---|---|---|
| DNS | 이름 → IP | ip-port-dns | TTL 만료 직후 조회 지연 |
| TCP·TLS | 신뢰 연결·암호화 | tcp-udp, https-tls | 연결을 매번 새로 맺음(keep-alive 없음) |
| LB·프록시 | 분배·헬스 체크·TLS 종료 | proxy | 타임아웃 설정 불일치, 재시도 폭주 |
| 서버 스레드 | 요청당 스레드 | thread-pool, mvc-request-flow | 느린 I/O로 풀 고갈 |
| 커넥션 풀 | DB 연결 재사용 | 커넥션 풀 | 풀 크기 < 동시 쿼리 |
| DB | 저장·조회 | db-index, transaction-acid | 인덱스 없음, 락 대기 |
| 직렬화 | 객체 → JSON | mvc-request-flow | 지연 로딩 N+1 |

### 어디서 늦었나 — 추적

요청 ID를 LB나 첫 필터에서 발급해 로그마다 찍고(MDC), 구간마다 시작·끝 시각을 남기면(트레이스) 한 요청의 타임라인이 나온다. 브라우저 개발자 도구의 Timing 탭은 DNS·연결·TTFB(첫 바이트까지)·다운로드를 나눠 보여 준다. TTFB가 길면 서버 안, 다운로드가 길면 응답 크기·네트워크. 서버 안은 APM(트레이스)이나 스레드 덤프로 어느 호출에서 `WAITING`인지 본다.

### 타임아웃의 층

브라우저 → LB → 서버 → DB 각각 타임아웃이 있다. 바깥이 안쪽보다 짧으면 바깥은 포기했는데 안쪽은 계속 일해 자원을 낭비하고, 바깥이 재시도하면 같은 일이 두 번 돈다. 원칙은 **안쪽으로 갈수록 짧게** — DB 쿼리 타임아웃 < 서비스의 외부 호출 타임아웃 < LB 타임아웃 < 클라이언트 타임아웃.

### 서버가 여럿이면

LB 뒤에 서버가 여럿이면 어느 서버로 갈지 모른다. 그래서 서버는 **무상태**여야 한다 — 세션은 Redis에, 파일은 오브젝트 스토리지에, 스케줄러는 한 대만 돌게(분산 락). 이 제약이 뒤 장들(인증, 캐시, 큐)의 설계를 정한다.

### 실무에서는

- 새 API를 만들면 "이 요청이 DB에 몇 번 가고 외부 호출이 몇 번인가"를 센다. 그것이 응답 시간의 대부분이다.
- 커넥션 풀·스레드 풀 크기는 함께 정한다. 스레드 200에 커넥션 10이면 190개는 기다린다.
- keep-alive와 HTTP/2를 켠다. 연결 수립 비용이 요청마다 붙지 않게.
- 헬스 체크 엔드포인트(`/actuator/health`)는 DB까지 확인하되 가볍게. LB가 이걸로 서버를 뺀다.
- 브라우저 Timing과 서버 로그의 시간이 크게 다르면 그 사이(LB·네트워크)를 의심한다.

### 면접 질문

#### 브라우저에 URL을 입력하면 무슨 일이 일어나나요?

DNS로 도메인을 IP로 바꾸고, TCP 3-way 핸드셰이크와 TLS 핸드셰이크로 암호화 연결을 연 뒤 HTTP 요청을 보냅니다. 로드밸런서가 서버 하나에 넘기면 Tomcat이 스레드 풀의 스레드에 맡기고, 필터 → 컨트롤러 → 서비스가 돌며 커넥션 풀의 연결로 DB에 쿼리하고, 결과를 JSON으로 직렬화해 같은 길을 거슬러 응답하고 브라우저가 렌더링합니다.
각 구간이 독립된 계층이라 어느 하나가 느리면 응답 시간에 그대로 더해지고, 병목은 대개 DB 쿼리와 풀 대기입니다.
예를 들어 keep-alive가 없으면 요청마다 연결 수립 왕복이 붙고, 커넥션 풀이 작으면 스레드가 기다리다 스레드 풀까지 고갈됩니다. 한계는 여기서 CDN·브라우저 캐시·HTTP/3 같은 변형을 생략했고, 서버가 여럿이면 무상태 제약이 따라온다는 점입니다.

#### 특정 시간대에 전체 API가 느려집니다. 어떻게 접근하나요?

전체가 함께 느리면 특정 코드보다 공유 자원의 포화를 봅니다 — 스레드 풀(busy threads), 커넥션 풀(대기 수), DB(CPU·락 대기·느린 쿼리 로그), 외부 API 지연입니다. 그 시간대에 무엇이 도는지(배치, 캐시 만료, 트래픽 피크)도 봅니다.
요청당 스레드 모델에서는 느린 요청 몇 개가 풀을 점유하면 빠른 요청까지 기다리기 때문에, 원인 API 하나가 전체를 느리게 만듭니다.
트레이스로 그 시간대 느린 요청의 구간별 시간을 보고, 스레드 덤프로 대부분의 스레드가 무엇을 기다리는지 확인합니다. 커넥션 풀 대기면 풀 크기·느린 쿼리, 외부 호출이면 타임아웃·서킷 브레이커·격리 풀입니다. 한계는 지표가 없으면 추측뿐이므로, 풀 사용률·응답 시간 분포(p95)·DB 대기를 평소에 수집해 둬야 한다는 점입니다.
