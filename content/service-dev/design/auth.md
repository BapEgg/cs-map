## 개념

**인증**(authentication)은 "당신이 누구인지"를 확인하는 것이다 — 아이디·비밀번호, 소셜 로그인, 토큰. 실패하면 **401**. **인가**(authorization)는 "그 사람이 이 자원에 이 행동을 해도 되는지"다 — 관리자만, 본인 주문만. 실패하면 **403**. 이름이 비슷해 헷갈리지만 순서와 위치가 다르다: 인증은 요청 입구(필터)에서 한 번, 인가는 컨트롤러·서비스에서 자원마다.

토큰 기반이면 로그인 때 짧은 **액세스 토큰**(15분~1시간)과 긴 **리프레시 토큰**(며칠~주)을 준다. 액세스 토큰은 매 요청에 실어 보내고 서버는 서명만 확인한다(DB 안 감). 만료되면 리프레시 토큰으로 새 액세스 토큰을 받는다. 리프레시 토큰은 서버가 저장해 두어 탈취 시 무효화할 수 있다.

`DELETE /orders/42`(주문 취소)를 따라가 보자.

- 필터: `Authorization: Bearer …` 헤더의 JWT 서명·만료를 확인. 없거나 틀리면 **401**로 끝, 컨트롤러 안 감. 맞으면 `SecurityContext`에 사용자 7번을 둔다.
- 컨트롤러: `@PreAuthorize("hasRole('USER')")` — 역할 확인. 통과.
- 서비스: 주문 42를 조회해 `order.memberId == 7`인지 확인. 다른 사람 주문이면 **403**(또는 존재를 숨기려면 404).
- 취소 실행 → 200.
- 결과: "로그인 안 됨"은 필터가 401로, "남의 것"은 서비스가 403으로 걸렀다. 인가를 역할만 보고 소유자 확인을 빠뜨리면 로그인한 누구나 남의 주문을 취소할 수 있다 — 가장 흔한 보안 구멍(IDOR).

## 왜 나왔나

HTTP는 무상태라 매 요청이 "누구인지"를 증명해야 했고(쿠키·세션·JWT 장), 서버가 여럿이면 세션을 공유하거나 서버가 기억하지 않는 토큰이 필요했다. 인증과 인가를 나눈 것은 실패 이유를 클라이언트에 정확히 알리고(다시 로그인 vs 권한 없음), 인증 로직을 한 곳(필터)에 모아 컨트롤러가 "이미 확인된 사용자"만 다루게 하기 위해서다.

## 확인 질문

- 설명해 보기: 401과 403의 차이를 한 문장으로?
  답: 401은 "누구인지 모르겠다(다시 로그인)", 403은 "누구인지는 알지만 이건 안 된다".
- 다음 상태 예측: 로그인한 사용자가 남의 주문을 `GET /orders/99`로 조회하면 어떤 확인이 어디서 필요한가?
  답: 필터의 인증은 통과한다. 서비스에서 주문 99의 소유자가 현재 사용자인지 확인해 아니면 403(또는 404). 역할 확인만으로는 못 막는다.
- 다음 상태 예측: 액세스 토큰 만료가 15분인데 사용자가 30분째 쓰고 있다. 어떻게 계속 쓰나?
  답: 클라이언트가 401을 받으면 리프레시 토큰으로 `/auth/refresh`를 불러 새 액세스 토큰을 받고 원래 요청을 재시도한다. 사용자는 모른다.

## 심화

### Spring Security의 자리

서블릿 필터 체인에 `SecurityFilterChain`을 끼운다. 인증 필터가 토큰·세션을 읽어 `Authentication` 객체를 `SecurityContextHolder`(ThreadLocal)에 두면 이후 컨트롤러가 `@AuthenticationPrincipal`로 꺼낸다. 인가는 URL 단위(`requestMatchers("/admin/**").hasRole("ADMIN")`)와 메서드 단위(`@PreAuthorize`) — 메서드 단위는 AOP 프록시라 자기 호출 제약이 같다. 필터에서 난 인증 실패는 `AuthenticationEntryPoint`가 401을, 인가 실패는 `AccessDeniedHandler`가 403을 만든다(`@ExceptionHandler`가 못 잡는 자리).

### 비밀번호 저장

평문·단순 해시(SHA-256)는 금지. bcrypt·argon2처럼 느리게 설계된 해시에 솔트를 넣어 저장하고(`PasswordEncoder`), 비교는 같은 해시로. 유출돼도 역산이 비싸게. "비밀번호 찾기"는 원래 값을 돌려줄 수 없으므로 재설정 링크다.

### 토큰 탈취에 대비

액세스 토큰은 짧게, 리프레시 토큰은 서버에 저장(Redis·DB)하고 사용 때마다 교체(rotation) — 재사용이 감지되면 그 사용자의 토큰을 전부 무효화. 브라우저에서는 `HttpOnly; Secure; SameSite` 쿠키에 담아 스크립트가 못 읽게. 로그아웃은 리프레시 토큰 삭제 + (필요하면) 액세스 토큰 블랙리스트.

### 소셜 로그인(OAuth 2.0)

비밀번호를 우리가 받지 않고 구글·카카오가 인증한 뒤 우리에게 "이 사용자가 맞다"는 코드를 준다. 우리는 코드를 토큰으로 바꿔 사용자 정보를 받고, 우리 서비스의 계정과 연결한 뒤 우리 토큰을 발급한다. 이후 요청은 우리 토큰으로 — 소셜 토큰을 매 요청에 쓰지 않는다.

### 실무에서는

- 인가는 "역할" + "소유자" 둘 다. 목록 조회는 `WHERE member_id = :me`를 쿼리에 박아 처음부터 남의 것을 안 가져온다.
- 존재 여부를 숨겨야 하는 자원(다른 사용자의 주문)은 403 대신 404를 준다.
- 관리자 API는 URL 경로(`/admin/**`)로 분리해 필터 단에서 막는다. 메서드마다 붙이면 빠뜨린다.
- 인증 실패 로그에 토큰 값을 남기지 않는다. 사용자 ID·사유·IP만.
- 게이트웨이(API Gateway)가 있으면 인증을 거기서 한 번 하고 서버들에는 검증된 사용자 ID를 헤더로 넘긴다. 서버끼리 내부 망이라는 전제.

### 면접 질문

#### 인증과 인가의 차이, 그리고 각각 어디서 처리하나요?

인증은 "누구인가"를 확인하는 것으로 실패 시 401, 인가는 "그 사람이 이 자원에 이 행동을 해도 되는가"로 실패 시 403입니다. 인증은 요청 입구의 필터(Spring Security 필터 체인)에서 한 번 하고, 인가는 URL 단위 규칙과 컨트롤러·서비스의 자원별 확인(역할 + 소유자)으로 합니다.
인증을 한 곳에 모으면 컨트롤러는 "이미 확인된 사용자"만 다루면 되고, 인가는 자원마다 규칙이 달라 그 자원을 아는 자리에서 해야 하기 때문입니다.
예를 들어 `DELETE /orders/42`는 필터가 토큰을 확인해 사용자를 두고, 서비스가 주문 42의 소유자가 그 사용자인지 확인합니다. 한계는 역할만 확인하고 소유자 확인을 빠뜨리면 로그인한 누구나 남의 자원을 다루는 구멍(IDOR)이 생기고, 필터 단의 예외는 `@ExceptionHandler`가 못 잡아 별도 핸들러가 필요하다는 점입니다.

- 꼬리: 존재하지 않는 자원과 권한 없는 자원의 응답을 왜 같게 두기도 하나요?
- 꼬리: `@PreAuthorize`가 동작하지 않는 경우는?

#### JWT를 쓰면 로그아웃과 토큰 탈취는 어떻게 처리하나요?

JWT는 서버가 기억하지 않아 만료 전엔 회수할 수 없으므로, 액세스 토큰을 짧게(15분 안팎) 두고 긴 리프레시 토큰은 서버에 저장해 두어 로그아웃·탈취 시 리프레시 토큰을 삭제하면 그 뒤 재발급이 막히게 합니다.
서버가 아무것도 기억하지 않는 장점을 액세스 토큰에서만 취하고, 회수 가능성은 리프레시 토큰 쪽에 두는 절충입니다.
탈취 대비로 리프레시 토큰은 사용할 때마다 교체하고 옛 토큰이 다시 쓰이면 전부 무효화하며, 브라우저에서는 `HttpOnly; Secure; SameSite` 쿠키에 담습니다. 즉시 차단이 꼭 필요하면 액세스 토큰 블랙리스트를 Redis에 두지만, 그러면 매 요청에 조회가 생겨 JWT의 장점이 줄어듭니다. 한계는 어떤 방식이든 액세스 토큰 만료까지의 창은 남으므로 그 길이가 보안과 편의의 조절점이라는 점입니다.

- 꼬리: 세션 방식과 비교해 JWT가 불리한 경우는?
