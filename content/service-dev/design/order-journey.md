## 개념

인기 공연 좌석 A-12가 딱 하나 남았고, 1,000명이 같은 순간 "예매하기"를 누른다. 한 명만 성공해야 하고, 나머지에게는 빠르게 "매진"을 알려야 하며, 성공한 사람은 결제와 알림까지 받아야 한다. 이 요구를 만족시키는 길이 곧 이 앱의 목차다.

큰 단계는 넷이다. **들어오기**(브라우저 → 네트워크 → 서버 스레드, 인증·검증), **좌석 확보**(트랜잭션 안에서 락으로 한 명만), **결제·확정**(외부 호출, 멱등, 타임아웃), **후속**(큐로 알림·집계, 캐시 무효화, 관측). 각 단계가 어느 단원인지 괄호로 표시했다.

1,000명의 클릭이 처리되는 과정을 따라가 보자.

- 클릭 → `POST /reservations {seat: "A-12"}` + `Authorization` + `Idempotency-Key`. DNS·TLS는 이미 열린 연결 재사용(요청의 전체 여정, HTTPS).
- LB가 서버 3대에 나눔. 각 Tomcat이 스레드 풀에서 스레드를 꺼내 맡김 — 1,000개 동시면 풀 200 × 3 = 600개는 처리, 400개는 큐 대기(스레드 풀, MVC 요청 흐름).
- 인증 필터가 JWT 검증 → 사용자 확정. 컨트롤러가 본문 검증(인증·인가).
- 서비스 `@Transactional reserve()` 시작 → 커넥션 풀에서 연결(스프링 트랜잭션, 커넥션 풀).
- `SELECT * FROM seats WHERE id = 'A-12' FOR UPDATE` — 행 락. 1,000개 트랜잭션 중 하나만 락을 얻고 나머지 999개는 **대기**(DB 락, 경쟁 상태, 임계 구역).
- 락을 얻은 트랜잭션: `status = AVAILABLE` 확인 → `RESERVED`로 갱신(변경 감지) → 예약 행 INSERT → 커밋 → 락 해제(영속성 컨텍스트, 트랜잭션·ACID).
- 다음 대기자가 락을 얻음 → `status = RESERVED` → `SeatTakenException` → 409 "매진". 999명이 차례로 이 경로 — 대기가 길어지지 않게 락 타임아웃 짧게, 또는 애초에 캐시에서 "남은 좌석 0"이면 DB에 안 가게(Redis·캐시).
- 성공자: 결제 서비스 호출, 타임아웃 3초, 멱등 키 전달. 응답 유실 시 같은 키로 재시도(멱등성·재시도·타임아웃). 결제 실패면 예약 취소(보상, 모놀리스/MSA).
- 커밋 뒤 `ReservationConfirmed` 이벤트 → 큐 → 알림 소비자가 문자 발송, 집계 소비자가 판매 통계(메시지 큐). 좌석 현황 캐시 키 삭제(캐시 무효화).
- 응답 201 → 브라우저 렌더링. 전 과정에 트레이스 ID가 붙어 있고, p95·오류율·락 대기 시간이 보드에 오른다(관측과 배포).
- 결과: 성공 1명, 409 999명, 이중 예약 0, 이중 결제 0. 각 단계의 실패는 그 단계의 장치(락·멱등·재시도·큐·보상)가 흡수했다.

## 왜 나왔나

앞 단원들은 부품을 하나씩 설명했다. 그런데 면접에서, 그리고 실제 설계에서 받는 질문은 "예매 시스템을 설계해 보세요"처럼 부품이 아니라 조립이다. 어느 단계에 어느 부품이 왜 들어가는지를 한 시나리오로 꿰어 보면 부품이 기억되고, 빠진 부품(멱등 키를 안 받았다면? 락이 없었다면?)이 무엇을 망가뜨리는지가 보인다. 이 장이 마지막인 이유다 — 지도 전체를 한 번에 밟는다.

## 확인 질문

- 설명해 보기: 1,000명 중 한 명만 좌석을 얻게 하는 장치는 어느 층에 있나?
  답: DB의 행 락(`FOR UPDATE`) 또는 유니크 제약 — 서버가 여럿이라 서버 안의 `synchronized`로는 안 된다. 서버 밖의 공유 지점(DB·Redis 분산 락)에서만 "하나"를 보장한다.
- 다음 상태 예측: 결제 서비스가 타임아웃됐는데 멱등 키 없이 재시도하면?
  답: 첫 요청이 실제로 결제됐다면 두 번 결제. 멱등 키로 재시도해야 결제 서비스가 같은 요청으로 알아보고 한 번만 처리한다.
- 다음 상태 예측: 알림 발송을 큐가 아니라 `reserve()` 트랜잭션 안에서 했다면?
  답: 문자 서버 응답을 기다리는 동안 행 락과 DB 연결이 묶여 999명의 대기가 그만큼 길어지고, 문자 서버 장애가 예매 장애가 되며, 롤백돼도 문자는 나간다.

### 락 대신 다른 길

행 락은 단순하고 정확하지만 999명이 줄을 선다. 대안 — **낙관적 락**: `UPDATE seats SET status='RESERVED', version=version+1 WHERE id='A-12' AND status='AVAILABLE' AND version=3`, 영향 행 0이면 실패. 대기 없이 즉시 409. **유니크 제약**: `reservations(seat_id)` 유니크 → INSERT 경쟁에서 하나만 성공. **Redis 선점**: `SET seat:A-12 user7 NX PX 300000`로 5분 선점 후 결제 → DB 확정. 좌석 수가 많고 경합이 심하면(티켓팅) Redis 선점 + 대기열이 흔하다.

### 재고 차감으로 바꾸면

"좌석 하나"가 아니라 "재고 100개"면 `UPDATE stocks SET qty = qty - 1 WHERE id = ? AND qty > 0` 한 줄이 원자적이라 락 대기가 짧다. 100개까지는 성공, 그 뒤는 영향 행 0 → 매진. 조회 후 갱신(`SELECT` 뒤 `UPDATE`)으로 나누면 경쟁 상태 — 격리 수준 장의 lost update.

### 전 과정의 타임아웃과 실패

클라이언트 10초 > LB 8초 > 서버 API 5초 > 결제 호출 3초 > DB 락 대기 1초. 락 대기 1초를 넘긴 999명 중 일부는 `LockWaitTimeout` → 409로 빠르게. 결제 3초 초과 → 재시도 1회 → 그래도 실패면 예약을 `PENDING`으로 두고 "결제 확인 중" 응답 → 배치가 결제 서비스에 조회해 확정 또는 취소. 사용자에게 "모른다"를 정직하게.

### 실무에서는

- 설계 리뷰는 이 시나리오처럼 "요청 하나를 끝까지" 따라가며 각 단계에 "여기서 실패하면?"을 묻는다.
- 부하 테스트는 "같은 좌석에 1,000명"으로 — 평균 트래픽이 아니라 최악의 경합.
- 락 대기 시간·락 타임아웃 수·결제 재시도 수·큐 지연을 지표로 둔다. 이 시나리오의 병목이 거기서 보인다.
- 처음부터 MSA·Redis·Kafka를 다 쓰지 않는다. 모놀리스 + DB 락 + `AFTER_COMMIT`으로 시작해 경합·부하가 실제로 보이면 하나씩 바꾼다.
- AI에게 "예매 API 만들어 줘"라고 시킨 뒤 위 대응표의 "빠지면" 열로 결과를 검토한다. 그것이 이 앱을 만든 이유다.

### 면접 질문

#### 인기 공연 좌석 예매 시스템을 설계해 보세요. 같은 좌석을 동시에 많은 사람이 누릅니다.

요청은 LB → 무상태 서버(JWT 인증) → 서비스 트랜잭션으로 들어오고, 좌석 확보는 서버 밖 공유 지점에서 한 명만 성공하게 합니다 — DB 행 락(`FOR UPDATE`) 또는 조건부 UPDATE(낙관적 락)나 유니크 제약, 경합이 극심하면 Redis `SET NX`로 선점 후 DB 확정. 결제는 타임아웃과 멱등 키로 부르고, 확정 뒤 알림·집계는 큐로, 좌석 현황은 캐시하되 확정 시 무효화합니다.
서버가 여럿이라 프로세스 안의 동기화로는 "하나"를 보장할 수 없고, 결제·알림 같은 외부 호출을 트랜잭션 안에 두면 락과 연결이 그만큼 묶이기 때문에 각각 자기 층에 둡니다.
예를 들어 1,000명이 A-12를 누르면 한 트랜잭션만 락을 얻어 `RESERVED`로 바꾸고 나머지는 409를 받으며, 성공자의 결제 응답이 유실돼도 같은 멱등 키로 재시도해 이중 결제가 없습니다. 한계는 행 락은 대기 줄이 생기므로 대량 경합에는 선점 + 대기열이 필요하고, 결제 타임아웃 뒤 "모르는" 상태는 `PENDING`과 사후 조회로 정리해야 하며, 이 전부에 트레이스·지표가 붙어야 운영이 된다는 점입니다.

- 꼬리: 결제가 타임아웃된 예약은 어떻게 처리하나요?

#### 이 설계에서 어느 한 장치를 빼면 무슨 일이 생기나요? 두 가지만 골라 설명해 주세요.

멱등 키를 빼면 결제 응답 유실 후 재시도가 새 결제가 되어 이중 결제가 나고, 재시도를 안 하면 사용자는 결제됐는지 모른 채 남습니다. 큐를 빼고 알림을 트랜잭션 안에서 보내면 문자 서버 응답 시간만큼 행 락과 DB 연결이 묶여 뒤에 선 999명의 대기가 길어지고, 문자 서버 장애가 예매 장애로 번지며, 롤백돼도 문자는 나갑니다.
장치 하나하나가 특정 실패 모드를 흡수하기 위한 것이라, 빼면 그 실패가 그대로 사용자에게 갑니다.
같은 식으로 락을 빼면 이중 예약, 타임아웃을 빼면 스레드 풀 고갈, 캐시 무효화를 빼면 매진된 좌석이 "남음"으로 보이고, 관측을 빼면 이 모든 것이 났는지조차 모릅니다. 한계는 장치가 많을수록 복잡하므로 실제 트래픽과 경합을 보고 필요한 것부터 넣어야 한다는 점입니다.
