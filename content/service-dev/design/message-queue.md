## 개념

주문이 들어오면 주문 저장은 지금 해야 하지만, 확인 메일·알림·통계 집계·추천 갱신은 몇 초 늦어도 된다. 이런 일을 요청 안에서 다 하면 응답이 느려지고, 메일 서버가 죽으면 주문까지 실패한다. **메시지 큐**는 "주문 생성됨"이라는 메시지를 큐에 넣고 바로 응답하게 하고, 별도의 **소비자**(consumer) 프로세스가 큐에서 꺼내 메일을 보낸다. 생산자와 소비자는 서로를 모르고 속도도 다르다.

큐가 주는 것 셋: **응답 시간**(무거운 일을 떼어 냄), **완충**(순간 폭주를 큐가 받아 소비자가 자기 속도로), **분리**(메일 서버가 죽어도 주문은 되고, 메시지는 남아 나중에 처리). 대신 "언제 처리되는지"는 보장 못 하고(최종 일관성), 같은 메시지가 두 번 갈 수 있다.

주문 생성 → 알림을 따라가 보자.

- `POST /orders` → 서비스가 주문을 DB에 저장 → 커밋 → `orderCreated{id: 42}` 메시지를 토픽에 발행 → 201 응답(50ms).
- 알림 소비자가 메시지를 받음 → 회원 조회 → 푸시 발송 → 처리 완료(ack). 통계 소비자도 같은 메시지를 따로 받아 집계.
- 푸시 서버가 5분 죽음: 소비자가 실패해 ack를 못 하면 메시지는 큐에 남고 재시도. 주문 API는 영향 없음.
- 소비자가 발송 뒤 ack 직전에 죽음: 메시지가 다시 배달돼 **푸시가 두 번** 간다 — 소비자는 "주문 42 알림 보냈음"을 기록해 두 번째는 건너뛰어야 한다(멱등 소비).
- 결과: 주문 응답은 빠르고 알림 장애와 분리됐다. 대가는 "적어도 한 번" 배달을 견디는 소비자와, 실패 메시지를 모아 두는 데드 레터 큐.

## 왜 나왔나

OS의 큐(생산자-소비자, 스레드 풀의 작업 큐)를 프로세스와 서버 밖으로 꺼낸 것이다. 한 프로세스 안의 큐는 프로세스가 죽으면 사라지고 다른 서버와 나눌 수 없다. 서비스가 여러 서버·여러 시스템으로 나뉘자 "일을 넘기되 상대가 지금 없어도 되는" 통로가 필요했고, 그것이 브로커(RabbitMQ, Kafka)다. Kafka는 큐를 디스크에 로그로 남겨 여러 소비자가 같은 메시지를 각자 읽고 되감을 수 있게 한 것이 다르다.

## 확인 질문

- 설명해 보기: 큐를 두면 무엇이 좋아지고 무엇을 포기하나?
  답: 응답 시간·완충·장애 분리를 얻고, 즉시 처리 보장과 정확히 한 번 처리를 포기한다(최종 일관성, 적어도 한 번).
- 다음 상태 예측: 소비자가 메시지를 처리하고 DB에 쓴 뒤 ack 전에 죽었다. 다음에 무슨 일이?
  답: 브로커가 같은 메시지를 다시 배달한다. 소비자가 멱등하지 않으면 DB에 두 번 쓴다.
- 다음 상태 예측: 주문 저장 트랜잭션 안에서 메시지를 발행했는데 트랜잭션이 롤백됐다. 메시지는?
  답: 이미 발행돼 소비자가 "없는 주문"의 알림을 보낸다. 커밋 뒤 발행(AFTER_COMMIT)하거나 아웃박스 패턴을 쓴다.

## 심화

### 배달 보장 세 가지

**최대 한 번**(at-most-once): 잃을 수 있지만 중복 없음 — 로그·지표. **적어도 한 번**(at-least-once): 안 잃지만 중복 가능 — 기본, 소비자가 멱등해야. **정확히 한 번**(exactly-once): 브로커·소비자·저장소가 함께 지원해야 하고 비싸다 — 실무에서는 "적어도 한 번 + 멱등 소비"로 같은 효과를 낸다.

### 순서

Kafka는 토픽을 파티션으로 나누고 **파티션 안에서만** 순서를 보장한다. 같은 주문의 이벤트를 같은 파티션에 넣으려면 키를 주문 ID로. 파티션 수가 소비자 병렬도의 상한이다. RabbitMQ는 큐 하나에 소비자 하나면 순서, 여럿이면 섞인다. "전체 순서"는 병렬을 포기해야 얻는다.

### 발행의 원자성 — 아웃박스

"DB 커밋과 메시지 발행이 둘 다 되거나 둘 다 안 되게"는 두 시스템이라 트랜잭션 하나로 못 묶는다. 아웃박스 패턴: 같은 DB 트랜잭션으로 `outbox` 표에 메시지를 넣고, 별도 워커(또는 CDC)가 표를 읽어 브로커에 발행한 뒤 표시한다. 워커가 죽어도 표에 남아 있어 안 잃고, 두 번 발행될 수 있으니 소비자는 멱등.

### 실패 처리

소비자가 예외를 던지면 재시도(즉시 몇 번 → 지수 백오프). 계속 실패하는 메시지(잘못된 데이터, 버그)는 **데드 레터 큐**로 보내 큐를 막지 않게 하고, 사람이 보고 재처리한다. 재시도 중 같은 파티션의 뒤 메시지는 기다린다 — 독(poison) 메시지 하나가 전체를 막지 않게 DLQ가 필수.

### 실무에서는

- 메시지에는 ID(멱등 키)와 발생 시각, 그리고 "무슨 일이 있었나"(이벤트)를 담는다. "무엇을 하라"(명령)보다 이벤트가 소비자를 늘리기 쉽다.
- 소비자는 처리 전에 "이 메시지 ID를 처리했나"를 확인하고 처리 후 기록한다(같은 트랜잭션).
- 소비 지연(lag)을 지표로 본다. 늘어나면 소비자를 늘리거나 파티션을 늘린다.
- 스프링에서는 `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 뒤 발행 — 발행 실패는 잃을 수 있으니 중요한 것은 아웃박스.
- 큐를 "느린 DB 대체"로 쓰지 않는다. 큐는 일을 미루는 것이지 없애는 것이 아니다 — 소비자가 못 따라가면 lag만 쌓인다.

### 면접 질문

#### 메시지 큐를 왜 쓰고, 도입하면 무엇을 신경 써야 하나요?

요청 안에서 지금 안 해도 되는 일(알림·집계·외부 연동)을 떼어 내 응답을 빠르게 하고, 순간 폭주를 큐가 완충하며, 소비 쪽 장애가 생산 쪽으로 번지지 않게 하기 위해 씁니다. 대신 배달이 "적어도 한 번"이라 소비자가 멱등해야 하고, 순서는 파티션 안에서만 보장되며, 처리 시점은 최종 일관성입니다.
브로커와 DB가 별개 시스템이라 정확히 한 번은 비싸고, 대신 재배달을 허용하고 소비자가 중복을 걸러 내는 것이 현실적이기 때문입니다.
예를 들어 주문 생성 뒤 알림을 큐로 보내면 푸시 서버가 죽어도 주문은 되고 메시지는 남아 나중에 갑니다. 신경 쓸 것은 커밋 전 발행(롤백된 주문의 알림)을 막는 아웃박스, 계속 실패하는 메시지를 빼내는 데드 레터 큐, 소비 지연 모니터링입니다. 한계는 디버깅이 어려워지고(요청 하나가 여러 프로세스에 걸침) 트레이스 ID 전파가 필요하다는 점입니다.

#### DB 저장과 메시지 발행을 함께 해야 합니다. 어떻게 원자성을 보장하나요?

같은 DB 트랜잭션 안에 아웃박스 표를 두고 메시지를 그 표에 저장한 뒤, 별도 워커나 CDC가 표를 읽어 브로커에 발행하고 발행됨으로 표시합니다(아웃박스 패턴).
DB와 브로커는 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없고, 커밋 전에 발행하면 롤백된 데이터의 메시지가 나가고 커밋 후에 발행하면 발행 실패 시 메시지를 잃기 때문입니다.
아웃박스는 "DB 커밋 = 메시지 저장"을 하나로 만들어 유실을 없애고, 워커가 발행 표시 전에 죽으면 다시 발행하므로 소비자는 메시지 ID로 중복을 걸러야 합니다. 한계는 워커의 폴링 지연만큼 발행이 늦고 표가 커지므로 발행된 행을 정리해야 하며, 간단한 알림처럼 잃어도 되는 것은 `AFTER_COMMIT` 리스너로 충분하다는 점입니다.
