## 개념

보통은 하나의 모델(엔티티·표)로 쓰기도 하고 읽기도 한다. 그런데 쓰기는 "주문 하나를 규칙대로 정확히"(정규화, 트랜잭션, 검증)이고, 읽기는 "회원명·상품명·배송 상태를 한 화면에"(조인 다섯 개, 집계)라 요구가 반대다. **CQRS**(Command Query Responsibility Segregation)는 둘을 **다른 모델**로 나눈다 — **명령**(command: 주문 생성·취소)은 정규화된 쓰기 모델과 원본 DB로, **조회**(query: 주문 목록 화면)는 화면 모양대로 미리 합쳐 둔 **읽기 모델**(역정규화 표, 캐시, 검색 엔진)로. 쓰기가 일어나면 이벤트가 읽기 모델을 갱신하므로, 둘 사이에 **잠깐의 지연**이 있다.

가장 흔한 계기는 둘이다. 읽기 부하가 쓰기보다 훨씬 커서 조인 쿼리가 원본 DB를 잡아먹을 때, 그리고 MSA에서 데이터가 서비스마다 나뉘어 **조인 자체가 불가능**할 때(모놀리스/MSA 장). 가벼운 형태(같은 DB에서 읽기 전용 복제본·조회 전용 리포지토리)부터 무거운 형태(별도 저장소 + 이벤트)까지 단계가 있다.

#### 예시 — 주문 목록 화면

```java
// 쓰기: 정규화된 엔티티, 트랜잭션, 검증
@Transactional
void place(PlaceOrder cmd) {
    Order order = Order.create(cmd);          // orders, order_items에 INSERT
    orderRepository.save(order);
    events.publish(new OrderPlaced(order));   // 커밋 뒤 발행(아웃박스)
}

// 읽기 모델 갱신: 이벤트를 받아 화면용 표 한 줄로
@EventListener
void on(OrderPlaced e) {
    orderSummaryRepository.upsert(new OrderSummary(
        e.orderId(), e.memberName(), e.firstProductName(), e.itemCount(), e.total(), e.status()));
}

// 조회: 조인 없이 한 표에서
List<OrderSummary> list(long memberId) {
    return orderSummaryRepository.findByMemberIdOrderByCreatedAtDesc(memberId);  // SELECT * FROM order_summary WHERE …
}
```

#### 작동 과정 — 주문 하나가 두 모델을 지나는 순서

- `POST /orders` → 쓰기 모델: `orders`·`order_items`에 INSERT, 재고 확인, 커밋. 응답 201.
- 커밋 뒤 `OrderPlaced` 이벤트 발행(아웃박스 → 큐).
- 읽기 모델 갱신기가 이벤트를 받아 `order_summary`에 한 줄 upsert. 회원명·상품명은 이벤트에 담겨 오거나 여기서 조회해 복사.
- 사용자가 바로 `GET /orders` → `order_summary` 조회. 갱신기가 아직 안 돌았다면 **방금 주문이 안 보인다**(수십 ms~수 초).
- 결과: 목록 조회는 조인 0회·인덱스 한 번. 대신 지연을 다뤄야 한다 — 응답에 방금 만든 주문을 포함시키거나, "처리 중" 표시, 또는 자기 쓰기는 원본에서 읽기(read-your-writes).

#### 비교 — 단계별 CQRS와 그 비용

| 단계 | 읽기 모델 | 동기화 | 지연 | 얻는 것 / 비용 |
|---|---|---|---|---|
| 0. 없음 | 같은 엔티티 | — | 없음 | 단순 / 조인·N+1이 읽기 화면마다 |
| 1. 조회 전용 쿼리·DTO | 같은 DB, 조회용 SQL·뷰 | — | 없음 | 읽기 코드가 화면에 맞음 / 쓰기 모델과 두 벌 |
| 2. 읽기 복제본 | 같은 스키마의 복제본 | DB 복제 | ms | 읽기 부하 분리 / 복제 지연 |
| 3. 역정규화 읽기 표 | 화면 모양 표(같은 DB 또는 별도) | 이벤트·트리거 | ms~s | 조인 제거, 서비스 간 조회 / 갱신 코드·정합성 책임 |
| 4. 별도 읽기 저장소 | Elasticsearch·Redis·문서 DB | 이벤트 | s | 검색·집계 최적 / 저장소 둘 운영, 재구축 필요 |

## 왜 나왔나

한 모델로 읽기와 쓰기를 다 하면 둘 중 하나가 손해를 본다 — 정규화하면 읽기가 조인 지옥, 역정규화하면 쓰기가 여러 곳을 갱신. 2010년 Greg Young이 "명령과 조회의 책임을 나누자"고 이름 붙였고(원래는 도메인 모델 설계 맥락), MSA가 퍼지면서 "서비스마다 DB가 따로라 조인이 안 된다"의 해법으로 자리 잡았다. 이벤트 소싱(상태 대신 이벤트 로그를 원본으로)과 자주 함께 언급되지만 별개다 — CQRS는 이벤트 소싱 없이도 쓰고, 대개 그렇게 쓴다.

## 확인 질문

- 설명해 보기: CQRS가 푸는 문제를 한 문장으로?
  답: 쓰기는 정합성, 읽기는 화면 맞춤이라 요구가 반대인데 한 모델로 하면 한쪽이 손해라서, 둘을 나누고 이벤트로 잇는다.
- 다음 상태 예측: 주문 직후 목록을 조회했는데 방금 주문이 없다. 버그인가?
  답: 읽기 모델 갱신 지연(최종 일관성)이다. 설계에서 예상해야 한다 — 방금 만든 주문을 응답에 담아 프런트가 목록에 끼워 넣거나, 자기 쓰기는 원본에서 읽거나, 지연을 "처리 중"으로 보여 준다.
- 다음 상태 예측: 읽기 모델 갱신기가 한 시간 죽어 있다가 살아났다면?
  답: 큐에 쌓인 이벤트를 순서대로 처리해 따라잡는다(멱등해야 함). 이벤트를 잃었다면 원본 DB에서 읽기 모델을 다시 만드는 재구축 경로가 필요하다.

## 심화

### 어디까지 나눌지

코드만 나누기(조회 서비스·DTO·조회 전용 리포지토리)는 거의 항상 이득이고 비용이 없다 — 여기서 시작한다. 저장소를 나누는 것은 읽기 부하가 원본을 위협하거나 조인이 불가능할 때만. "CQRS 도입"이 곧 별도 저장소 + 이벤트를 뜻하지 않는다.

### 지연을 다루는 방법

- 응답에 결과 포함: 명령 응답에 만들어진 주문을 실어 프런트가 목록에 즉시 반영.
- read-your-writes: 방금 쓴 사용자는 잠깐 원본에서 읽게 라우팅.
- 버전·타임스탬프: 읽기 모델이 어느 이벤트까지 반영했는지 노출해 프런트가 기다리거나 재조회.
- 화면 설계: "처리 중" 상태를 정식 상태로 두어 지연이 버그가 아니게.

### 읽기 모델 갱신의 정합성

이벤트는 적어도 한 번 배달되므로 갱신은 멱등(upsert, 이벤트 ID 기록). 순서가 섞이면 옛 상태로 덮을 수 있으므로 같은 주문의 이벤트는 같은 파티션으로, 또는 버전 비교 후 갱신. 재구축(원본에서 읽기 모델 전체 재생성)은 처음부터 만들어 둔다 — 버그로 읽기 모델이 오염됐을 때 유일한 복구 수단이다.

### 쓰지 말아야 할 때

도메인이 단순하고 읽기·쓰기 부하가 비슷하며 조인이 잘 되는 단일 DB 서비스. 여기서 저장소를 나누면 지연·동기화 코드·운영만 늘고 얻는 게 없다(Azure 패턴 문서의 "not recommended when"). 강한 일관성이 필요한 화면(잔고, 재고 수량)은 읽기 모델이 아니라 원본에서 읽는다.

### 실무에서는

- 첫 단계는 `@Transactional(readOnly = true)` 조회 서비스 + 화면별 DTO 프로젝션. JPA 엔티티 그래프를 조회에 그대로 쓰지 않는다.
- 목록·검색·통계 화면이 무거워지면 역정규화 표 하나(`order_summary`)를 두고 커밋 뒤 이벤트(아웃박스)로 갱신. 재구축 배치를 같이 만든다.
- 검색은 Elasticsearch, 집계 대시보드는 별도 저장소 — 이것도 CQRS의 4단계다.
- 지연 SLA(몇 초 안에 반영)를 지표로 재고 알림을 건다.

### 면접 질문

#### CQRS는 무엇이고 어떤 문제를 풀며, 무엇을 포기하나요?

명령(쓰기)과 조회(읽기)의 모델·코드·필요하면 저장소까지 분리하는 패턴입니다. 쓰기는 정규화된 원본에서 트랜잭션·검증으로 정합성을 지키고, 읽기는 화면 모양대로 미리 합쳐 둔 모델에서 조인 없이 가져오며, 둘은 이벤트로 동기화됩니다. 푸는 문제는 읽기·쓰기의 상반된 요구를 한 모델이 감당하지 못하는 것과, MSA에서 서비스 간 조인이 불가능한 것입니다.
포기하는 것은 즉시 일관성 — 쓰기 뒤 읽기 모델에 반영되기까지 지연이 있고, 갱신 코드·재구축·저장소 운영이 늘어납니다.
예를 들어 주문 목록 화면을 `order_summary` 한 표로 조회하고 `OrderPlaced` 이벤트로 갱신하면 조인 다섯 개가 인덱스 한 번이 됩니다. 한계는 단순한 서비스에 저장소 분리까지 하면 비용만 들므로 조회 코드 분리(DTO·조회 서비스)부터 단계적으로 가야 하고, 잔고·재고처럼 강한 일관성이 필요한 화면은 읽기 모델이 아니라 원본에서 읽어야 한다는 점입니다.

- 오답: "CQRS = 이벤트 소싱" — 별개다. CQRS는 이벤트 소싱 없이 역정규화 표와 이벤트만으로 흔히 쓴다.
- 오답: "CQRS를 하려면 DB를 두 개 둬야 한다" — 조회 코드·DTO만 나누는 것도 CQRS의 첫 단계이고 대개 거기서 충분하다.
- 꼬리: 방금 쓴 데이터가 조회에 안 보이는 문제를 어떻게 다루나요?
- 꼬리: 읽기 모델이 잘못됐을 때 어떻게 복구하나요?

#### 주문·상품·회원이 서로 다른 서비스로 나뉘어 있습니다. 회원별 주문 목록(상품명 포함) 화면을 어떻게 만드나요?

주문 서비스 안에 화면용 읽기 모델(`order_summary`: 주문 ID·회원명·대표 상품명·건수·금액·상태)을 두고, 주문 생성·상품명 변경·회원명 변경 이벤트를 구독해 갱신합니다. 화면은 이 표만 조회합니다. 대안인 API 합성(주문 목록을 받아 상품·회원 서비스에 N번 조회)은 지연과 장애 전파가 커서 목록 화면에는 맞지 않습니다.
서비스별 DB라 조인이 불가능하므로 "조회 시점에 합치기" 대신 "쓰기 시점에 미리 합쳐 두기"로 바꾸는 것이고, 그것이 CQRS의 읽기 모델입니다.
상품명이 바뀌면 `ProductRenamed` 이벤트로 관련 요약 행을 갱신하되, 주문 당시 이름을 보존해야 하는 정책이면 갱신하지 않습니다. 한계는 이벤트 지연 동안 옛 이름이 보이고, 이벤트 유실·순서 문제를 멱등 갱신과 재구축으로 막아야 하며, 요약 표가 여러 서비스의 데이터를 복제한 것이라 어느 서비스가 그 정합성을 책임지는지 정해야 한다는 점입니다.

- 오답: "주문 서비스가 회원·상품 DB를 직접 조인한다" — 서비스 경계를 깨고 스키마 결합이 생겨 독립 배포가 사라진다.
- 꼬리: API 합성이 맞는 경우는 언제인가요?
