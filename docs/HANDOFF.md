## 1. 이 프로젝트가 뭔지

**CS 기초부터 심화까지를 “개념 지도”로 한 곳에 모아, 클릭해서 파고들고 눈으로 동작을 보며 외우는 웹앱.**
옵시디언처럼 계속 개념을 추가해 가지만, 웹으로 배포해서 누구나 볼 수 있게 한다.

### 사용자가 이걸 만드는 이유 (가장 중요)
- CS 공부를 하다 보면 **한 줄 한 줄에 모르는 전문용어**가 많다. 하나씩 검색하고 찾아다니느라 **진도가 너무 늦다.** → **페이지를 떠나지 않고** 모든 정보를 얻고 싶다.
- **눈으로 보면 이해가 훨씬 빠르다.** for문을 머릿속으로 그리는 것보다 애니메이션으로 보는 게 빠르듯, 내부 동작을 시각화해서 이해하고 싶다.
- 개념을 **역사·흐름(왜 이게 나왔나)** 으로 이해하고 외우는 걸 좋아한다. (예: 함수 → 클래스 → 객체 → 모듈 → 패키지 → 컴포넌트 → API)
- 기초는 **비전공자·1학년도 이해할 수준**, 그리고 원하는 사람은 **면접관이 파고드는 수준까지 심화**할 수 있어야 한다.

### 원본 자료
`docs/reference/`의 손필기 3장이 출발점이다. 현재 콘텐츠는 거의 이 3장을 옮긴 것이다.

- `note-3-program-dev.png`: 프로그램 개발 - 기능 (함수 → 클래스 → 객체/인스턴스 → 모듈 → 패키지 → 컴포넌트/CBD → API/OpenAPI)

사용자가 “이런 시각화”의 예로 보여준 영상은 **배열에서 최댓값 찾기 애니메이션**이었다.

### 레퍼런스 영상 분석 (2026-09-11, 녹화본 56초에서 프레임 추출해 확인)

> ⚠️ 아래는 **참고**다. 사용자가 “꼭 같은 디자인을 할 필요는 없다”고 했다. 판단 기준은 6-2-1을 따른다.

**Manim(3Blue1Brown 라이브러리) 스타일**이다. 온라인 강의 화면을 녹화한 것이고, 우리가 베낄 것은 영상이 아니라 **시각 언어**다. (Manim은 영상을 렌더링하는 파이썬 도구라 재생/일시정지 같은 조작이 안 된다. 우리는 SVG + 트윈으로 같은 느낌을 내면서 조작 가능하게 만든다.)

| 관찰 | 우리가 가져갈 것 |
|---|---|
| 어두운 남색 배경(#1e2530 근처), 요소는 **얇은 흰 테두리 + 반투명 채움**인 큰 정사각형 | 칸은 크게, 채움보다 테두리 위주 |
| 값은 **세리프 숫자**, 라벨은 산세리프 | 값과 이름이 한눈에 구분된다 |
| 색은 **역할 3개뿐**: 현재(올리브/노랑) · 비교 대상(빨강) · 확정(초록) | 역할 색을 토큰으로 고정하고 그 이상 늘리지 않는다 |
| 좌상단 변수는 **딱 3개**(`number`, `compare_number`, `is_max_num`) | 인계서 6-2 원칙(보조 정보 2~3개)과 일치 |
| **숫자가 상자에서 변수 칸으로 날아간다.** 그동안 상자는 비어 있다가 되돌아오면 다시 채워진다 | **값 대입을 움직임으로 보여준다.** 가장 중요한 포인트 |
| `False ↔ True` 같은 **텍스트 값 변경도 모핑**된다(순간 교체가 아님) | 숫자·불리언이 바뀔 때도 트윈을 건다 |
| **매우 느리다.** 원소 6개 훑는 데 30초 = 단계당 4~5초 | 기본 속도를 느리게 잡고 속도 조절을 준다 |
| **2단계 구성**: ① 자세한 비교 패스 → 화면을 완전히 비움 → ② 화살표로 빠르게 요약 리플레이 | 긴 장면은 “자세히 → 요약” 두 패스로 나눈다 |
| 요약 패스에서 **노란 화살표가 좌→우로 이동**하고, 결과 라벨(`Max: 6`)이 화살표 위에 붙어 함께 움직인다. 끝나면 화살표·라벨·칸이 모두 초록으로 | 포인터와 결과값을 한 덩어리로 움직인다 |

## 2. 지금까지의 진행 (프로토타입 v1 → v3)

단일 HTML 프로토타입으로 사용자와 “한줄평 → 수정”을 반복했다. 최종본이 `docs/prototype/cs-map-v3.html`이다(브라우저로 바로 열림).

| 버전 | 한 일 | 사용자 한줄평(요약) |
|---|---|---|
| v1 | 지도 모양 3종 비교: A 손그림 흐름도(드릴다운), B 그래프 뷰(force), C 마인드맵 트리 + 퀴즈 | A: 역사로 외우기 최적이지만 양이 많아지면 꽉 차 보임. 카드 구조(한 줄 정의 / 왜 나왔나 / 흐름 / 하위 개념)는 좋음. B: 정신없음, 트리처럼 내려가게. C: 가장 좋지만 가로 스크롤 불편 → 드래그 이동 원함. 퀴즈: 주제별 범위 선택 원함. 공통: 기초 + 심화(내부 구조·활용·면접), 사용자가 직접 추가할 수 있으면 좋겠음 |
| v2 | 좌→우 트리(드래그 이동) / 위→아래 트리 + 흐름 화살표, 이 가지만 크게 보기, 퀴즈 범위·면접 문제, 기초/심화/기여 탭 | 열린 노드가 흰색으로 바뀌고 색이 임의로 보임 → **깊이별 색**으로. 위→아래 트리는 가독성이 떨어지고, 열린 노드 왼쪽 세로 바가 거슬림. 표기는 “전공·면접 수준” 대신 그냥 **기초 / 심화**. 설명 속 모르는 용어를 누르면 설명을 보여주거나 해당 트리로 가야 함. **기여 기능은 아직 필요한지 모르겠음** (개인 공부용 우선). 집중용 배경음(브라운/화이트 노이즈)과 뽀모도로 원함. 오른쪽 설명이 한 줄씩 딱딱해서 읽기 힘듦 |
| v3 | 시각화 5종(페이지 교체, CPU 스케줄링, 주소 변환, 디스크 스케줄링, 캐시와 지역성), 용어 누르기(중첩 카드), 읽기 편한 설명(문장 줄바꿈·형광펜·연결어), 깊이별 색, 위→아래 트리 직각 연결선, 집중(노이즈+뽀모도로), 기여 탭 제거 | **다크 모드 필요.** 시각화 가독성이 너무 안 좋음 → **천천히 움직이는 설명 애니메이션**(힙/스택/데이터 영역 비교, 정렬 애니메이션 같은 것). 콘텐츠를 다듬어야 함. 사용자가 개념별 **메모**를 쓸 수 있어야 함. **한 줄 정의** 가독성 개선 필요. GitHub로 옮겨서 계속 작업 |

## 3. 확정된 결정 사항

사용자가 모두 동의했다(“다 좋고”).

1. **기술**: Vite + React + TypeScript. 배포는 Vercel 또는 Cloudflare Pages(push 시 자동 배포).
2. **콘텐츠는 코드와 분리**: 개념 1개 = 마크다운 파일 1개(`content/`). 옵시디언으로 열어 편집할 수 있게 한다.
3. **다크 모드**: 라이트 / 다크 / 시스템 따라가기. 모든 색은 토큰으로 관리한다.
4. **내 메모**: 개념마다 자유 메모 + “내 말로 쓰는 한 줄 정의” + 헷갈림 표시. 1단계는 브라우저 저장 + JSON 내보내기/가져오기, 2단계(나중)는 로그인 + DB 동기화.
5. **한 줄 정의는 3줄 카드**: 한 줄 / 비유 / 키워드. 형제 개념은 비교표로 묶는다. (5장의 작성 규칙 참고)
6. **과목 뼈대 확장**: 컴퓨터 구조 / 운영체제 / 자료구조 / 알고리즘 / 네트워크 / 데이터베이스 / 프로그래밍 언어(함수→클래스→…) / **서비스 개발은 실무 트랙으로 분리**.
7. **시각화 전면 재작업**: 천천히 움직이는 설명 애니메이션. **메모리 영역(코드·데이터·힙·스택) 장면 1개로 스타일을 먼저 확정**한 뒤 나머지를 옮긴다.
8. **기여(다른 사용자 제안) 기능은 보류.** 개인 공부 도구로 먼저 다듬고, 필요해지면 “내 메모 → 공개 제안” 방식으로 확장한다.

### 2026-09-11 추가 결정 (Claude Code 첫 세션)

9. **콘텐츠 범위 확정**: Java + Spring + DB + CS 기초 + 서비스 개발 전체 과정.
   동기는 “바이브코딩을 하려면 최초 계획부터 구현까지 흐름을 알아야 한다”는 것.
10. **트리 최상위를 5갈래로 재배치**한다(5-5 참고). 프로토타입의 4갈래로는 위 범위를 담을 수 없다.

    이유: v3의 가장 큰 불만이 시각화였고, 스타일을 먼저 못 박아야 이후 장면을 같은 틀로 찍어낼 수 있다.

## 4. 기능 명세 (v3 프로토타입 기준 + 확정 사항)

### 4-1. 개념 트리 (메인 화면)
- **좌→우 트리(기본)** / **위→아래 트리** 전환.
- 캔버스 조작: 드래그로 이동, 휠로 스크롤, Ctrl+휠/핀치로 확대, ＋/－/화면 맞춤 버튼. 가로 스크롤바는 쓰지 않는다.
- 노드를 누르면 펼침/접힘(＋/− 표시)과 동시에 설명 패널이 열린다. 펼치면 카메라가 새로 보이는 자식들 쪽으로 부드럽게 따라간다.
- **깊이별 색**: 진할수록 큰 개념(범례 표시). 선택해도 노드 색이 바뀌지 않고, 선택은 형광펜/테두리로만 표시한다.
- 노드 옆 배지: `심화`(보라) = 심화 내용 있음, `▶`(청록) = 시각화 있음, 퀴즈 결과 점(초록/주황).
- **이 가지만 크게 보기**: 하위 트리만 루트로 떼어서 본다. 상단 경로(📍 전체 › 운영체제 › …)로 복귀하고, Esc는 한 단계 뒤로.
- 위→아래 트리: 직각(엘보) 연결선. **흐름 화살표는 바로 옆 형제끼리만** 그리고, 이유 글씨는 선택한 노드에 연결된 것만 보인다.

### 4-2. 설명 패널
- 상단: “← 이전 개념으로 돌아가기”(용어·칩으로 이동한 경우), 경로, 제목, **▶ 동작 과정 눈으로 보기** 버튼(시각화가 있을 때).
- 탭: **기초 | 심화 | 내 메모**(내 메모 탭은 신규).
- 기초: 3줄 카드(한 줄/비유/키워드) → 왜 나왔나(문장마다 줄바꿈, 핵심 구절 형광펜, “그래서/하지만” 연결어 색 표시) → 흐름(이전 —이유→ 이것 —이유→ 다음) → 하위 개념 칩 → 비교표(형제).
- 심화: 🔧 내부 구조 / 🌍 실제 활용 / 🎤 면접 질문(“먼저 말로 답해보고 → 모범 답변 보기” + 꼬리 질문).
- **용어 누르기**: 설명 속 용어는 자동으로 링크된다(문단마다 첫 등장만, 자기 자신은 제외). 누르면 **그 문단 바로 아래에 설명 카드**가 펼쳐진다. 카드 안 용어를 또 누르면 경로가 쌓인다(📖 지역성 › 캐시 라인). 트리에 있는 개념이면 “🌳 트리에서 보기”, 시각화가 있으면 “▶ 눈으로 보기”.

### 4-3. 퀴즈 모드
- 범위 선택(가지가 있는 모든 노드) + 문제 종류(기초 개념 / 면접 질문).
- 기초: 정의·배경을 흐리게 가림 → 떠올린 뒤 공개 → ✓ 기억났음 / ✗ 헷갈렸음. 면접: 심화의 면접 질문 중 무작위.
- 범위별 점수를 보여준다. (신규) 결과는 내 메모와 함께 저장한다.

### 4-4. 🎧 집중
- 노이즈: 끄기 / 브라운 / 핑크 / 화이트 + 볼륨. Web Audio로 생성한다(외부 음원 파일 없음). 루프 경계 클릭 제거 처리가 들어 있다.
- 뽀모도로: 공부/휴식/긴 휴식(4번째마다) 시간 설정, 시작/일시정지/초기화/건너뛰기, 전환 시 알림음 + 토스트, 휴식 중 소리 끄기 옵션, 탭 제목에 남은 시간 표시.

### 4-5. 내 메모 (신규)
- 개념별: 자유 메모(마크다운), 내 말로 쓰는 한 줄 정의, 헷갈림 표시, (선택) 태그.
- 트리 노드에 메모 표시, “내 메모 모아보기” 화면.
- 저장: `localStorage`(버전 키 포함) + JSON 내보내기/가져오기. 나중에 Supabase 등으로 동기화할 수 있게 저장 계층을 인터페이스로 분리한다.

### 4-6. 다크 모드 (신규)
- 라이트/다크/시스템 3단 토글. 트리 깊이 팔레트, 용어 밑줄, 형광펜, 시각화 색 모두 두 테마에서 대비를 확인한다.

## 6. 시각화 재설계 가이드

### 6-1. v3가 안 읽힌 이유
- 변수 창, 표, 격자, 부가 설명이 **한 화면에 동시에** 떠서 시선이 흩어진다.
- 상태가 **순간적으로 바뀌어** 무엇이 변했는지 눈이 못 따라간다.
- 칸이 작고 표·고정폭 글씨 위주라 “그림”이 아니라 “읽을거리”처럼 보인다.

### 6-2. 원칙
1. **장면 하나 = 주인공 하나.** 보조 정보는 변수 2~3개와 자막 한 줄까지만.
2. **모든 변화는 움직임으로.** 이동/등장/퇴장/색 전환을 300~700ms로 보간한다. 요소가 “날아가서 들어가는” 모습이 보여야 한다.
3. **자동 재생.** 시각화를 열면 바로 움직이기 시작한다. “재생 버튼을 눌러 영상을 시작하는” 느낌이 아니라,
   화면에 들어오면 이미 살아 있는 그림이어야 한다. (2026-09-11 사용자 요청)
   - 기본 속도는 느리게, 단계 사이에 짧은 멈춤.
   - 배속은 **1.0 / 1.2 / 1.5 / 1.8 / 2.0** 다섯 단계.
   - 일시정지/이전/다음은 주되, 처음 상태는 “재생 중”이다.
   - 한 바퀴 다 돌면 멈추고 “처음부터”를 띄운다. 무한 반복하지 않는다(옆에서 계속 움직이면 글을 못 읽는다).
   - 키보드 ← → Space.
4. **코드 + 그림 나란히**(pythontutor 스타일). 실행 중인 코드 줄이 켜지면 그림이 변한다.
5. 요소는 크게(칸 최소 44px), 여백은 넉넉하게. 라이트/다크 모두 대응하고 `prefers-reduced-motion`도 존중한다.
6. 구현: **단계(step) 배열 = 상태 스냅샷**, 렌더러는 이전 상태 → 다음 상태를 트윈으로 보간한다. SVG 기반, 애니메이션은 Motion(framer-motion) 또는 GSAP 중 선택한다.
7. 알고리즘 로직(단계 생성)과 그리기를 분리한다. 로직은 순수 함수로 두고 **단위 테스트**를 붙인다(7-2의 검증값 사용).

### 6-2-3. 첫 장면을 만들며 정한 것 (2026-09-11, `src/viz/`)

앞으로 만드는 장면에도 그대로 적용한다.

1. **사라질 때는 두 박자.** 빨갛게 표시(자리는 그대로) → 서서히 사라짐(자리 반납) → 목록에서 제거.
   곧바로 없애면 **뭐가 사라졌는지 눈이 못 따라간다.** 상태에 `dying`과 `gone`을 따로 둔다.
2. **무대는 넉넉하게.** 가장 많이 쌓였을 때도 빈칸이 남게 잡는다.
   딱 맞게 잡으면 화면이 꽉 차서 “자원이 부족하다”는 엉뚱한 인상을 준다. 테스트로 막는다.
3. **자동 재생은 화면에 들어올 때.** 페이지를 열자마자가 아니다(안 보이는 동안 혼자 다 돌아버린다).
   `IntersectionObserver`로 보일 때 시작하고, 끝까지 가면 멈춘 뒤 “↻ 처음부터”를 띄운다.
4. **트윈은 CSS 트랜지션으로 충분하다.** 상태 배열의 각 요소에 안정된 key를 주면
   같은 요소가 새 위치로 미끄러져 간다. Motion/GSAP은 아직 안 넣었다. 필요해지면 그때 넣는다.
5. **라벨은 최소로.** 프레임 이름표를 넣으려다 영역 라벨과 자리가 겹쳤다.
   자막이 이미 이름을 말하므로 그림에는 테두리만 남겼다(“장면 하나 = 주인공 하나”).
6. 코드와 그림은 나란히 두되, 화면이 좁으면(≈1000px 미만) 세로로 쌓는다.

### 6-2-4. 무대를 전체 화면으로 띄우며 정한 것 (2026-09-11, `src/viz/VizStage.tsx`)

1. **초점은 재생기 안으로 가져온다.** ←/→/Space 처리기가 `.viz`에 붙어 있고 keydown은
   위로만 올라간다. 바깥 상자에 초점을 두면 안내에 적은 키가 하나도 안 먹는다.
   닫을 때는 열었던 버튼으로 돌려준다.
2. **전체 화면 무대는 기다리지 않고 바로 재생한다.** 화면을 덮고 열리니
   `IntersectionObserver`를 기다릴 이유가 없고, 그 기다림이 안 풀리면 자동 재생이 통째로 멈춘다.
   (패널 안에 끼워 넣는 작은 재생기는 6-2-3의 3번 그대로 유지.)
3. **그림은 남는 높이 안에 가둔다.** `height: 100%`만으로는 부족하다 — 높이가 정해지지 않은
   flex 칸 안에서 auto로 풀리면 SVG가 viewBox 비율대로 폭에서 높이를 만들어 자막·조작을 덮는다.
   자리를 잡아 두고(`position: relative`) 절대 배치로 얹는다.
4. **`margin: 0 auto`는 세로 배치에서 지운다.** 가로 auto 여백이 stretch를 막아
   폭이 0이 되고(안쪽이 absolute라 잴 내용이 없다) 그림이 통째로 사라진다.

### 6-2-5. 지도 카메라 규칙 (2026-09-11, `src/tree/`)

1. **자동 맞춤의 배율 바닥은 화면 폭에 따라 다르다.** 폰(366px)에서 전체를 맞추면 0.55까지
   내려가 14px 제목이 7.7px이 된다. 좁은 화면에서는 0.85를 바닥으로 두고 밀어서 보게 한다.
   손으로 줄이는 건 계속 0.55까지 허용한다 — 전체 모양을 훑어보려는 의도이므로.
2. **다 들어가면 가운데, 안 들어가면 시작점에 붙인다.** 넘치는데 가운데에 두면 양쪽이 똑같이
   잘려서 좌→우 트리의 뿌리와 과목 열이 화면 밖으로 사라진다. 잘릴 거라면 잎 쪽이 잘려야 한다.
3. **테두리 색은 바탕 대비 3:1 아래로 내려가지 않는다.** 노드의 유일한 경계라서,
   더 옅게 두면 깊은 노드가 배경에 녹는다. 깊이 표현은 이 바닥 위에서만 옅어진다.
4. **호버는 테두리 색까지 바꾼다.** 채움만 짙게 하면 다크에서 채널당 5~7밖에 차이가 안 나
   커서가 어디 있는지 알 수 없다.

### 6-2-1. 판단 기준은 “사람이 이해하기 쉬운가” (2026-09-11)

레퍼런스 영상과 손필기 노트는 **방향을 잡으라고 준 자료**지 사양이 아니다.
사용자가 분명히 했다: “진짜 참고용이지 꼭 같은 디자인을 할 필요는 없는데 **사람이 이해하기 쉬워야 해**.”

그래서 원본과 닮았는지로 판단하지 않는다. 매번 이렇게 묻는다.
**“이 그림을 처음 보는 사람이 이 개념을 이해하게 되는가?”**

### 6-2-2. 모든 장면은 “무대를 먼저 세우고, 그 위에서 움직인다”

**이게 이 프로젝트 시각화의 핵심 규칙이다.** 메모리 영역은 이 규칙의 첫 적용 예일 뿐,
앞으로 만드는 **모든** 시각화가 이 방식을 따른다. (2026-09-11 사용자 확인:
“메모리구조를 예로 든 거지 그것만 만드는 게 아니야. 앞으로 시각화가 필요한 부분들은
저런 방식으로 넣어야 이해가 좋겠다는 의미였어”)

**1단계 · 무대 세우기 (공간축).** 아직 아무것도 안 움직인다.
그 개념이 사는 공간이 **어떻게 생겼는지**를 먼저 그린다. 칸이 하나씩 나뉘고 이름이 붙는다.
“무엇이 어디에, 어떤 크기로, 왜 그 자리에 있는가”가 여기서 끝나야 한다.

**2단계 · 그 위에서 움직이기 (시간축).** 이제 값·요청·데이터가 그 무대 위를 지나간다.
1단계에서 세운 칸이 채워지고 비워지고 서로를 밀어낸다.

글자로 나열하는 것과 구조를 보여주는 것은 다르다.
“메모리에는 코드·데이터·힙·스택 영역이 있다”고 적는 것과,
그 칸들이 실제로 어디에 놓이고 **힙과 스택이 서로를 향해 자라 가운데 빈 공간이 줄어드는 걸**
보여주는 것은 다르다. 항상 후자여야 한다.

각 장면에서 “무대”가 무엇인지:

| 장면 | 1단계 · 무대 | 2단계 · 그 위의 움직임 |
|---|---|---|
| 메모리 영역 | 메모리 막대를 코드·데이터·힙·스택으로 나눔 | 변수·`malloc` 상자·함수 프레임이 쌓이고 사라짐 |
| 페이지 교체 | 프레임 3칸과 디스크 | 페이지가 들어오고, 자리가 없으면 하나가 밀려남 |
| CPU 스케줄링 | 준비 큐와 CPU 자리 | 프로세스가 줄을 서고 CPU를 잡았다 놓음 |
| 주소 변환 | 가상 주소 → TLB → 페이지 테이블 → 물리 메모리 경로 | 주소 하나가 그 경로를 따라 흘러감 |
| 디스크 스케줄링 | 0~199 트랙과 헤드 | 헤드가 요청을 찾아 실제로 이동 |
| 캐시와 지역성 | 캐시 라인 구조와 배열의 메모리 배치 | 행 우선/열 우선으로 훑을 때 적중과 미스 |
| 정렬 | 막대 배열 | 막대가 실제로 자리를 맞바꿈 |
| JVM 메모리 + GC | 힙을 Eden·Survivor·Old로 나눔 | 객체가 생기고 살아남아 승격되고 쓸려나감 |
| Spring 요청 흐름 | 필터 → 디스패처 서블릿 → 컨트롤러 → 서비스 → 리포지토리 경로 | 요청 하나가 그 길을 통과해 응답으로 돌아옴 |

### 6-3. 첫 장면: 메모리 영역 (스타일 확정용)
세로 메모리 막대를 그린다. 낮은 주소부터 **코드 | 데이터 | 힙 ↓ … (빈 공간) … ↑ 스택**이고, 힙은 위로 자라고 스택은 아래로 자란다.
```c
int g = 1;                         // 데이터 영역
void f(int x) { int y = x * 2; }   // f 프레임
int main(void) {
    int a = 3;                     // 스택: main 프레임
    int *p = malloc(sizeof(int));  // p는 스택, 가리키는 상자는 힙
    *p = 7;
    f(a);                          // 스택에 f 프레임이 쌓였다가 return 시 사라짐
    free(p);                       // 힙 상자 사라짐
    return 0;
}
```
- 스토리보드: 프로그램 로드(코드 영역에 명령어) → `g`가 데이터 영역에 반짝 → `main` 프레임이 스택에 쌓임 → `a=3` → `malloc`으로 힙에 상자 등장 + 스택의 `p`에서 화살표 → `*p=7` 값이 상자로 날아감 → `f(a)` 프레임이 위로 쌓이고 `x`에 3 복사 → `y=6` → return, 프레임이 사라짐 → `free(p)`, 상자와 화살표가 사라짐 → 종료.
- 심화 토글: BSS(초기화 안 된 전역), 스택 오버플로, 메모리 누수(`free` 누락) 장면.
- **사용자에게 이 장면을 먼저 보여주고 한줄평을 받은 뒤** 나머지 시각화에 같은 스타일을 적용한다.

### 6-4. 이후 재작업 목록
정렬(버블·선택·삽입·퀵·병합, 막대가 실제로 자리 교환), 페이지 교체(FIFO/LRU/OPT), CPU 스케줄링(FCFS/SJF/SRTF/RR), 주소 변환(TLB·페이지 테이블·페이지 폴트), 디스크 스케줄링, 캐시와 지역성. 이후 후보는 프로세스 상태 전이, 교착상태, 자료구조(스택/큐/해시/트리/힙)다.

### 7-1. `docs/prototype/cs-map-v3.html` 안의 위치
| 이름 | 내용 |
|---|---|
| `const RAW` | 기초 데이터 62개 노드: `[id, 제목, 한 줄 정의, 왜 나왔나(**강조** 포함), 하위 id[], 흐름[[from,to,이유]]]` |
| `const DEEP` | 심화 샘플 9개(cache, thread, ctx, rr, mlfq, paging, vm, lru, api): `ins`/`use`/`iv[{q,a,f[]}]`/`checked` |
| `const GLOSS`, `NODE_TERMS` | 용어 사전 약 67개 + 트리 노드명 용어 연결 |
| `SIMMAP`, `SIMS` | 개념 → 시각화 매핑, 시각화 5종의 단계 생성 로직과 렌더 |

권장: `RAW/DEEP/GLOSS`를 `content/` 마크다운으로 바꾸는 **일회성 변환 스크립트**를 먼저 만든다. 3줄 카드의 비유·키워드는 비어 있으니 콘텐츠 작업 때 채운다.

### 7-2. 검증된 시각화 결과값 (테스트에 사용)
- 페이지 교체, 참조열 `7 0 1 2 0 3 0 4 2 3 0 3 2 1 2 0 1 7 0 1`, 프레임 3개 → 폴트 수 **FIFO 15 / LRU 12 / OPT 9**
- CPU 스케줄링, P1(도착 0, 실행 5) P2(1,3) P3(2,8) P4(3,6) → 평균 대기 **FCFS 5.75 / SJF(비선점) 5.25 / SRTF 5.00 / RR(q=2) 9.75**
  - RR 규칙: 같은 시각에는 새로 도착한 프로세스를 먼저 줄 세우고, 퀀텀이 끝난 프로세스는 그 뒤로 보낸다.
- 디스크, 헤드 53, 요청 `[98,183,37,122,14,124,65,67]`, 0~199 → **FCFS 640 / SSTF 236 / SCAN(0 방향 먼저) 236 / C-SCAN(199 방향, 복귀 이동 포함) 382**
  - SCAN/C-SCAN의 방향과 복귀 계산은 교재마다 달라서 화면에 명시한다.
- 캐시, 배열 `a[4][8]`, 캐시 라인 = 원소 4개, 캐시 2줄(LRU) → **행 우선 적중 24/미스 8, 열 우선 적중 0/미스 32**

### 7-3. 알려진 문제
- 기초 콘텐츠가 손필기 3장 기반이라 과목이 빠져 있다(5-5 참고). 심화는 9개뿐이다.
- 용어 자동 링크가 문맥을 무시한다(5-3 참고).
- 퀴즈 기록과 기억 표시가 새로고침하면 사라진다(내 메모 저장소와 통합할 것).
- 위→아래 트리에서 멀리 떨어진 형제 사이 흐름 화살표가 길어진다(프로토타입은 흐리게 처리함).
- 제목 폰트는 Google Fonts `Gaegu`(손글씨)이고 본문은 시스템 폰트다. 폰트 로딩에 실패할 때의 대체 폰트를 확인할 것.
- 문장 분리에 정규식 lookbehind를 쓴다. 구형 Safari 대응이 필요하면 교체한다.

## 9. 사용자와 일하는 방식

- **한국어로 소통한다.** 사용자는 편한 말투를 쓴다.
- **큰 작업 전에는 계획을 먼저 설명하고 동의를 받는다.** (사용자가 명시적으로 요청함)
- 단계마다 **직접 눌러볼 수 있는 결과물**을 주고, 항목별 **한줄평**을 받아 반영하는 루프가 잘 맞는다. 결과물에 “이번에 바뀐 점(한줄평 반영)” 목록을 붙이면 좋다.
- 사용자는 머릿속으로만 그리기보다 **눈으로 보는 걸** 선호한다. 설명보다 화면으로 보여준다.
- 기능 아이디어를 계속 낸다. 좋은 건 받되, 범위가 커지면 마일스톤에 배치해서 제안한다.
- 사실 정확성이 중요하다(학습 도구). 심화 내용은 출처로 확인한다.
